## Findings

### Correctness risks / gaps

#### Medium — A failed final side can produce a successful comparison

- **What's wrong.** A benchmark side writes `status=completed` while its NUnit test is still running. If the final planned side then exits nonzero, for example after a fixture teardown failure, the wrapper stops scheduling sides and invokes the comparison with all planned artifacts already present. The comparison has no record of the process failure and can return `acceptable` with exit 0. The documented contract calls for exit 2 for a failed side.
- **Evidence.** The pipeline writes the completed artifact before NUnit teardown. The wrapper observes the child exit code, then discards the failure when it breaks out of the loop and returns the report's exit code. The Pester failure test configures the mocked report to return 2, so it cannot catch disagreement between the child process and completed artifacts. [PerfBenchmarkSidePipeline.cs L258–L267](https://github.com/Ed-Fi-Alliance-OSS/Data-Management-Service/blob/6eced35cfce7ac0b5f2e73082e3c492070d5f12d/src/dms/tests/EdFi.DataManagementService.Performance.Harness/Measurement/PerfBenchmarkSidePipeline.cs#L258-L267), [ApiIntegrationTestBase.cs L528–L539](https://github.com/Ed-Fi-Alliance-OSS/Data-Management-Service/blob/6eced35cfce7ac0b5f2e73082e3c492070d5f12d/src/dms/tests/EdFi.DataManagementService.Tests.Integration/ApiIntegrationTestBase.cs#L528-L539), [BenchmarkComparison.psm1 L691–L715](https://github.com/Ed-Fi-Alliance-OSS/Data-Management-Service/blob/6eced35cfce7ac0b5f2e73082e3c492070d5f12d/eng/performance/BenchmarkComparison.psm1#L691-L715), [BenchmarkComparison.psm1 L916–L945](https://github.com/Ed-Fi-Alliance-OSS/Data-Management-Service/blob/6eced35cfce7ac0b5f2e73082e3c492070d5f12d/eng/performance/BenchmarkComparison.psm1#L916-L945), [BenchmarkComparison.Tests.ps1 L345–L353](https://github.com/Ed-Fi-Alliance-OSS/Data-Management-Service/blob/6eced35cfce7ac0b5f2e73082e3c492070d5f12d/eng/performance/tests/BenchmarkComparison.Tests.ps1#L345-L353), [Harness README L466–L472](https://github.com/Ed-Fi-Alliance-OSS/Data-Management-Service/blob/6eced35cfce7ac0b5f2e73082e3c492070d5f12d/src/dms/tests/EdFi.DataManagementService.Performance.Harness/README.md#L466-L472)
- **Impact.** Automation can accept a failed run, and the retained JSON and Markdown can describe it as valid. A targeted reproduction with both side artifacts present, a failed final side, and the real comparison loader, engine, and writer returned exit 0.
- **Recommendation.** Persist the final child exit status for each side and make nonzero or missing status invalidate the comparison. Cover a final side that writes complete evidence and exits nonzero, asserting both the report and wrapper exit code.

#### Medium — The report accepts paging results from a different commit

- **What's wrong.** The new report loader deserializes `run-manifest.json` and `results.json` without invoking the existing artifact validator. Its projection takes commit and provider identity from the manifest and latency from the rows. If a retained candidate directory has the right manifest but contains baseline `results.json` from the same workload, matching scenario IDs, offsets, and sample counts let the baseline timings pass as candidate evidence.
- **Evidence.** The normal producer validates the files together. That validator checks the rows' subject and runner commits against the manifest and checks that latency summaries agree with raw samples. The report loader discards these row identities before applying its own manifest-identity and workload checks. ### Design/spec drift

#### High — Neither provider completed the required qualification

- **What's wrong.** Jira requires at least five independent same-build qualification pairs per provider, repeatable detection of the declared slowdown through the candidate path, and reported near-boundary probes. The branch ships a provisional 0.3.0 profile with both fingerprints unset. The Jira comment confirms that the qualification campaign did not run. The SQL Server write reached an in-band sizing factor and a 13% derived threshold, which covers one of the four provider/scenario demonstrations at the sizing stage.
- **Evidence.** The committed design requires separate provider qualification. The README reports demonstration thresholds of 22% and 61% for PostgreSQL and 20% for the SQL Server read, all above the 13% limit. The SQL Server read also missed the sizing band. Both providers still lack the required repeatability, detection, and boundary-probe evidence. [DMS-1019 acceptance criteria and qualification comment](https://edfi.atlassian.net/browse/DMS-1019), [04-performance-benchmarks.md L33–L49](https://github.com/Ed-Fi-Alliance-OSS/Data-Management-Service/blob/6eced35cfce7ac0b5f2e73082e3c492070d5f12d/reference/design/backend-redesign/epics/12-ops-guardrails/04-performance-benchmarks.md#L33-L49), [benchmark-profile.json L1–L7](https://github.com/Ed-Fi-Alliance-OSS/Data-Management-Service/blob/6eced35cfce7ac0b5f2e73082e3c492070d5f12d/src/dms/tests/EdFi.DataManagementService.Performance.Harness/Configuration/benchmark-profile.json#L1-L7), [benchmark-profile.json L75–L122](https://github.com/Ed-Fi-Alliance-OSS/Data-Management-Service/blob/6eced35cfce7ac0b5f2e73082e3c492070d5f12d/src/dms/tests/EdFi.DataManagementService.Performance.Harness/Configuration/benchmark-profile.json#L75-L122), [Harness README L575–L625](https://github.com/Ed-Fi-Alliance-OSS/Data-Management-Service/blob/6eced35cfce7ac0b5f2e73082e3c492070d5f12d/src/dms/tests/EdFi.DataManagementService.Performance.Harness/README.md#L575-L625)
- **Impact.** The branch delivers comparison mechanics and diagnostic evidence. PostgreSQL and SQL Server remain unqualified for the declared +20% p50 sensitivity. The current warnings use provisional thresholds.
- **Recommendation.** Keep qualification open until both providers complete the documented campaign at the original +20% target, or explicitly revise the ticket scope and track qualification as follow-up work. Describe the SQL Server write as calibrated and sized pending qualification.

#### Medium — A frozen profile blocks the documented recalibration workflow

- **What's wrong.** After moving a frozen profile to a different supported host, all sides can agree with each other and pass the required environment rules. The engine still rejects `Calibration` and `Sizing` against the old qualified fingerprint. It then suppresses the replacement fingerprint, threshold suggestions, and sizing output. The README instructs operators to recalibrate first and update those values afterward.
- **Evidence.** `Compare` calls `CheckQualifiedEnvironment` for every purpose before it decides whether to emit calibration and sizing output. The profile validator requires both fingerprints at version 1.0.0 or later, so clearing the stale fingerprint while keeping the frozen version also fails. The existing mismatch test uses the default `Candidate` purpose. - **Impact.** Moving to another host or changing a fingerprinted database setting requires an undocumented profile change before the workflow can derive replacement parameters. A targeted reproduction with identical sides on a different CPU model returned `invalid` and emitted no calibration block.
- **Recommendation.** Allow same-build `Calibration` and `Sizing` to derive provisional evidence for a new fingerprint after required-value, sampling, and within-run consistency checks pass. Keep the qualified-fingerprint match for candidate comparisons and qualification runs.

## Verification and Limitations

- **Coverage.** Reviewed the wrapper's setup, prebuild and side sequencing, the profile and workload, read and write verification, PostgreSQL fixture preparation and plan replay, evidence loading and comparison, report generation, and the CI and documentation changes. Diff scope was 45 files. The design index edits were checked for story-link consistency.
- **Executed checks.** `git diff --check df7e23425beef2de46fa98b3b5b48578cb2d3692 6eced35cfce7ac0b5f2e73082e3c492070d5f12d` passed. Three database-free reproductions exercised the frozen-profile recalibration case, mismatched retained paging artifacts, and a failed final side. They used synthetic evidence from the harness test builder and the local .NET harness binary. The binary's bundled profile hash matched the branch profile. The final-side reproduction stubbed the side and used the real PowerShell orchestration, comparison engine, and report writer.
- **Test source inspected.** The wrapper Pester cases for setup, ordering, failed sides, exit codes and collection, the NUnit tests for workload and side artifacts, and the comparison tests for environment mismatch, coverage, qualification eligibility and directory loading. Full suites and live PostgreSQL and SQL Server benchmarks were outside the verification performed.
- **Gaps.** Qualification results are based on Jira, the PR, and the README. The review did not inspect the raw Jira evidence archive or independently measure benchmark variance.
