# DMS-1606: OAuth token error contract

Date: 2026-10-20. Status: **written specification awaiting user approval**. The decisions and two design sections below were approved in conversation; that does not approve this written artifact or an implementation plan. No story implementation, builds, local tests, or Docker actions have been performed.

## 1. Intent, authority and scope

Make DMS token failures consumable by OAuth clients through root `error` / `error_description` strings, JSON media type, appropriate statuses, and a usable Basic challenge, while preserving successful requests and safe response-to-log diagnostics.

Authority: [DMS-1606](https://edfi.atlassian.net/browse/DMS-1606), refined by the explicit decisions below; existing disclosure and request contracts remain authoritative except where expressly superseded. Baseline: current branch `DMS-1606`, commit `334ce4443a172d8b6ef145c5367d68068f52c351`. Work stays in this repository and branch.

Apply the contract to the two supported-content-type POST token mappings, at the root and existing qualified routes. Include their manager/handler failures, selected-endpoint global-limiter 429, and writable frontend 413/500 responses. Identify the mappings through endpoint metadata, not substring/path guesses.

Explicit exclusions approved in conversation: unsupported-content-type POST fallback 404; non-POST 405; startup configuration failures without token endpoint selection; responses already started; disconnected clients; and failures generated by servers/proxies outside DMS application control. Those retain existing behavior. Do not change DMS 404 to ODS 415 under this story.

Also excluded: CMS implementation changes, token issuance, new grants or scope forwarding, strict Basic decoding, JSON duplicate rejection, tenant/authorization changes, global FailureResponse replacement, general correlation/serializer consolidation, DMS-1550's Warning-log policy, persistence, schema hashes and mapping-version changes. `RelationalMappingVersion` remains v3.

## 2. Approved choices and rationale

| Decision | Contract |
|---|---|
| D1: infrastructure | Preserve 429/502/503. Use `temporarily_unavailable` for 429/503 and `server_error` for 502. These are documented DMS token extensions, not RFC 6749 section 5.2 token codes. Writable selected-endpoint 500 also uses `server_error`; 413 uses `invalid_request`. |
| D2: format / diagnostics | Strict OAuth body; preserve normalized correlation through one reversible ASCII-encoded response header. Do not retain problem-details body members. |
| D3: parity / local classification | Use the row matrix below: no credentials and partial credentials are disjoint normalized-value cases. Retain malformed Basic-like 400 and existing parsing/check order. Explicitly document departures from DMS-1604/ODS. |
| D4: provider fallbacks | Every upstream 401 remains 401 invalid_client despite malformed bodies. Recognized provider 400 codes remain 400, except invalid_client after caller Authorization authentication becomes 401. Unclassifiable provider 400 becomes safe 502. Unusable descriptions use fixed DMS text. |
| D5: ownership / verification | DMS-1606 owns row 13's single parsing fix and coverage; cross-reference DMS-1549 and reconcile its old envelope/log wording explicitly. Preserve unit and real-stack E2E coverage for every inventory row. Jira workflow changes remain with ticket owners. |

Choose one DMS token-local helper and the existing HTTP boundaries. A global error conversion would affect resource/token_info responses and risk rewriting already serialized content; a shared DMS/CMS package adds coupling without a demonstrated requirement. The local helper gives all token error producers one serialization/header contract, without a new framework.

ODS parity is precise rather than universal: strict OAuth body shape and supported request families align. Missing/partial credentials, mixed mechanisms, missing grants, malformed JSON and Basic challenge behavior intentionally differ. Infrastructure proxy policy and the correlation response header are DMS-specific. ODS itself uses shared problem responses outside its token action. See the [source comparison](../../.plans/DMS-1606-ods-parity-validation.md), including current-main, pinned-ADR and release refs; no live parity execution is asserted.

## 3. Wire contract and complete story matrix

Every in-scope error has HTTP media type `application/json` (UTF-8 charset allowed), a root `error` string and a root nonempty `error_description` string. This design always supplies a usable description although OAuth makes it optional. No `error_uri`, `type`, `title`, `status`, `detail`, `correlationId`, `validationErrors`, or `errors` body members are emitted.

Every token 401 has exactly the DMS-owned challenge `Basic realm="EdFi.DataManagementService"`. Other error statuses have no WWW-Authenticate challenge. Never copy arbitrary provider challenges, correlation values, or other upstream headers.

Every in-scope error has `X-Correlation-ID = Uri.EscapeDataString(normalizedTraceId.Value)`: UTF-8 percent encoding, unreserved characters unchanged, literal percent encoded, and decoding exactly once recovers the exact log value. Continue existing cached ingestion, configured request-header selection, fallback ID and normalization limits. The output header is fixed and independent of whether client-ID ingestion is enabled. Do not tighten normalization to ASCII. Update gateway fallback guidance to name this header and its decoding rule.

Rows assume earlier validation has passed. C = the fixed Basic challenge above; all rows also require the media/body/correlation contract. Fixed descriptions reuse existing safe text where applicable; add fixed messages for missing grant, malformed JSON and generic recognized provider codes without usable descriptions.

| Story row / condition | HTTP / error | Challenge | Affected behavior and meaningful verification |
|---|---|---|---|
| 1: no header, neither body field nonblank | 401 / invalid_client | C | Manager splits the existing missing-pair branch using normalized values. Unit + E2E cover absent/null/empty/both-blank equivalence. |
| 2: no header, exactly one body field nonblank | 400 / invalid_request | None | Manager classifies a partial pair. Cover each side missing/null/empty/blank, form and JSON, with no outbound send. |
| 3: non-Basic header rejected locally | 401 / invalid_client | C | Keep existing Basic recognition and body-cannot-rescue rule. Cover with and without body credentials; retain known substring-recognition limitation. |
| 4: present empty/whitespace header | 400 / invalid_request | None | Preserve distinction from absent header and precedence over body credentials. |
| 5: malformed Basic-like header rejected by header addition | 400 / invalid_request | None | Preserve rejection location after grant validation; do not expose/log the header or FormatException message. Test malformed header with valid and invalid grant. |
| 6: Basic plus any nonblank body credential | 400 / invalid_request | None | Preserve mixed-mechanism rule; test partial mixed pair and blank/empty fields that still count as omitted. |
| 7: repeated form grant_type/client_id/client_secret | 400 / invalid_request | None | Frontend rejects before manager. Cover mixed-case names, duplicate empty values and duplicate plus Bearer. |
| 8: complete body pair with a field over 2048 UTF-16 units | 400 / invalid_request | None | Preserve cap and earlier partial/mixed checks. Cover both fields at 2048/2049 and no outbound send. |
| 9: missing/empty/null grant, otherwise valid request | 400 / invalid_request | None | Separate missing from unsupported in manager. Cover form and JSON null; credentials still take precedence. |
| 10: present unsupported grant | 400 / unsupported_grant_type | None | Whitespace-only is present unsupported, without trimming. Preserve case-insensitive client_credentials acceptance. |
| 11: malformed/mistyped/empty/null JSON body | 400 / invalid_request | None | Replace frontend empty 400 with fixed OAuth error. Cover wrong field types and Production/Development; no manager call or secret-bearing parse logs. |
| 12: upstream object 401 | 401 / invalid_client | C | Classify from status, not provider code. Cover correct/missing/unknown/non-string fields, CMS problem object and both caller mechanisms. |
| 13: upstream non-object/unparseable 401 | 401 / invalid_client | C | Reuse guarded object parser; fixed description and selected-summary Information event. Cover empty/HTML/array/string/number/boolean/null; genuine transport still row 17. |
| 14a: upstream 400 with recognized section 5.2 string code | 400 / same code | None | Allow exact ordinal lowercase six-code allowlist. Preserve only usable description; exercise every code, plus unusable-description fallbacks. |
| 14b: upstream 400 invalid_client after caller Authorization authentication | 401 / invalid_client | C | Mandatory exception to 14a; use original caller context, not DMS's generated upstream Basic. Body-auth invalid_client remains 400. Test both through real manager to HTTP. |
| 14c: upstream 400 without usable recognized code | 502 / server_error | None | Malformed/non-object/missing/unknown/non-string/unsafe code is an unusable provider response; same safe gateway body as row 17. |
| 15: upstream 429 | 429 / temporarily_unavailable | None | Preserve canonical-limit recognition and locally reconstructed limit/reuse guidance in error_description; otherwise fixed generic rate-limit text. Cover both accepted CMS URNs, malformed/near-miss/hostile inputs. |
| 16: upstream 409 contention | 503 / temporarily_unavailable | None | Fixed retry description, trace-only Information event, no provider body parsing/disclosure and no invented Retry-After. |
| 17: other upstream non-200 status / transport failure | 502 / server_error | None | Keep fixed, externally equivalent gateway responses. Cover upstream 5xx/other status and deterministic transport abort; preserve existing diagnostic levels. |

Additional selected-endpoint paths: limiter 429 uses fixed generic rate-limit description and preserves existing Retry-After metadata/rounding; frontend body-limit 413 uses fixed invalid-request description; unexpected frontend 500 uses fixed generic server description. All have no challenge and carry encoded correlation when writable. Unit/HTTP tests must prove non-token controls retain their previous responses and no rewrite occurs after response start or client disconnection.

## 4. Components and flow

1. `TokenEndpointModule` keeps form/JSON parsing, duplicate detection, normalization inputs and routes. Add token metadata to both POST mappings. Direct parser/duplicate errors use the same token response helper as Core.
2. `OAuthManager` keeps `IOAuthManager` and its existing parameters/HttpResponseMessage return. Apply the matrix, retaining original caller Authorization context before body credentials are normalized into upstream Basic. Only grant_type is sent in the upstream form; successful 200 content remains passthrough.
3. A small Core/OAuth response helper owns System.Text.Json serialization, fixed wire names, media type, status-appropriate challenge, encoded correlation and service-owned text. It accepts classified errors and safe descriptions, never raw provider JSON. It does not depend on ASP.NET.
4. Frontend response writing copies status/content/body and only the helper's approved error headers. Preserve successful-response forwarding behavior. Make X-Correlation-ID and WWW-Authenticate readable under the existing allowed-origin CORS policy without broadening allowed origins or changing middleware order; this does not promise new CORS availability on errors rejected before CORS runs.
5. `WriteRateLimitRejectionAsync` and `LoggingMiddleware` select token formatting only when endpoint metadata identifies a token POST. Keep existing request logging and status semantics. When an unexpected exception is caught before response start and writing the OAuth error succeeds, finish that handled response after its failure log rather than rethrowing and risking server replacement/abort. If already started, canceled, or writing fails, preserve existing failure handling; do not buffer or rewrite a partial response. Non-token exception handling remains unchanged.
6. Keep the shared `FailureResponse` API and all non-token consumers. After call-site analysis, remove only private token formatting code/constants made unused by replacement, and correct touched comments (including the stale 5xx-to-503 claim). Safe parser and log-summary functions remain reusable; wire string validation must not change scalar log-summary behavior accidentally.

## 5. Disclosure, diagnostics and compatibility safeguards

- Provider codes for row 14 must be actual JSON strings in the exact allowlist: invalid_request, invalid_client, invalid_grant, unauthorized_client, unsupported_grant_type, invalid_scope. Do not stringify numbers/booleans, normalize an unknown code into a known code, or accept the DMS infrastructure extensions as provider section 5.2 codes.
- A provider description is usable only as a nonempty JSON string whose decoded characters are U+0020-U+0021, U+0023-U+005B, or U+005D-U+007E. Escaping JSON Unicode/control/quote/backslash characters does not make the decoded value conformant. Invalid descriptions use fixed DMS text without changing an otherwise valid classification. Do not add a new response-description size policy under this story.
- Never pass nested fields, arbitrary body text, provider error_uri, internal URIs or provider-authored 429 messages to the client. Rebuild canonical token-limit guidance from the parsed positive integer and DMS templates; move its information from the old errors array to error_description.
- On 401 fallback, including malformed/non-object bodies or newly unusable descriptions, emit the existing selected-summary Information event under normalized TraceId.Value. Reuse names-only handling for nonstandard members, URI withholding, sanitize-before-truncate, 2048-character per-summary bounds and 20 other-field names. Emit even when no fields can be summarized. Use the same summary discipline for newly handled classified-400 description fallbacks. Keep current generic-429 Warning and contention trace-only logging.
- Existing 502 bounded/sanitized Warning-body logging and transport Error logging remain governed by current behavior/DMS-1550; do not claim an all-level no-body policy or widen logs. Manual JSON parse exceptions and malformed-header exception messages remain withheld. Assert request secrets and nested/URI sentinels do not leak through the new response or selected-summary paths.
- Preserve no-store behavior from SecurityHeadersMiddleware, success payloads, request-field/grant casing, empty/null normalization, whitespace behavior, credential percent encoding, cap and validation precedence. Do not add new provider Retry-After forwarding.
- Regression assertions must distinguish duplicate-before-header, credential-before-grant, mixed/partial-before-cap, cap-before-grant, and grant-before-header-add. Include percent, plus, slash, Unicode and surrogate-normalization cases in header decode-to-log equality; do not construct new TraceIds outside the existing ingestion contract.
