# Story: Document the Custom-Validator Implementer Guide

## Description

Once the contract, the fan-in step, and the composition seam have shipped, none of the reasoning behind them is written anywhere an implementer outside this spike would find it. This story adds implementer-facing documentation, packaged with the abstractions package so it travels with the contract rather than living only in the repository, per:

- `reference/design/custom-validation-DMS-1345/design.md` ("### Registration and Composition", "### Lifetime and Resolution", "## Failure Surfacing", "## Security Posture", "## Versioning and Compatibility")
- `reference/design/plugins-DMS-1462/design.md` ("### The Plugin Contract", "### Load Isolation", "### Trust Model and Verification") for everything about delivery

**Scope change 2026-08-27: the delivery path is a plugin, not a composition-root call.**
Spike DMS-1462 reversed the compiled-in decision (`reference/design/plugins-DMS-1462/design.md`, "## Divergence from the Custom Validation Epic").
This guide covers authoring a validator, registering it inside an `EdFiApiPlugin.ContributeServices` override, what the contract does and does not give it, and the failure semantics it must design around.
Packaging, directory layout, acquisition, and the trust model are the plugin implementer guide's subject (`PLUGINS.md`, packed into `EdFi.Api.Plugins`), and this guide links there rather than restating them.
The criteria below that described compiled-in delivery are marked superseded in place, with their replacement stated, so a reader of the filed ticket sees both.

This story now also depends on the plugin spine's host-integration story, since the sample it documents runs only under the loader.

Several of the guide's obligations are places where the obvious phrasing would overpromise, and the design assigns them here deliberately rather than leaving them to be discovered. The startup guard catches unresolvable constructor dependencies but not a service that constructs cleanly and throws when its request-scoped state is read, so the per-request-state rule is stated as a rule the implementer follows, not a guarantee the platform enforces. Reaching around the contract to host services such as `IDocumentStoreRepository` works and nothing stops it, so the guide states the supported-versus-possible line rather than implying an enforcement that does not exist. And the ODS UniqueId behaviour DMS-1414 will want is blocked by two gaps rather than one, store reads and document identity, so the guide names both instead of implying that a store-read capability alone would deliver it.

This story depends on the abstractions-contract, fan-in-step, and composition-seam stories, and grounds every claim in what those actually shipped rather than re-deriving it from design.md.

## Acceptance Criteria

- A markdown document under `src/dms/core/EdFi.DataManagementService.CustomValidation/` contains a compiling code sample showing how to implement `ICustomResourceValidator`, including its `AppliesTo` declaration and the full `ValidateAsync` signature.
- The same document contains a compiling code sample of an `EdFiApiPlugin` subclass whose `ContributeServices` override registers the validator with `TryAddEnumerable` and configures its options, showing both the `Action<TOptions>` overload of `Configure` and the `configuration.GetSection(...)` form. It states which package each line needs, because neither contract package supplies them: `EdFi.Api.CustomValidation` declares no dependencies at all (`src/dms/core/EdFi.DataManagementService.CustomValidation/EdFi.DataManagementService.CustomValidation.csproj:21-35`) and `EdFi.Api.Plugins` declares only `Microsoft.Extensions.Configuration.Abstractions` and `Microsoft.Extensions.DependencyInjection.Abstractions`. So `TryAddEnumerable` is reachable through `EdFi.Api.Plugins`, the `IConfiguration` parameter and `GetSection` are too, and the implementer declares `Microsoft.Extensions.Options` for the `Action<TOptions>` form and `Microsoft.Extensions.Options.ConfigurationExtensions` for the section-binding form. The guide states this as a property the implementer inherits rather than a gap: the contracts oblige a consumer to nothing they did not choose. SUPERSEDED: the composition-root snippet. A deployment adds no line anywhere; it names the plugin in `Plugins:Allowed`, and the guide shows that configuration instead.
- The document states that a breaking change to `ICustomResourceValidator` or `CustomValidationFailure` requires every validator to be recompiled. The published id is `EdFi.Api.CustomValidation`, the semver promise covers the contract's own types and nothing else, and the package version is the contract's own rather than the DMS release version, so a validator built against contract `1.0.0` is compatible with every DMS release that carries `1.0.0` whatever that release is numbered. The package is built but not yet published; see design.md "### Publishing deferral".
- The document restates the corrected version of what `ICustomResourceValidator`'s own XML documentation says about delivery. The plugin spine's host-integration story corrects `src/dms/core/EdFi.DataManagementService.CustomValidation/ICustomResourceValidator.cs:16-17`, which currently tells an implementer the interface "is compiled into the host deployment and registered into DMS's composition; it is not loaded from a dropped-in assembly at runtime"; this guide must not contradict the corrected comment, and a test asserts the two agree on the delivery path.
- SUPERSEDED: the "surfaces at the implementer's own compiler" guarantee rested on compiled-in delivery. Replaced by: the document states that the contract follows an additive-only policy for the life of the package, so a validator built against an older `EdFi.Api.CustomValidation` runs on a newer host by construction, that a member added to `ICustomResourceValidator` after first publication carries a default implementation, and that target framework remains a compatibility axis alongside the package version because a plugin is served the host's shared framework.
- SUPERSEDED in its premise, retained in its consequence. There is no rebuild precondition under host-first loading: the host's contract assembly is served to the plugin whatever version it compiled against, so the two directions are stated instead. An older plugin on a newer host binds to the host's copy and runs. A newer plugin on an older host is refused at load with a named fatal, "plugin requires EdFi.Api.CustomValidation >= X, host carries Y", before any type is loaded. The document also states the third case the guard cannot see: a validator whose `ValidateAsync` body reaches a host assembly member that exists at compile time and not on the deployed host (possible only for a plugin that reached around the contract into host assemblies, which the supported-versus-possible line below already forbids) surfaces as a logged 500 on the first matching write, not at startup, because that method is not JIT-compiled until then.
- The document states the constructor rules: constructors run on every write request regardless of whether `AppliesTo` matches, so they must stay trivial; and a validator's constructor must not require per-request state. The second is stated as a rule the implementer follows, with an explicit note that the startup guard catches only unresolvable dependencies and will not catch a service that constructs cleanly and throws when its request-scoped state is read.
- The document states the transient-only lifetime rule and that the startup guard aborts the process on a non-transient descriptor, on an `ImplementationInstance` descriptor, and on an `ImplementationFactory` descriptor, so an implementer knows why a factory registration is rejected. It must also state what to use instead, since the rejected shape includes the legitimate `ServiceDescriptor.Transient<ICustomResourceValidator, MyValidator>(sp => new MyValidator(...))` form: a constructor argument that is not itself a service is supplied through `Configure<TOptions>` and `IOptions<TOptions>` constructor injection. Without that, an implementer hits the guard with no documented way forward.
- The document states that `AppliesTo` matching is exact and case-sensitive, that there is no wildcard, and that an entry matching no resource produces a startup warning rather than a failure, so a typo surfaces as a warning rather than as a validator that silently never runs.
- The document states the `AppliesTo` getter's cost rule, the sibling of the constructor rule above: the fan-in step reads `AppliesTo` on every write request for every registered validator, before any filtering happens, so the getter must be cheap, synchronous, and free of I/O. A lookup inside the getter slows every write the deployment serves, including writes to resources that validator does not apply to and writes whose `ValidateAsync` is never called. It belongs beside the constructor rule rather than left implicit, both being costs an implementer pays on writes their validator has nothing to say about, and the guide covering only one of the pair is what would make the other look acceptable.
- The document states what `document` actually is: the profile-effective body, which is the profile-shaped body when a writable profile applies and `ParsedBody` otherwise, together with the consequence that version metadata injected into `ParsedBody` is visible on non-profile writes and absent on writable-profile writes.
- The document states that a returned `OnPath` or `OnResource` failure always produces a 400 in the documented shape, and that an unhandled validator exception always produces a loud, logged 500, never a silent success. It notes that two of the catch chain's three special-cased exception types belong to Core's own authorization machinery: one is not referenceable from the abstractions package at all, and throwing the other from a validator is unsupported. The third is cancellation, and the guide states its consequence for a validator doing outbound I/O: an `OperationCanceledException` raised on a request the client has already aborted propagates rather than becoming a 500, so a validator must not swallow the token's cancellation and report a validation failure instead.
- The document states that message order within `errors` and within each `validationErrors` entry is not part of the contract and a client must not depend on it. This is a client-facing contract term that would otherwise reach no deliverable.
- The document states the write-path cost of I/O in a validator: the fan-in step awaits every applicable validator before the request reaches its handler, so a slow or unreachable external system makes every matching POST and PUT slow or failing; the only timeout is whatever the validator's own client is configured with; and a timeout surfaces as a 500 rather than a skipped validator.
- The document states the deployment-scoping rule: a registration belongs to a whole DMS deployment, not to one district, so a district-specific rule is scoped by the `ValidationScope` that `ValidateAsync` receives. It must state that `Tenant` is null unless multi-tenancy is enabled and that `RouteQualifiers` is how a district is normally identified, so an implementer does not write a rule that silently never matches in a single-tenant routed deployment.
- The document states the security posture an operator inherits: a validator runs in the DMS process with full process trust and can do anything that process can do, that the load context isolates assembly identity and is not a security boundary, and that the trust boundary is whoever controls the plugin root and the allowlist, linking to the trust model in the plugin implementer guide and `docs/OPERATIONS.md` for the controls.
- The document states that this version's contract gives a validator no store access, so rules requiring a lookup against stored data cannot be expressed within the supported surface. It must also state the supported-versus-possible line rather than implying an enforcement that does not exist: an implementer can reference a host assembly and constructor-inject services such as `IDocumentStoreRepository`, nothing stops it, and doing so forfeits the package's compatibility promise because those assemblies carry no semver commitment.
- The document states that the ODS "a person's UniqueId cannot be modified" rule is not expressible under this version's contract, and gives both reasons design.md records rather than only the first. The rule compares the submitted UniqueId against the **persisted** one, which needs a store read this contract does not offer; and it keys that read on the persisted document's own identifier (`EdFi.Ods.Features/UniqueIdIntegration/Validation/UniqueIdNotChangedEntityValidator.cs:39`), which `ValidateAsync` never receives, there being no `DocumentUuid` parameter and `ValidationScope` carrying route qualifiers rather than the route. It points at both deferred items, store access and document identity, so a reader concludes neither that the gap is an oversight nor that store access alone closes it.
- The document states why the document body is not a substitute for that missing identity, since an implementer who reads the previous point will otherwise reach for `$.id`. On `Update` the pipeline does require a body `id` matching the route id (`Validation/MatchingDocumentUuidsValidator.cs:23-27`), but a writable profile can strip `id` from the profile-effective body the validator actually receives, since an `IncludeOnly` member filter keeps only the members the profile names (`Profile/WritableRequestShaper.cs:661-670`); and on `Upsert` the body carries no `id` at all by construction (`Middleware/RejectResourceIdentifierMiddleware.cs:35-45`).
- SUPERSEDED and inverted. The document states that a validator is delivered as a plugin: a directory under the plugin root named in `Plugins:Allowed`, published with `dotnet publish --no-self-contained`, and links to `PLUGINS.md` for layout, packaging, acquisition, and the fatal catalogue. It states that compiling a validator into a DMS build remains possible and is not the documented route.
- The document is the contract project's `CUSTOM-VALIDATION.md`, which the csproj already declares as its `PackageReadmeFile` and which the packed nupkg already carries. This story replaces its placeholder content with the full guide.
- The validator sample and the `EdFiApiPlugin` sample are mirrored verbatim as compiling fixture classes in a project whose only Ed-Fi references are the packed `EdFi.Api.CustomValidation` and `EdFi.Api.Plugins`, plus whichever `Microsoft.Extensions.Options*` packages the samples themselves need, declared by that project rather than inherited. That is exactly what `eng/verification/CustomValidationConsumer/CustomValidationConsumer.csproj:57-58` already does and what design.md's "### Registration and Composition" states as policy, and it is what makes the project match an external implementer rather than a project with a richer closure. Mirroring them into `EdFi.DataManagementService.Core.Tests.Unit` would prove nothing, since that project references Core, the frontend, and three Backend projects and has `InternalsVisibleTo` on Core, so a sample reaching for a Core internal would compile green there and fail for every real consumer.
