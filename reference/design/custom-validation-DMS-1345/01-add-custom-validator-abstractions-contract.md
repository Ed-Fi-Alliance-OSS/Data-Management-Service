# Story: Add the Custom-Validator Abstractions Contract

## Description

DMS's four validator interfaces are all `internal` to `EdFi.DataManagementService.Core`, so nothing outside that assembly can implement or replace them without modifying core source. This story ships the public, versioned contract a district or vendor implements against, per:

- `reference/design/custom-validation-DMS-1345/design.md` ("### Validator Contract" defines the types; "### Resource Applicability" and "### Per-Invocation Inputs" define their semantics)

The contract is six public top-level types in `EdFi.DataManagementService.CustomValidation`: `ICustomResourceValidator`, `CustomValidationFailure` (with nested `OnPath` and `OnResource`), `ValidatedResource`, `ValidatedResourceInfo`, `CustomValidationOperation`, and `ValidationScope`.

Shipping the types is only half the work. A contract nothing packs is not consumable by an implementer, so this story also adds the pack path: a `build-dms.ps1` target and a per-PR lane that packs the package, asserts its contents, and compiles a scratch consumer against it. It stops short of publishing; see design.md "### Publishing deferral".

This story ships the contract only. It does not wire any pipeline step to consume it and does not implement any concrete validator.

**Scope change: the contract ships from its own project, and is packed but not published.**
The contract types and the inputs their signatures name live in a new project, `EdFi.DataManagementService.CustomValidation`, packaged as `EdFi.Api.CustomValidation`, rather than in `EdFi.DataManagementService.Core.External`.
The per-PR lane packs the package, asserts its contents, and compiles a scratch consumer against it; no prerelease or release job publishes it.
design.md "**The contract declares its own inputs**" and "### Publishing deferral" are the authoritative statements of both changes and are not restated here.

Three criteria below are superseded rather than suspended, because the contract no longer ships from `Core.External`: the package id is `EdFi.Api.CustomValidation` rather than `EdFi.Api.Core.External`; the contract declares its own input types rather than reusing `Core.External`'s; and `Core.External`'s package references are not touched at all, which makes the `Microsoft.CodeAnalysis` removal and the `Options`/`DependencyInjection.Abstractions` additions unrelated cleanup rather than prerequisite work.
The prerelease and release criteria are suspended, not withdrawn, and are the starting point for whoever takes publishing up at the end of the epic.

## Acceptance Criteria

- `ICustomResourceValidator`, `CustomValidationFailure` (with `OnPath` and `OnResource`), `ValidatedResource`, `ValidatedResourceInfo`, `CustomValidationOperation`, and `ValidationScope` exist as public types in `EdFi.DataManagementService.CustomValidation`, with signatures matching design.md "### Validator Contract". The packed nupkg exports exactly those types and no others, asserted against the XML documentation file the package carries.
- The contract's own member types require no new package references. Every one is either BCL (`JsonNode`, `Task`, `CancellationToken`, `IReadOnlyList<>`, `IReadOnlyDictionary<>`) or already public in that assembly (`ProjectName`, `ResourceName`, `ResourceInfo`, `TraceId`, `RouteQualifierName`, `RouteQualifierValue`).
- SUPERSEDED, see the scope note above. `Core.External` is not the published assembly and is not modified by this story, so retiring its unused `Microsoft.CodeAnalysis` reference is ordinary cleanup rather than prerequisite work. The measurement is retained because it is the reason the cleanup is worth doing at all: that one reference pulls the Roslyn packages, the six `System.Composition.*` packages, and `Humanizer.Core`, 16 of the 26 packages the assembly resolves to.
- `Microsoft.Extensions.Options` and `Microsoft.Extensions.DependencyInjection.Abstractions` are added as explicit `PackageReference`s. Both already arrive transitively through `Microsoft.Extensions.Logging`, so this changes no resolved version; it makes the registration extension's dependencies declared rather than inherited from a reference the project does not otherwise use. Note for whoever picks this up: of the two logging packages, only `Microsoft.Extensions.Logging.Abstractions` is used, and only for `EventId`.
- The produced nupkg's declared dependencies are exactly `Be.Vlaanderen.Basisregisters.Generators.Guid.Deterministic`, `Sandwych.QuickGraph.Core`, `Microsoft.Extensions.Logging`, `Microsoft.Extensions.Logging.Abstractions`, `Microsoft.Extensions.Options`, and `Microsoft.Extensions.DependencyInjection.Abstractions`, and the public types it exports from the validation namespace are exactly `ICustomResourceValidator`, `CustomValidationFailure` (with `OnPath` and `OnResource`), `ValidatedResource`, `CustomValidationOperation`, and `ValidationScope`. Both are asserted against the extracted package. The type-surface half is what fails if a registration-hook interface or a store-read facade is ever added, which a `grep` for a name that exists nowhere on any branch cannot do. An implementer registers through an ordinary `IServiceCollection` extension in their own assembly, and this version's contract offers no store access.
- `CustomValidationFailure` has a private parameterless base constructor and exactly two sealed, non-positional nested `record` cases, each with an explicit validating constructor and get-only properties.
- A unit test proves `OnPath` throws `ArgumentException` for a null path, `""`, `"$"`, and any path not `"$."`-prefixed, and for a null or empty message, and that `OnResource` throws for a null or empty message.
- A unit test proves `OnPath` **accepts** a bare `"$."`. That is DMS's own document-level `validationErrors` key - `DocumentValidator` emits it whenever `InstanceLocation` is empty (`Validation/DocumentValidator.cs:226`, `:315`) and `Middleware/ParseBodyMiddleware.cs:37` ships it - so rejecting it would make a document-level `validationErrors` entry inexpressible through this contract.
- A unit test proves that within the abstractions assembly's own public construction surface, `OnResource` is the only way to express a failure carrying no path. Asserted reflectively over `CustomValidationFailure`'s public and protected constructors, where the expected set is exactly one member, the compiler-synthesized copy constructor. The test names that constructor as expected rather than asserting an empty set, because C# forbids restricting it (CS8878). Cross-assembly derivation through it is closed *here*, not deferred to the consumption point: an abstract `private protected` member on the base record cannot be overridden from another assembly, so no concrete external case compiles (CS0534). See design.md **Sealing limit**.
- A `build-dms.ps1` package target produces a nupkg whose package id is `EdFi.Api.CustomValidation`, proven by invoking the target locally and asserting on the id inside the produced nuspec rather than on the file's existence. The id follows the repository's existing `EdFi.Api*` convention, mirroring `EdFi.Api.SchemaTools` being packed from `EdFi.DataManagementService.SchemaTools`, and cannot be changed after first publication without breaking every consumer that compiled against it.
- The csproj declares the package metadata every shipped DMS package already carries, asserted against the produced nuspec alongside the id: `PackageLicenseExpression` of `Apache-2.0`, a `PackageProjectUrl` of the repository, a `Title`, and a `Description`. `EdFi.Api.SchemaTools` declares all four in its csproj (`src/dms/clis/EdFi.DataManagementService.SchemaTools/EdFi.DataManagementService.SchemaTools.csproj`), and `EdFi.Api` and `EdFi.Api.ConfigurationService` declare the equivalents in their hand-written nuspecs, so a package published without them would be the only DMS package on the feed with no declared license. `Product`, `Authors`, and `Company` need no declaration here: they already arrive from `src/dms/Directory.Build.props`, which is why this criterion names only what that file does not supply.
- The produced nupkg contains the implementer-guide markdown at the `PackagePath` the csproj declares, proven by extracting the package. A markdown file placed beside the csproj is not packed by default SDK behaviour, so a `PackageReadmeFile` plus a matching packed content item is required. A placeholder document satisfies this criterion if the implementer-guide story has not yet landed.
- `.github/workflows/on-prerelease.yml` carries the whole per-package artifact pipeline every shipped DMS package already has, not just a pack and a push. `EdFi.Api`, `EdFi.Api.SchemaTools`, and `EdFi.Api.ConfigurationService` each have all five stages today; for `EdFi.Api` they are `pack-dms` (`:30`), `sbom-create-dms` (`:158`), `provenance-create-dms` (`:280`), `publish-package-dms` (`:309`), and the SBOM-plus-provenance upload steps inside `attach-dms-artifacts-to-release` (`:381`), with `pack-schema-tools` (`:94`), `sbom-create-schema-tools` (`:220`), `provenance-create-schema-tools` (`:295`), and `publish-package-schema-tools` (`:344`) the matching set for SchemaTools, whose release assets are attached by that same job. A fourth package added with only pack and push would be the one DMS package shipped with no SBOM and no SLSA provenance.
- Concretely, that means: the pack job exposes a `hash-code` output holding the base64 SHA-256 of the nupkg; an `sbom-create` job generates an SPDX 2.2 manifest through `Microsoft.Sbom.DotNetTool`, uploads it as `<package>-SBOM`, and exposes `sbom-hash-code`; a `provenance-create` job calls `Ed-Fi-Alliance-OSS/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@v2.0.0` with the pack job's hash and a `provenance-name` unique to this package, since a shared name would collide with the existing `edfiApi.intoto.jsonl` and `edfiApiSchemaTools.intoto.jsonl` artifacts; and the release-attach job downloads the SBOM through the SLSA `secure-download-artifact` action against `sbom-hash-code` and uploads both assets to the GitHub release. Naming the stages rather than saying "follow the existing jobs" is deliberate: the provenance file name is the one part that cannot be copied verbatim.
- `.github/workflows/on-release.yml` carries a matching `Promote ... Package` step in the `promote-azure-artifact` job, alongside the three that exist. This is required separately, since the release workflow only promotes what the prerelease workflow published.
- A scratch class library referencing the produced `EdFi.Api.CustomValidation` package, plus its own references to `Microsoft.Extensions.Options` and `Microsoft.Extensions.DependencyInjection.Abstractions`, compiles both a type implementing `ICustomResourceValidator` and the registration extension exactly as design.md "### Registration and Composition" documents it, including the `Action<TOptions>` overload of `Configure` and the `TryAddEnumerable` call. The scratch project declaring those two itself rather than inheriting them is what proves the package imposes no closure of its own.
- `dotnet build src/dms/EdFi.DataManagementService.sln` succeeds with `TreatWarningsAsErrors` set on the new contract project, which with `GenerateDocumentationFile` makes CS1591 an error and therefore makes documenting every public type mandatory.

## Tasks

1. Add a new project `src/dms/core/EdFi.DataManagementService.CustomValidation/` holding the contract types under namespace `EdFi.DataManagementService.CustomValidation`, and reference it from `EdFi.DataManagementService.Core`.
2. Implement `CustomValidationFailure` exactly as design.md specifies: private parameterless base constructor, two sealed non-positional nested records, explicit validating constructors, get-only properties.
3. Declare the contract's own inputs - `ValidatedResource`, `ValidatedResourceInfo`, and `ValidationScope` - with plain `string` members rather than reusing `Core.External`'s branded types, so the package carries no dependency on DMS's internal model. `ValidatedResourceInfo` carries identity and version only; DMS's write-path policy flags are deliberately not published, and adding a field later is a source-breaking change only for code that constructs or deconstructs the type, which DMS does and implementers generally do not, so widening it later is far cheaper than narrowing it. Declare `ValidationScope.RouteQualifiers` as `IReadOnlyDictionary<string, string>`, and state in its XML documentation that the declared type is documentation rather than protection, the defensive copy being made by the fan-in step.
4. Add unit tests in `src/dms/core/EdFi.DataManagementService.Core.Tests.Unit` covering constructor validation and the reflective single-path-less-constructor assertion.
5. SUPERSEDED, see the scope note above. The contract project declares no package references at all, so there is no dependency set to curate and `Core.External` is left alone.
6. Add a `CustomValidation` package target to `build-dms.ps1` following the `BuildSchemaToolsPackage` shape, with package id `EdFi.Api.CustomValidation`.
7. Add the package metadata properties to the csproj - `PackageLicenseExpression`, `PackageProjectUrl`, `Title`, `Description` - plus `PackageReadmeFile` and the matching packed content item pointing at the document the implementer-guide story owns, following the shape `EdFi.DataManagementService.SchemaTools.csproj` already uses.
8. Add the pack, SBOM, provenance, publish, and release-attach stages to `on-prerelease.yml` and a promote step to `on-release.yml`, following the existing API and SchemaTools jobs and giving the provenance artifact its own file name.
9. Build the scratch consumer library against the produced package, compiling both the validator and the documented registration extension, and record the result in the pull request.
