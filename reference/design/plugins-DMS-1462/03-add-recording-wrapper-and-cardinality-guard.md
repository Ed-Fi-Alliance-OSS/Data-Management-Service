# Story: Add the Recording Service Collection and Cardinality Guard

## Description

The loader returns plugin instances; something has to invoke `ContributeServices` on each, know what each one registered, and refuse the registrations the design refuses.
This story adds the recording `IServiceCollection` wrapper, the host-held cardinality registry, the Phase B invocation, and the four guard checks fed by the wrapper, per:

- `reference/design/plugins-DMS-1462/design.md` ("### Contract Cardinality", "### Startup Failure Semantics" for the wrapper and guard rows, "### Observability" for the inventory event)
- `reference/design/custom-validation-DMS-1345/03-add-custom-validator-composition-seam-and-startup-guard.md` (DMS-1434), the post-container startup guard this story extends

Three of the checks run at the wrapper, before a call reaches the real collection: removal or overwrite of a pre-existing host-owned descriptor, removal or overwrite of a pre-existing logging-pipeline descriptor, and `Clear`.
Four run after the container is built: two claims on one replace-cardinality contract, a plugin registering a host-owned service type that is no declared contract, a plugin that registered no declared contract at all, and an activation probe over every declared-contract registration.
**Two** of them key on one test, whether a `ServiceType` is declared in an assembly whose **assembly name** begins `EdFi.DataManagementService.` or `EdFi.DmsConfigurationService.`: host-owned removal and overwrite at the wrapper, and host-owned displacement in the guard.
The other three do not use it at all. The replace-conflict check counts claims against the host's own cardinality registry, the no-contract-registered check intersects a plugin's additions with that same registry, and the logging carve-out keys on four named service types.
design.md records that a third rule keyed on the host-owned test would be the signal the wrapper has become something it should not be.

**The post-container checks are a startup task of their own, in the frontend, not additions to Core's.**
DMS-1434's guard is an `IDmsStartupTask` in `EdFi.DataManagementService.Core`, which cannot see the per-plugin records this story produces in `EdFi.Api.Plugins.Hosting` without a project reference that would invert the dependency and drag the contract assembly into every Core consumer.
So `EdFi.Api.Plugins.Hosting` exposes a pure audit function over the records and the contract registry, returning findings, and the DMS frontend owns a thin `IDmsStartupTask` that calls it, ordering just above DMS-1434's guard inside the same executed 200-299 window.
Core is untouched by this story.

**This is therefore the story that adds the frontend's `ProjectReference` into `src/plugins/`, and it is the first one that needs it.**
`src/dms/frontend/EdFi.DataManagementService.Frontend.AspNetCore/EdFi.DataManagementService.Frontend.AspNetCore.csproj` references Core, Core.External, and the two backends today, and nothing more; the reference to `EdFi.Api.Plugins.Hosting` is new work.
`src/dms/Dockerfile`'s build stage already carries `src/plugins/` by then, because draft 01 put it there for exactly this reason: `.github/workflows/on-dms-pullrequest.yml` builds that Dockerfile in nine places on a relevant pull request, one shared CI image build and eight matrix legs, and a frontend reference into a tree the build stage cannot reach fails `dotnet restore --locked-mode` in all of them.

**The wrapper cannot see a declined `TryAdd`, and the answer is a registration rule rather than a projection.**
`TryAdd` reads `Count` and the indexer, compares, and returns without handing the candidate descriptor to the collection, so a decline arrives at the wrapper as an anonymous scan with no service type and no implementation type attached.
An earlier revision of the design answered that by masking replace-cardinality descriptors from each plugin's view, and that is withdrawn as unsound: `RemoveAll<T>` and `Replace` walk the collection by index, reading through the masked view and calling `RemoveAt(i)` against the real one, so over `[IReplaceContract, IB, IC]` with the first masked, `RemoveAll<IC>()` removes the two it was not asked to remove and keeps the one it was.
So the wrapper hides nothing.
A plugin claiming a replace-cardinality contract registers it with a plain `Add`, the implementer guide says so, and a plugin that used `TryAdd` and silently declined adds nothing and therefore fails the no-contract-registered check below, which names it.
That backstop reaches the decline only when the decline was the plugin's one contribution, and this story states the residual rather than implying full coverage: a plugin that also registers another declared contract or contributes a Phase A source passes every check, and the intended replacement silently never happens.

**Attribution is a snapshot-and-diff around each hook, not per-call bookkeeping.**
The invoker snapshots the real collection before each plugin's hook and compares it after: present-after-and-not-before by reference is that plugin's additions, present-before-and-not-after is its removals, and a service type in both lists is a replacement.
Hooks run one at a time in allowlist order, so each diff belongs to exactly one plugin.
The wrapper still exists, because the removal rules have to fire before a call reaches the real collection, but that is now its only job.

This story depends on draft 02 for the instances and on DMS-1434 for the guard it runs beside.

## Acceptance Criteria

- `RecordingServiceCollection` implements `IServiceCollection` and is a **pass-through**: every read member returns exactly what the real collection holds, in the same order, and every write member applies the removal rule below and then delegates. It hides, reorders, and projects nothing. Proven by asserting that a plugin enumerating the collection during its hook sees the same sequence as the real collection, that `Count`, the indexer, `IndexOf`, and `Contains` agree with it, and that a replace-contract descriptor the host registered before the hook is visible to the plugin like any other.
- `RemoveAll<T>()` called from inside a hook removes the descriptors for `T` and nothing else. This is a regression test with a named cause: an earlier design masked replace-cardinality descriptors from the plugin's view, and because `RemoveAll<T>` and `Replace` read indices through the view and write them to the real collection, `RemoveAll<IC>()` over `[IReplaceContract, IB, IC]` with the first masked removed `IReplaceContract` and `IB` and kept `IC`. Any reintroduction of a projection fails this criterion.
- The wrapper records **no** declined `TryAdd` calls, and a test documents why by driving `TryAddSingleton<IFoo, Foo2>` against a wrapper over a collection that already holds `IFoo` and asserting the wrapper observed only `Count` and indexer reads and never saw `Foo2`. That test exists so nobody later adds an acceptance criterion the seam cannot satisfy.
- Attribution comes from a snapshot of the real collection taken before each plugin's hook and diffed after it, by reference: additions, removals, and replacements are derived per plugin from that diff, and a test with two plugins registering into one collection asserts each plugin's record names only its own descriptors.
- A `PluginContractRegistry` type in `EdFi.Api.Plugins.Hosting` holds a set of `(Type contract, Cardinality cardinality)` entries the host constructs and passes to the invoker; DMS's registry names `ICustomResourceValidator` as fan-in. The type is this story's; the frontend-owned static that holds DMS's one instance of it, `DmsPluginContracts.Registry`, is draft 04's, because a DMS-specific value belongs on the DMS side of the seam. Neither name is a rename of the other, and this story's tests construct fixture registries directly rather than through `DmsPluginContracts`. The registry is never read from configuration or from a plugin. Because it is host-supplied, a fixture registry declaring a fixture replace contract is what the conflict tests below use, so none of them depends on a real replace contract existing yet.
- The registry also exposes `ContractAssemblyNames`, and it **derives** them rather than holding a second hand-written list: `typeof(EdFiApiPlugin).Assembly.GetName().Name`, which is always in the set, plus `entry.Contract.Assembly.GetName().Name` for every entry, de-duplicated ordinally. This is the value draft 04 passes to `PluginLoader.Load` for the skew preflight. Three tests pin it. DMS's own registry yields exactly `EdFi.Api.Plugins` and `EdFi.DataManagementService.CustomValidation` - the **assembly** name of the contract that packs under the id `EdFi.Api.CustomValidation`, and a test asserts the package id is not what comes out, since a reference in assembly metadata carries an assembly name and the preflight would silently match nothing. A registry with no entries still yields `EdFi.Api.Plugins`, so the base contract cannot drop out of the skew check. And adding a fixture contract entry adds its declaring assembly with no other change, which is the property that keeps a per-type contract added by a later companion document covered without touching the loader.
- `LoadedPlugins.ContributeServices(IServiceCollection, IConfiguration, PluginContractRegistry)` invokes each plugin's hook in allowlist order through its own recording wrapper, writes `invoking ContributeServices on <plugin>` to `Console.Error` **before** each call, turns a thrown exception into a fatal naming the plugin and the composition phase, and **returns** a `PluginAuditInput` carrying the per-plugin records and the registry the audit needs. `LoadedPlugins` is draft 02's aggregate over `IReadOnlyList<LoadedPlugin>`; this story adds the method to it rather than introducing a new type. A test has the fixture hook throw and asserts the announcement is already on the channel. The invoker throws rather than choosing a bootstrap phase: it is called from inside `AddServices`, so in DMS the failure lands in whichever bootstrap phase the host was running, which draft 04 states is `ConfigureServices`, and in CMS it lands in a plain `Program.cs` with no phase at all.
- Removing, replacing, or assigning through the indexer over a descriptor that was present before the plugin's hook began **and** whose `ServiceType` is host-owned is fatal at the wrapper, naming the plugin and the service type, and the real collection is asserted unchanged. Proven with `services.Replace(...)` on `IDocumentStoreRepository`, `RemoveAll<T>()` over a host type, and an indexer assignment over a pre-existing host-owned slot. `Clear` is always fatal.
- Removing a pre-existing **non-host** descriptor is permitted and recorded, outside the logging carve-out below. Proven with a fixture whose hook removes a pre-existing framework descriptor that is not in the logging pipeline set: the plugin loads, and its inventory lists the removal with the displaced implementation type.
- **A plugin that removes, replaces, or overwrites a pre-existing logging-pipeline descriptor is fatal at the wrapper**, naming the plugin and the service type, with the real collection asserted unchanged. The set is four service type names, all declared in `Microsoft.Extensions.Logging.Abstractions`: `Microsoft.Extensions.Logging.ILoggerProvider`, `Microsoft.Extensions.Logging.ILoggerFactory`, `Microsoft.Extensions.Logging.ILogger`, and the open generic `Microsoft.Extensions.Logging.ILogger<>`. It is written as service type names rather than as an assembly or namespace rule, because it must cover the types whose descriptors carry the process's logging and nothing else in `Microsoft.Extensions.*`. The set is deliberately inclusive rather than minimal: measured on `net10.0`, neither `AddLogging` nor `AddSerilog` registers a descriptor for the non-generic `ILogger`, so no removal can match it in DMS as shipped, and it is in the set anyway because the rule is about what a plugin may remove rather than about what the host happens to register. The story states that, so nobody later "tidies" the fourth name out on the grounds that nothing registers it, and no criterion asserts a fatal on non-generic `ILogger` against a DMS-populated collection, because none can fire there.
- The exercising call is `logging.ClearProviders()`, and the fixture calls it. Measured on `net10.0`, `LoggingBuilderExtensions.ClearProviders` is exactly `Services.RemoveAll<ILoggerProvider>()`: against a collection built by `AddLogging(b => b.AddConsole())` it removed the one `ILoggerProvider` descriptor and left `ILoggerFactory` and `ILogger<>` in place. DMS wires Serilog inside `AddServices` at `Infrastructure/WebApplicationBuilderExtensions.cs:125`, and Phase B runs after `AddServices`' own registrations, so the providers a plugin clears are the host's. An earlier revision made this the criterion that proved the removal exemption; it is now the criterion that proves the carve-out, and the change of direction is deliberate rather than a wording drift.
- The fatal is asserted to be **reportable**: the test asserts the message reached `Console.Error` and that the collection still holds the host's `ILoggerProvider` descriptors when it did, which is the property that comes from refusing the call before it lands rather than auditing after it.
- A plugin that only **adds** an `ILoggerProvider` loads unaffected, which keeps the carve-out from being a ban on a plugin shipping its own sink.
- A plugin that registers a descriptor and then replaces it is unaffected, which pins the pre-existing scope.
- A fixture plugin calling the real `AddHttpClient()`, `AddOptions<T>().Bind(...)`, `AddLogging()`, and one real cloud SDK client registration, against a collection DMS's own `AddServices` has already populated, loads with nothing rejected. This is a test against the libraries as shipped, not against a fixture that imitates them. What it proves is that the wrapper does not reject ordinary registration work; it does **not** prove the pre-existing scope, because none of those four removes anything. A metadata sweep of `Microsoft.Extensions.Http`, `Microsoft.Extensions.Options`, `Microsoft.Extensions.Options.ConfigurationExtensions`, and `Microsoft.Extensions.Azure` 1.11.0 found their only `ServiceCollectionDescriptorExtensions` references to be `TryAdd`, `TryAddSingleton`, `TryAddTransient`, and `TryAddEnumerable`, so an earlier claim that `AddHttpClient`, options builders, and `AddAzureClients` call `Replace` and `RemoveAll` internally is false and this criterion no longer rests on it. The pre-existing scope is proven by the own-descriptor `Replace` criterion above; the `ClearProviders` criterion proves the logging carve-out, not the scope. The cloud SDK is `Microsoft.Extensions.Azure`, whose `AddAzureClients` is the ordinary vendor registration a plugin is most likely to make; `Azure.Extensions.AspNetCore.Configuration.Secrets` is the configuration-provider package and registers nothing, so it is the wrong one to reach for. `src/Directory.Packages.props` pins no `Azure*` package today, so whichever is chosen is added there, since the repository manages package versions centrally (`src/Directory.Packages.props:3`). The pull request states plainly that this adds a new dependency tree to central package management and that it is **test-only**: the entry exists so the wrapper can be proven against a real vendor registration helper rather than an imitation, no production project references it, and its transitive closure reaches no shipped assembly. If a reviewer would rather not carry that closure at all, the alternative is to drop the real-SDK criterion and keep only the framework helpers, which is a weaker test and is named here so the trade is visible rather than discovered in review.
- **The replace count is over descriptors the per-hook diffs attribute to plugins, and a pre-existing host default is not one of them.** A replace contract exists to displace a host default, so the collection legitimately holds two descriptors for it when one plugin has claimed it. Two criteria pin the boundary against a fixture host default registered before the hooks run: one plugin claiming that contract with `Add` **passes**, with the plugin named as the single claimant in its inventory record; two plugins claiming it over the same host default is **fatal**, naming both plugins and the contract. Counting descriptors on the collection rather than counting attributed claims fails the first, which is the wrong answer this pair exists to catch.
- Two plugins each registering a fixture replace-cardinality contract with `Add` are both named in the fatal along with the contract.
- A plugin that claims a fixture replace-cardinality contract with `TryAdd` while another plugin already holds it **and contributes nothing else** is fatal as having registered no declared contract, naming that plugin. This is the design's answer to a decline the seam cannot observe, and the message says the plugin contributed nothing rather than pretending to know why. The criterion exists so the invisible decline is provably not silent, and its scope is written into it: the backstop is a conjunction, so it fires on the contribute-nothing case and not on a plugin that declined on a replace contract while also registering something declared.
- The residual is stated in the story rather than left for a reader to find. A second test, asserting a limit rather than a capability, has a fixture plugin `TryAdd` a fixture replace contract that a host default already holds **and** register a fixture fan-in contract, and asserts the boot succeeds with the host default still resolved and no finding anywhere naming the declined claim. It is a characterization test: it pins what the design does not detect, so nobody later reads the no-contract-registered criterion as covering every declined `TryAdd`. No new check is added, because cardinality is host metadata and the candidate a declining `TryAdd` carried is not observable at this seam.
- **One** plugin registering two descriptors for the same fixture replace-cardinality contract is fatal on its own, naming the plugin and the contract. Proven with one hook calling `Add` twice with different implementation types. Without this criterion the case passes and DI's last-wins silently picks one, which is the outcome the replace cardinality's "0 or 1" exists to refuse.
- A plugin registering `IDocumentStoreRepository`, host-owned and no declared contract, is fatal naming the plugin and the type; a plugin registering its own types, `Microsoft.Extensions.*` options, and an `IHostedService` beside a declared contract loads unaffected, and its inventory lists the hosted service. A separate case pins that the predicate keys on assembly identity rather than package identity: `ICustomResourceValidator` is declared in the assembly `EdFi.DataManagementService.CustomValidation`, so it matches the host-owned predicate and is admitted only because the declared-contract exemption is evaluated first; a test asserts that registering it succeeds and that removing it from the registry makes the same registration fatal.
- In the startup guard: a plugin whose hook registered only its own types is fatal as having contributed no declared contract, naming the plugin and listing what it did register. The message names the likeliest cause, a plugin allowlisted on the wrong host.
- Every registration of a declared plugin contract is resolved once from a throwaway scope; a registration that cannot be constructed is fatal, naming the plugin, the contract, and the activation exception. The probe is an activation check and not a disposal boundary, and the story says so rather than claiming the instances are discarded: scoped and transient instances go with the scope, while a singleton resolved inside it is cached in the root container and stays the instance production uses, which is measured rather than assumed. Proven with a fixture plugin registering a fan-in contract implementation whose constructor takes a service nobody registered. This is the plugin guard's own probe: DMS-1434's activation probe covers `ICustomResourceValidator` because that contract's story asked for it, and a contract added by a later companion document would otherwise arrive with no activation at all.
- The per-plugin inventory record carries every service type registered, every non-host removal, the host-first version substitutions from draft 02, and that draft's per-file digests and loaded flags read from the plugin's `.deps.json`, and a test asserts the record feeds the guard's checks and the logged event from one source rather than two.
- **The `PluginAuditInput` the invoker returns reaches the task as a singleton instance the frontend registers, and the seam is a criterion rather than an implementation choice.** The records are produced during Phase B, inside `AddServices`, while the task is resolved after `builder.Build()`, so nothing the task can resolve reaches a local variable in `AddServices`. A Core-free frontend extension called once and unconditionally from `WebApplicationBuilderExtensions.AddServices` registers both halves in one place: `services.AddSingleton(auditInput)` for the value the invoker just returned, and the task itself. This is the call-site shape DMS-1434's own Core-owned extension already uses, and `AddJwtAuthentication` before it.
- The task takes `PluginAuditInput` by constructor. It resolves no service collection, and a test asserts as much by asserting the frontend's diff registers no `IServiceCollection`. Registering an **instance** rather than a type means the container activates nothing, and because the host registers it after every hook has already run, a plugin that registered its own `PluginAuditInput` cannot displace it: the host's is the last registration for that service type and a single-service resolve takes the last. A test proves that with a fixture plugin whose hook registers a decoy `PluginAuditInput` and asserts the audit still reads the host's records.
- With no plugin allowlisted the invoker returns an empty `PluginAuditInput`, the singleton is still registered, and the task runs and reports nothing. A test asserts a plugin-free boot is unaffected, which is what lets this story's task assertion run before draft 04 wires the loader into `Program.cs`.
- **The interim hand-off shape is named here rather than left between this story and draft 04, on both halves.** This story invokes `ContributeServices` over draft 02's static `LoadedPlugins.Empty` from inside `AddServices` and does **not** change that method's signature; the audit value that invocation returns is what the frontend extension registers, so "the value the invoker just returned" needs no draft-04 wiring to be a real value. Draft 04 owns the signature change that replaces `Empty` with the aggregate `PluginLoader.Load` returned, and nothing else about this seam moves when it does.
- The four post-container checks live in a frontend-owned `IDmsStartupTask` whose `Order` is in 200-299 and above DMS-1434's guard, reading findings from a pure audit function in `EdFi.Api.Plugins.Hosting`. A test asserts the task actually executed during a real `WebApplicationFactory<Program>` boot, following DMS-1434's own precedent for that assertion, and the pull request diff is asserted to contain no change under `src/dms/core/`.
- The DMS-1434 guard's existing criteria continue to pass unchanged: transient-only audit, descriptor-shape audit, activation probe, `Order` in 200-299, and post-container placement.
- The DMS frontend project gains a `ProjectReference` to `src/plugins/EdFi.Api.Plugins.Hosting/`, its `packages.lock.json` is regenerated and committed, and `build-dms.ps1 DockerBuild` is run and asserted to succeed, which is what proves draft 01's build-stage change actually covers the reference this story adds. `--locked-mode` does not catch a missing project entry, so the image build is the assertion rather than the restore.
- `dotnet test src/plugins/EdFi.Api.Plugins.Hosting.Tests.Unit` and `dotnet test src/dms/frontend/EdFi.DataManagementService.Frontend.AspNetCore.Tests.Unit` pass.

2. Add `RecordingServiceCollection` as a pass-through with the pre-existing snapshot and the two wrapper-side fatals, and derive the per-plugin record from a snapshot-and-diff around each hook rather than from per-call recording.
3. Add the Phase B invoker on draft 02's `LoadedPlugins` with the pre-call announcement, the throw-to-fatal wrapping, and the `PluginAuditInput` return value.
4. Add the audit function in `EdFi.Api.Plugins.Hosting` (replace-conflict, displacement, no-contract, activation) over the per-plugin records and the registry, and the frontend-owned `IDmsStartupTask` that calls it and takes the existing fatal path. Add the frontend extension that registers the returned `PluginAuditInput` as a singleton instance and the task beside it, called once from `AddServices`. Add the frontend's `ProjectReference` into `EdFi.Api.Plugins.Hosting` and regenerate its lock file. Do not modify DMS-1434's guard or anything under `src/dms/core/`.
5. Build the fixture plugins this story needs as test assets under `src/plugins/EdFi.Api.Plugins.Hosting.Tests.Unit/Fixtures/`, beside draft 02's: replace-contract claimants (one plugin claiming over a fixture host default, two plugins claiming over the same host default, one plugin claiming twice, and one claiming with `TryAdd` behind another), a decoy `PluginAuditInput` registrant, host-type registrant, own-types-only registrant, a `ClearProviders` caller and an add-a-provider-only caller for the logging carve-out, a remover of a pre-existing non-logging framework descriptor for the exemption, a `RemoveAll<T>` caller for the pass-through regression, unsatisfiable-dependency registrant, and the real-helpers caller. Nothing in this arrangement gives `src/plugins/` a reference to the frontend.
6. Write the wrapper tests, the guard tests, and the single-source inventory test.
