# Story: Add the Recording Service Collection and Cardinality Guard

## Description

The loader returns plugin instances; something has to invoke `ContributeServices` on each, know what each one registered, and refuse the registrations the design refuses.
This story adds the recording `IServiceCollection` wrapper, the host-held cardinality registry, the Phase B invocation, and the five guard checks fed by the wrapper, per:

- `reference/design/plugins-DMS-1462/design.md` ("### Contract Cardinality", "### Startup Failure Semantics" for the wrapper and guard rows, "### Observability" for the inventory event)
- `reference/design/custom-validation-DMS-1345/03-add-custom-validator-composition-seam-and-startup-guard.md` (DMS-1434), the post-container startup guard this story extends

Four of the checks run at the wrapper, before a call reaches the real collection: removal or overwrite of a pre-existing host-owned descriptor, removal or overwrite of a pre-existing logging-pipeline descriptor, an unkeyed addition of a logging service the host reserves, and `Clear`.
Five run after the container is built: two claims on one replace-cardinality contract, a plugin registering a host-owned service type that is no declared contract, a declared contract registered under `KeyedService.AnyKey` by anyone, a plugin left with no surviving declared-contract registration, and an activation probe over the surviving declared-contract registrations. The first four are static checks; any finding stops the audit before activation.
**Two** of them key on one test, whether a `ServiceType` is declared in an assembly whose **assembly name** begins `EdFi.DataManagementService.` or `EdFi.DmsConfigurationService.`: host-owned removal and overwrite at the wrapper, and host-owned displacement in the guard.
The remaining checks do not use it. The replace-conflict check counts attributed claims against the host's own cardinality registry, the wildcard check reads the records and the composition snapshot against that registry, the no-contract check intersects each plugin's additions with the registry and then with the composition snapshot, the activation probe resolves declared contracts, the two logging rules key on named service types, and `Clear` is always refused.
design.md records that a third rule keyed on the host-owned test would be the signal the wrapper has become something it should not be.

**The post-container checks are a startup task of their own, in the frontend, not additions to Core's.**
DMS-1434's guard is an `IDmsStartupTask` in `EdFi.DataManagementService.Core`, which cannot see the per-plugin records this story produces in `EdFi.Api.Plugins.Hosting` without a project reference that would invert the dependency and drag the contract assembly into every Core consumer.
So `EdFi.Api.Plugins.Hosting` exposes a pure audit function over the records and the contract registry, returning findings, and the DMS frontend owns a thin `IDmsStartupTask` that calls it, ordering just above DMS-1434's guard inside the same executed 200-299 window.

**This story changes nothing under `src/dms/core/` except one file, and the exception is named rather than left as an absolute the diff contradicts.**
The permitted change is `src/dms/core/EdFi.DataManagementService.Core.Tests.Unit/packages.lock.json`, and only its regeneration.
That project carries a `ProjectReference` to the DMS frontend (`src/dms/core/EdFi.DataManagementService.Core.Tests.Unit/EdFi.DataManagementService.Core.Tests.Unit.csproj:62`), so the frontend's new reference into `src/plugins/` changes the dependency closure it restores, and a lock file that did not record it would fail `dotnet restore --locked-mode` in CI.
No Core production file, no other generated Core file, and no DMS-1434 implementation or test changes: the exemption is this one path and not a general exemption for generated files under Core.

**This is therefore the story that adds the frontend's `ProjectReference` into `src/plugins/`, and it is the first one that needs it.**
`src/dms/frontend/EdFi.DataManagementService.Frontend.AspNetCore/EdFi.DataManagementService.Frontend.AspNetCore.csproj` references Core, Core.External, and the two backends today, and nothing more; the reference to `EdFi.Api.Plugins.Hosting` is new work.
`src/dms/Dockerfile`'s build stage already carries `src/plugins/` by then, because draft 01 put it there for exactly this reason: `.github/workflows/on-dms-pullrequest.yml` builds that Dockerfile in nine places on a relevant pull request, one shared CI image build and eight matrix legs, and a frontend reference into a tree the build stage cannot reach fails `dotnet restore --locked-mode` in all of them.

**The wrapper cannot see a declined `TryAdd`, and the answer is a registration rule rather than a projection.**
`TryAdd` reads `Count` and the indexer, compares, and returns without handing the candidate descriptor to the collection, so a decline arrives at the wrapper as an anonymous scan with no service type and no implementation type attached.
An earlier revision of the design answered that by masking replace-cardinality descriptors from each plugin's view, and that is withdrawn as unsound: `RemoveAll<T>` and `Replace` walk the collection by index, reading through the masked view and calling `RemoveAt(i)` against the real one, so over `[IReplaceContract, IB, IC]` with the first masked, `RemoveAll<IC>()` removes the two it was not asked to remove and keeps the one it was.
So the wrapper hides nothing.
A plugin claiming a replace-cardinality contract registers it with a plain `Add`, the implementer guide says so, and a plugin that used `TryAdd` and silently declined adds nothing and therefore fails the no-contract-registered check below, which names it.
That backstop reaches the decline only when the decline was the plugin's one contribution, and this story states the residual rather than implying full coverage: a plugin that also registers another declared contract or contributes a Phase A source passes every check, and the intended replacement silently never happens.

**Attribution is a snapshot-and-diff around each hook, not per-call bookkeeping.**
The invoker snapshots the real collection before each plugin's hook and compares it after: present-after-and-not-before by reference is that plugin's additions, present-before-and-not-after is its removals, and a service type in both lists is a replacement.
Hooks run one at a time in allowlist order, so each diff belongs to exactly one plugin.
The wrapper still exists, because the removal rules have to fire before a call reaches the real collection, but that is now its only job.

This story depends on draft 02 for the instances and on DMS-1434 for the guard it runs beside.

## Acceptance Criteria

- A declared contract registered under `KeyedService.AnyKey` is fatal, naming the contract, before any activation occurs. On .NET 10, `GetKeyedServices(T, KeyedService.AnyKey)` enumerates concrete-key registrations rather than the wildcard registration, and enumerating a concrete key does not reach the wildcard fallback either. A single-service lookup could reach the fallback with a concrete key, but the host has no supplied key for it. Tests cover a wildcard declared contract alone and beside a concrete-key registration, assert that the refusal prevents activation, and prove a wildcard registration of a service that is not a declared contract is permitted. Unkeyed and concrete-key declared-contract registrations remain supported by this audit, subject to the contract's own rules.
- **The refusal has no host exemption**, because the requirement is a property of the registration rather than of who made it: a wildcard registration of a declared contract the host made is exactly as unactivatable as a plugin's, and exempting it would leave the audit asserting an activation it never performed. The check reads both the per-plugin records and the composition snapshot; a registration present in both is reported once, a registration the records attribute names its contributing plugin, and a registration they do not attribute names no plugin at all rather than inventing one. It runs with the other static checks, before activation. Proven by a case whose wildcard declared-contract registration is made by the fixture host, asserting the fatal, an empty plugin-name list, and that nothing at all was constructed; the plugin-attributed cases already assert a single finding, which is what pins the de-duplication against the snapshot.
- **What is refused is a registration that survived composition.** The rule's rationale is that the required startup activation cannot reach a wildcard registration, and nothing is activated for a descriptor that is no longer on the collection, so a record-sourced candidate is intersected against the composition snapshot by reference identity before attribution and de-duplication. Proven by a regression case in which one plugin registers the removable declared contract under the wildcard key beside a surviving unkeyed contribution and a later plugin removes the wildcard registration: the descriptor is absent from the snapshot, the addition and the removal are both still recorded, the audit finds nothing, and the surviving implementations are activated. Attribution, de-duplication, and the refusal of a surviving host or unattributed wildcard registration are unchanged by it.
- A plain-container characterization test, with no plugin, record, or audit in it, pins the .NET behaviour the refusal rests on: over a collection holding a wildcard registration, a concrete-key registration, and an unkeyed one, `GetKeyedServices(AnyKey)` returns the concrete-key registration and not the wildcard, `GetKeyedServices` under a concrete key and under an unregistered key reach the wildcard registration in neither case, and the unkeyed enumeration does not reach it either. It also asserts the positive: `GetKeyedService` under an arbitrary concrete key **does** return the wildcard registration, so the fixture proves the registration is usable through that distinct single-service path and the refusal is about this audit's probe rather than about the registration being inert. If a future runtime makes an enumerable resolve reach a wildcard registration, this is the case that fails and says the refusal can be revisited.
- `RecordingServiceCollection` implements `IServiceCollection` and is a **pass-through**: every read member returns exactly what the real collection holds, in the same order, and every write member applies the removal rule and the logging reservation below and then delegates. It hides, reorders, and projects nothing. Proven by asserting that a plugin enumerating the collection during its hook sees the same sequence as the real collection, that `Count`, the indexer, `IndexOf`, and `Contains` agree with it, and that a replace-contract descriptor the host registered before the hook is visible to the plugin like any other.
- `RemoveAll<T>()` called from inside a hook removes the descriptors for `T` and nothing else. This is a regression test with a named cause: an earlier design masked replace-cardinality descriptors from the plugin's view, and because `RemoveAll<T>` and `Replace` read indices through the view and write them to the real collection, `RemoveAll<IC>()` over `[IReplaceContract, IB, IC]` with the first masked removed `IReplaceContract` and `IB` and kept `IC`. Any reintroduction of a projection fails this criterion.
- The wrapper records **no** declined `TryAdd` calls, and a test documents why by driving `TryAddSingleton<IFoo, Foo2>` against a wrapper over a collection that already holds `IFoo` and asserting the wrapper observed only `Count` and indexer reads and never saw `Foo2`. That test exists so nobody later adds an acceptance criterion the seam cannot satisfy.
- Attribution comes from a snapshot of the real collection taken before each plugin's hook and diffed after it, by reference: additions, removals, and replacements are derived per plugin from that diff, and a test with two plugins registering into one collection asserts each plugin's record names only its own descriptors.
- A `PluginContractRegistry` type in `EdFi.Api.Plugins.Hosting` holds a set of `(Type contract, Cardinality cardinality)` entries the host constructs and passes to the invoker; DMS's registry names `ICustomResourceValidator` as fan-in. The type is this story's; the frontend-owned static that holds DMS's one instance of it, `DmsPluginContracts.Registry`, is draft 04's, because a DMS-specific value belongs on the DMS side of the seam. Neither name is a rename of the other, and this story's tests construct fixture registries directly rather than through `DmsPluginContracts`. The registry is never read from configuration or from a plugin. Because it is host-supplied, a fixture registry declaring a fixture replace contract is what the conflict tests below use, so none of them depends on a real replace contract existing yet.
- The registry also exposes `ContractAssemblyNames`, and it **derives** them rather than holding a second hand-written list: `typeof(EdFiApiPlugin).Assembly.GetName().Name`, which is always in the set, plus `entry.Contract.Assembly.GetName().Name` for every entry, de-duplicated ordinally. This is the value draft 04 passes to `PluginLoader.Load` for the skew preflight. Three tests pin it. DMS's own registry yields exactly `EdFi.Api.Plugins` and `EdFi.DataManagementService.CustomValidation` - the **assembly** name of the contract that packs under the id `EdFi.Api.CustomValidation`, and a test asserts the package id is not what comes out, since a reference in assembly metadata carries an assembly name and the preflight would silently match nothing. A registry with no entries still yields `EdFi.Api.Plugins`, so the base contract cannot drop out of the skew check. And adding a fixture contract entry adds its declaring assembly with no other change, which is the property that keeps a per-type contract added by a later companion document covered without touching the loader.
- `LoadedPlugins.ContributeServices(IServiceCollection, IConfiguration, PluginContractRegistry)` invokes each plugin's hook in allowlist order through its own recording wrapper, writes `invoking ContributeServices on <plugin>` to `Console.Error` **before** each call, turns a thrown exception into a fatal naming the plugin and the composition phase, and **returns** a `PluginAuditInput` carrying the per-plugin records and the registry the audit needs. `LoadedPlugins` is draft 02's aggregate over `IReadOnlyList<LoadedPlugin>`; this story adds the method to it rather than introducing a new type. A test has the fixture hook throw and asserts the announcement is already on the channel. The invoker throws rather than choosing a bootstrap phase: it is called from inside `AddServices`, so in DMS the failure lands in whichever bootstrap phase the host was running, which draft 04 states is `ConfigureServices`, and in CMS it lands in a plain `Program.cs` with no phase at all.
- Removing, replacing, or assigning through the indexer over a descriptor that was present before the plugin's hook began **and** whose `ServiceType` is host-owned is fatal at the wrapper, naming the plugin and the service type, and the real collection is asserted unchanged. Proven with `services.Replace(...)` on `IDocumentStoreRepository`, `RemoveAll<T>()` over a host type, and an indexer assignment over a pre-existing host-owned slot. `Clear` is always fatal.
- Removing a pre-existing **non-host** descriptor is permitted and recorded, outside the logging carve-out below. Proven with a fixture whose hook removes a pre-existing framework descriptor that is not in the logging pipeline set: the plugin loads, and its inventory lists the removal with the displaced implementation type.
- **A plugin that removes, replaces, or overwrites a pre-existing logging-pipeline descriptor is fatal at the wrapper**, naming the plugin and the service type, with the real collection asserted unchanged. The set is four service type names, all declared in `Microsoft.Extensions.Logging.Abstractions`: `Microsoft.Extensions.Logging.ILoggerProvider`, `Microsoft.Extensions.Logging.ILoggerFactory`, `Microsoft.Extensions.Logging.ILogger`, and the open generic `Microsoft.Extensions.Logging.ILogger<>`. It is written as service type names rather than as an assembly or namespace rule, because it must cover the types whose descriptors carry the process's logging and nothing else in `Microsoft.Extensions.*`. The set is deliberately inclusive rather than minimal: measured on `net10.0`, neither `AddLogging` nor `ILoggingBuilder.AddSerilog` registers a descriptor for the non-generic `ILogger`, so no removal can match it in DMS as shipped, and it is in the set anyway because the rule is about what a plugin may remove rather than about what the host happens to register. The story states that, so nobody later "tidies" the fourth name out on the grounds that nothing registers it, and no criterion asserts a fatal on non-generic `ILogger` against a DMS-populated collection, because none can fire there.
- The exercising call is `logging.ClearProviders()`, and the fixture calls it. Measured on `net10.0`, `LoggingBuilderExtensions.ClearProviders` is exactly `Services.RemoveAll<ILoggerProvider>()`: against a collection built by `AddLogging(b => b.AddConsole())` it removed the one `ILoggerProvider` descriptor and left `ILoggerFactory` and `ILogger<>` in place. DMS wires Serilog inside `AddServices` at `Infrastructure/WebApplicationBuilderExtensions.cs:125`, and Phase B runs after `AddServices`' own registrations, so the providers a plugin clears are the host's. An earlier revision made this the criterion that proved the removal exemption; it is now the criterion that proves the carve-out, and the change of direction is deliberate rather than a wording drift.
- The fatal is asserted to be **reportable**: the test asserts the message reached `Console.Error` and that the collection still holds the host's `ILoggerProvider` descriptors when it did, which is the property that comes from refusing the call before it lands rather than auditing after it.
- A plugin that only **adds** an `ILoggerProvider` loads unaffected, which keeps the carve-out from being a ban on a plugin shipping its own sink.
- **Protecting removal alone leaves the pipeline open, so a plugin's unkeyed registration of `ILoggerFactory`, the non-generic `ILogger`, or `ILogger<>` open or closed is also fatal at the wrapper**, naming the plugin and the service type, with the real collection asserted unchanged. These three are resolved singly rather than enumerated, and a single-service resolve takes the last registration, so a plain `Add` displaces the host's logging with no removal and no call the removal rule can see. `ILoggerProvider` is deliberately not in this set, because providers are enumerated and a plugin's sink composes with the host's.
- **The rule is enforced on the incoming descriptor, on `Add`, `Insert`, and indexer assignment, before the write lands**, and the existing removal protection still applies to whatever an indexer assignment overwrites. Criteria cover each of the three write paths, a closed `ILogger<T>` as well as the open generic and the non-generic `ILogger`, a hook that catches the refusal and carries on, which still fails the composition through the same latch the other refusals use, and the collection asserted unchanged with the refusal on `Console.Error`.
- **It is written as an explicit reservation of the host's unkeyed logging services and not as duplicate detection**, and a criterion pins the difference: the same registration is refused against a collection holding no logging descriptor of that type at all. The rule reads nothing from the collection, because what it protects is the resolve a host component makes later; a rule conditioned on an existing descriptor would pass for a plugin that got there first.
- Adding a **keyed** logging registration stays permitted, because an unkeyed resolve reaches no keyed descriptor, so it replaces nothing the host resolves. A criterion pins it beside the provider one.
- **This cannot be implemented in the post-container audit alone**, and the story says why rather than leaving it as a placement preference: the audit needs a logger before it can report anything, and the registration under test is exactly what decides which logger it gets. The story also corrects the helper explanation the earlier revision ran together: `ILoggingBuilder.AddSerilog` adds a provider and is permitted, and is the overload DMS itself calls at `Infrastructure/WebApplicationBuilderExtensions.cs:120`, while the `IServiceCollection.AddSerilog` overload, which `Serilog.Extensions.Hosting` supplies and a plugin may bring even though this repository carries only `Serilog.Extensions.Logging`, can register an `ILoggerFactory` and is consequently forbidden inside a plugin hook by this policy. The real `AddLogging` helper stays permitted because every call it makes against the collection is in the `TryAdd` family and declines against a host that has already wired logging, which is asserted rather than assumed; against a collection with no logging at all it would be refused, and that criterion states so.
- A plugin that registers a descriptor and then replaces it is unaffected, which pins the pre-existing scope.
- A fixture plugin calling the real `AddHttpClient()`, `AddOptions<T>().Bind(...)`, `AddLogging()`, and one real cloud SDK client registration, against a collection DMS's own `AddServices` has already populated, loads with nothing rejected. This is a test against the libraries as shipped, not against a fixture that imitates them. What it proves is that the wrapper does not reject ordinary registration work; it does **not** prove the pre-existing scope, because none of those four removes anything. A metadata sweep of `Microsoft.Extensions.Http`, `Microsoft.Extensions.Options`, `Microsoft.Extensions.Options.ConfigurationExtensions`, and `Microsoft.Extensions.Azure` 1.11.0 found their only `ServiceCollectionDescriptorExtensions` references to be `TryAdd`, `TryAddSingleton`, `TryAddTransient`, and `TryAddEnumerable`, so an earlier claim that `AddHttpClient`, options builders, and `AddAzureClients` call `Replace` and `RemoveAll` internally is false and this criterion no longer rests on it. The pre-existing scope is proven by the own-descriptor `Replace` criterion above; the `ClearProviders` criterion proves the logging carve-out, not the scope. The cloud SDK is `Microsoft.Extensions.Azure`, whose `AddAzureClients` is the ordinary vendor registration a plugin is most likely to make; `Azure.Extensions.AspNetCore.Configuration.Secrets` is the configuration-provider package and registers nothing, so it is the wrong one to reach for. The version is pinned in the fixture tree's own `src/plugins/EdFi.Api.Plugins.Hosting.Tests.Unit/Fixtures/Directory.Packages.props` rather than in `src/Directory.Packages.props`, and the placement is a criterion rather than an implementation detail. That file already imports its parent, so a fixture keeps every version the repository manages centrally and this adds one the repository has no opinion about; the sibling entry there records the measurement that makes the scoping worth having, since adding `Microsoft.Extensions.Options.ConfigurationExtensions` centrally rewrote thirty-two committed production lock files. The entry is **test-only**: it exists so the wrapper can be proven against a real vendor registration helper rather than an imitation, only the real-helpers fixture references it, no production project does, and its transitive closure reaches no shipped assembly. The pull request states that plainly. If a reviewer would rather not carry that closure at all, the alternative is to drop the real-SDK criterion and keep only the framework helpers, which is a weaker test and is named here so the trade is visible rather than discovered in review.
- **The replace count is over descriptors the per-hook diffs attribute to plugins, and a pre-existing host default is not one of them.** A replace contract exists to displace a host default, so the collection legitimately holds two descriptors for it when one plugin has claimed it. Two criteria pin the boundary against a fixture host default registered before the hooks run: one plugin claiming that contract with `Add` **passes**, with the plugin named as the single claimant in its inventory record; two plugins claiming it over the same host default is **fatal**, naming both plugins and the contract. Counting descriptors on the collection rather than counting attributed claims fails the first, which is the wrong answer this pair exists to catch.
- Two plugins each registering a fixture replace-cardinality contract with `Add` are both named in the fatal along with the contract.
- A plugin that claims a fixture replace-cardinality contract with `TryAdd` while another plugin already holds it **and contributes nothing else** is fatal as having registered no declared contract, naming that plugin. This is the design's answer to a decline the seam cannot observe, and the message says the plugin contributed nothing rather than pretending to know why. The criterion exists so the invisible decline is provably not silent, and its scope is written into it: the backstop is a conjunction, so it fires on the contribute-nothing case and not on a plugin that declined on a replace contract while also registering something declared.
- The residual is stated in the story rather than left for a reader to find. A second test, asserting a limit rather than a capability, has a fixture plugin `TryAdd` a fixture replace contract that a host default already holds **and** register a fixture fan-in contract, and asserts the boot succeeds with the host default still resolved and no finding anywhere naming the declined claim. It is a characterization test: it pins what the design does not detect, so nobody later reads the no-contract-registered criterion as covering every declined `TryAdd`. No new check is added, because cardinality is host metadata and the candidate a declining `TryAdd` carried is not observable at this seam.
- **One** plugin registering two descriptors for the same fixture replace-cardinality contract is fatal on its own, naming the plugin and the contract. Proven with one hook calling `Add` twice with different implementation types. Without this criterion the case passes and DI's last-wins silently picks one, which is the outcome the replace cardinality's "0 or 1" exists to refuse. Its message names the plugin and how many registrations it made and tells the plugin's author to register the contract once, rather than offering the `Plugins:Allowed` remedy the two-plugin fatal offers: the allowlist holds one entry for this plugin, so no allowlist change can choose between two registrations made inside it. Two criteria pin the split, one asserting the author-facing remedy here and one asserting the operator-facing remedy on the two-plugin case.
- A plugin registering `IDocumentStoreRepository`, host-owned and no declared contract, is fatal naming the plugin and the type; a plugin registering its own types, `Microsoft.Extensions.*` options, and an `IHostedService` beside a declared contract loads unaffected, and its inventory lists the hosted service. A separate case pins that the predicate keys on assembly identity rather than package identity: `ICustomResourceValidator` is declared in the assembly `EdFi.DataManagementService.CustomValidation`, so it matches the host-owned predicate and is admitted only because the declared-contract exemption is evaluated first; a test asserts that registering it succeeds and that removing it from the registry makes the same registration fatal.
- In the startup guard: a plugin whose hook registered only its own types is fatal as having contributed no declared contract, naming the plugin and listing what it did register. The message names the likeliest cause, a plugin allowlisted on the wrong host.
- **The rule measures survival rather than registration.** Each plugin's declared-contract additions are compared against the composition snapshot by reference identity, and a plugin with none left there fails this check. Removing a pre-existing descriptor that is neither host-owned nor part of the logging pipeline stays permitted, so a later plugin may legitimately take away an earlier one's declared-contract registration; the removal is nobody's fatal and the composition it produces is what fails, against the plugin left with nothing live rather than against the plugin that removed it. The diagnostics distinguish the two shapes: "registered no plugin contract this host declares" and "none of them survived service composition", each with the remedy its own first question implies.
- **A two-plugin regression proves it, over a fixture contract declared in an assembly no Ed-Fi host prefix matches.** The contract has to be a non-host one, because the wrapper refuses a plugin removing a host-owned descriptor, so with the fixture host's own contracts the case cannot be composed at all. The later plugin removes the earlier plugin's only declared contribution while contributing a declared contract of its own: the earlier plugin is named in the fatal with the survival message, the later plugin is not named, the earlier plugin's addition and the later plugin's removal are both still in the records, and the snapshot holds no descriptor for the contract. A companion case has the earlier plugin also contribute a second declared contract the later one does not touch, and the composition audits clean, which is what stops the rule being read as "any removal of a declared contract is fatal".
- **The replace-cardinality count keeps its historical accounting and is not quietly aligned with the rule above.** It counts every descriptor the per-hook diffs attributed, surviving or not, because two claims on one replace contract are an operator decision that a later removal does not resolve; counting survivors would let the pair pass whenever the second plugin tidied up after the first. Both accountings are stated where they are implemented so neither is read as an oversight in the other.
- **Declared-contract registration must be finished by the composition snapshot, and that is the audit's supported composition contract rather than a claim about detection.** Later host registrations of unrelated infrastructure remain supported and are unexamined; a declared-contract registration, removal, or new key added after the snapshot is outside what this audit undertakes to cover. Nothing in the story or the code describes a historical removed descriptor as activatable, the snapshot as the container's final descriptor set, or the probe as detecting every possible later registration.
- When the static checks pass, the audit resolves the **surviving supported** declared-contract registrations once from a throwaway scope, through the unkeyed group and each discovered concrete-key group; a registration that cannot be constructed is fatal, naming the plugin, the contract, and the activation exception. Concrete keys are discovered from the composition snapshot and from the per-plugin records, so a keyed registration the host made forms a group of its own, and a key discovered only from a record is one whose descriptors are all gone: its group resolves to nothing and activates nothing. The probe is an activation check and not a disposal boundary, and the story says so rather than claiming the instances are discarded: scoped and transient instances go with the scope, while a singleton resolved inside it is cached in the root container and stays the instance production uses, which is measured rather than assumed. Proven with a fixture plugin registering a fan-in contract implementation whose constructor takes a service nobody registered. This is the plugin guard's own probe: DMS-1434's activation probe covers `ICustomResourceValidator` because that contract's story asked for it, and a contract added by a later companion document would otherwise arrive with no activation at all.
- The per-plugin inventory record carries every service type registered, every non-host removal, the host-first version substitutions from draft 02, and that draft's per-file digests and loaded flags read from the plugin's `.deps.json`, and a test asserts the record feeds the guard's checks and the logged event from one source rather than two.
- **The record's members are host implementation data and the type says so.** It is public because the audit function and the frontend's startup task live in different assemblies and both read it, and it carries what those two and the inventory event need rather than a curated surface for a plugin author. A member with no check keying on it, `ReplacedServiceTypes` being the one, is kept because the inventory event distinguishes a replacement from a bare removal and deriving that again at the log site would be the second source this record exists to avoid; its own documentation says it is reported rather than checked. None of it is a compatibility commitment to a third party, and it is not trimmed to what today's checks read.
- **The two fixture staging targets stay separate, and the difference between what each stages is not described as a defect.** The plugin hosting tests stage the full fixture list; the frontend test project stages the two fixtures whose criteria are about DMS's own types, because publishing thirty-odd directories into a second project's output would double a long build for assets no test there reads. Their freshness rules reach the same conclusion by the same reasoning and are written out in each file. No shared staging abstraction is introduced here: the case for one would be a demonstrated need, and two call sites with different fixture lists is not that.
- **The `PluginAuditInput` the invoker returns reaches the task as a singleton instance the frontend registers, and the seam is a criterion rather than an implementation choice.** The records are produced during Phase B, inside `AddServices`, while the task is resolved after `builder.Build()`, so nothing the task can resolve reaches a local variable in `AddServices`. A Core-free frontend extension called once and unconditionally from `WebApplicationBuilderExtensions.AddServices` registers both halves in one place: `services.AddSingleton(auditInput)` for the value the invoker just returned, and the task itself. This is the call-site shape DMS-1434's own Core-owned extension already uses, and `AddJwtAuthentication` before it.
- The task takes `PluginAuditInput` by constructor. It resolves no service collection, and a test asserts as much by asserting the frontend's diff registers no `IServiceCollection`. Registering an **instance** rather than a type means the container activates nothing, and because the host registers it after every hook has already run, a plugin that registered its own `PluginAuditInput` cannot displace it: the host's is the last registration for that service type and a single-service resolve takes the last. A test proves that with a fixture plugin whose hook registers a decoy `PluginAuditInput` and asserts the audit still reads the host's records.
- With no plugin allowlisted the invoker returns an empty `PluginAuditInput`, the singleton is still registered, and the task runs and reports nothing. A test asserts a plugin-free boot is unaffected, which is what lets this story's task assertion run before draft 04 wires the loader into `Program.cs`.
