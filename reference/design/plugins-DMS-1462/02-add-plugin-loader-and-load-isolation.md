# Story: Add the Plugin Loader, Discovery, and Load Isolation

## Description

With the contract in place, nothing yet reads `Plugins:Allowed`, finds a plugin directory, or loads an assembly out of it.
This story adds the loader in `EdFi.Api.Plugins.Hosting`: allowlist binding, allowlist-driven discovery, one non-collectible `AssemblyLoadContext` per plugin with host-first resolution, the contract-skew and refused-version fatals, and `Console.Error` diagnostics, per:

- `reference/design/plugins-DMS-1462/design.md` ("### The Unit of Delivery", "### Discovery", "### Load Isolation", "### Configuration Surface", "### Startup Failure Semantics" for the loader-side rows, "### Observability" for the pre-logger channel)

The loader is host-agnostic.
It takes an `IConfiguration`, returns the loaded plugin instances in allowlist order, writes its own outcomes to `Console.Error`, and throws a `PluginLoadException` on any fatal.
It knows nothing about `RunBootstrapPhase`, Serilog, or either host's `Program.cs`; draft 04 wires it in.

Host-first resolution is the only subtle code in the spine, and its two decisions, serve from the host whatever the host carries and treat a host copy older than the plugin declared as fatal rather than falling back, are pinned by probe tests rather than assumed.
The design records the measurement this rests on: `AssemblyLoadContext.Default.LoadFromAssemblyName` throws `FileNotFoundException` both when the host lacks an assembly and when it carries an older version, so the loader must ask by simple name and compare versions itself rather than distinguishing the two by exception type.
This story does not invoke `ContributeServices` through a recording wrapper; it returns the instances and draft 03 owns the invocation.

## Acceptance Criteria

- A `PluginsOptions` type binds the `Plugins` section with `Directory` (default `/app/plugins`, resolved against `AppContext.BaseDirectory` when relative) and `Allowed` as a `string` defaulting to the empty string. `Allowed` is split on commas once at bind time, each name trimmed, empty elements dropped, and the resulting order asserted to be the order written. A name repeated before or after trimming is fatal, naming the duplicate. `Plugins__Allowed` set as an environment variable binds to the same ordered list as the JSON form.
- Each surviving name must be a single path segment matching `^[A-Za-z0-9][A-Za-z0-9._-]*$`; anything else is fatal, naming the entry and the rule, **before** the name is used to compose a path. Proven with `/etc/passwd`, `C:\\Windows`, `..`, `../sibling`, `sub/dir`, `sub\\dir`, and a leading-dot name, each asserted fatal and each asserted not to have opened any file. This is not stylistic: `Path.Combine(root, "/etc/passwd")` returns `/etc/passwd`, discarding the root entirely.
- Independently of the name rule, the composed `<Directory>/<Name>` is canonicalized with `Path.GetFullPath` and asserted to start with the canonicalized root plus a directory separator; a path that does not is fatal, naming the entry and both paths. Proven by pointing `Plugins:Directory` at a path containing a symbolic link that escapes the root, so the check is exercised against something the name rule cannot see.
- For each name in order, the loader resolves `<Directory>/<Name>/<Name>.dll` and `<Directory>/<Name>/<Name>.deps.json`. A missing root with a non-empty allowlist, a missing directory, a missing entry assembly, and a missing `.deps.json` are each fatal, naming the expected path. A missing root with an empty or absent allowlist returns an empty result and writes nothing.
- Before loading any type, the loader reads the entry assembly's references through `System.Reflection.Metadata` and, for every reference whose simple name matches a contract assembly the host declares, compares the referenced version to the version the host carries. A reference higher than the host's is fatal, naming the plugin, the contract, the version required, and the version the host carries, and a test asserts the failure came from the metadata read rather than from a type load by using a fixture whose type load would produce a different, recognizable error. The declared contract assemblies come from the caller, not from a constant in the loader, so `EdFi.Api.CustomValidation` and every later per-type contract are covered without a code change here; a test passes a two-entry set and asserts a fixture skewed on the second entry is fatal and names it.
- A `.deps.json` carrying a `libraries` entry whose `type` is `runtimepack` is fatal, naming the plugin, because that is what a self-contained publish produces. The check does **not** key on a runtime identifier in `runtimeTarget`: a fixture published with `dotnet publish -r <rid> --no-self-contained` carries `".NETCoreApp,Version=v10.0/<rid>"` there and no `runtimepack` library, and a test asserts that fixture loads, since a RID-specific framework-dependent publish is how a plugin ships native assets.
- Each plugin loads into its own `AssemblyLoadContext` named for the plugin, non-collectible, backed by an `AssemblyDependencyResolver` over the plugin's `.deps.json`. `Load` calls `Default.LoadFromAssemblyName(new AssemblyName(assemblyName.Name))`, with the simple name only and no version: a `FileNotFoundException` from that call means the host carries nothing by that name and falls through to the resolver, and any other result is the host's copy. If the host's copy has a lower `AssemblyVersion` than `assemblyName.Version`, the loader throws, naming the plugin, the assembly, the version requested, and the version the host carries; otherwise the host's copy is returned. A test asserts the simple-name form is what is passed, by loading a fixture that declares a higher version of an assembly the host carries and asserting the host's copy was reached rather than a `FileNotFoundException` swallowed.
- The runtime wraps an exception thrown from inside `Load` in a `FileLoadException` whose `InnerException` is the thrown exception; the loader unwraps that chain before reporting, and a test asserts the reported message is "plugin '<name>' requires <assembly> >= <requested>, host carries <actual>" rather than the wrapper's "An operation is not legal in the current state."
- Before constructing the plugin, the loader runs a preflight over the plugin's `.deps.json`: for every `runtime` entry carrying an `assemblyVersion`, it asks the host for that simple name and applies the same comparison, so a skewed dependency no hook happens to touch is still fatal at load rather than on a request. A test asserts a fixture whose skewed dependency is never referenced from any executed code path is still fatal, which is the case the `Load` override alone would miss.
- `LoadUnmanagedDll` is overridden and returns `_resolver.ResolveUnmanagedDllToPath(unmanagedDllName)`, falling back to the base implementation when the resolver has no answer. A fixture plugin carrying a native asset under `runtimes/<rid>/native/` resolves it and calls into it. The story asserts no check that a declared native asset exists for the running RID: native resolution is lazy, so a missing one surfaces as `DllNotFoundException` at first use, and the design records that as a known gap.
- The loader reflects over the entry assembly's exported types for public non-abstract `EdFiApiPlugin` subclasses with a public parameterless constructor. Zero and more than one are each fatal, naming what was found. The one match is constructed and its `Name` compared to the directory name; a mismatch is fatal naming both.
- The loader writes to `Console.Error` one line per allowlisted name in order, whether it succeeded or failed, and on failure the fatal reason. It also records, for every assembly it served host-first whose version differs from the version the plugin's `.deps.json` declared, the name and both versions, on a `LoadedPlugin` record the caller can log once a logger exists. `LoadedPlugin` also carries, for every assembly loaded into that plugin's context from the plugin directory, the file name, `AssemblyVersion`, and SHA-256 as read from disk, collected by enumerating the context's `Assemblies` after loading and keeping those whose location sits under the plugin directory. A test asserts a plugin carrying a private third-party dependency lists both that dependency and the entry assembly, since hashing only the entry assembly would leave the third-party code an incident responder cares about unrecorded.
- Fixture plugin directories are built as test assets under `src/plugins/EdFi.Api.Plugins.Hosting.Tests.Unit/Fixtures/`: a well-formed plugin; one with no subclass; one with two; one whose `Name` disagrees with its directory; one whose entry assembly is corrupt; one published self-contained; one published `-r <rid> --no-self-contained`, which must load; one with no `.deps.json`; one carrying a private copy of `EdFi.Api.Plugins`, which asserts the host's copy is served; two plugins carrying different major versions of one third-party dependency the host does not carry, which asserts each gets its own; one built against a contract version higher than the host's; one declaring a higher version of an assembly the host carries; one whose skewed dependency is never referenced from executed code, for the preflight; and one carrying a native asset. Each fatal row is asserted to throw rather than log, and the well-formed cases are asserted to return one instance each in allowlist order.
- The `IChangeToken` regression test from design.md "### Load Isolation": a fixture plugin that binds options through `IOptions<T>` from a configuration section is loaded, `ContributeServices` is invoked against a real `ServiceCollection`, the provider is built, and the options resolve. A second copy of the loader with an enumerated shared set substituted for host-first is asserted to fail this case with `TypeLoadException`, so the test pins the decision rather than restating it.
- A probe test records what `Default.LoadFromAssemblyName` does when asked for a higher version of an assembly the host carries and when asked for an assembly the host does not carry, and asserts the two are indistinguishable by exception type. If a future runtime makes them distinguishable, this test fails and the loader's simple-name approach is revisited deliberately rather than silently.
- A test asserts a plugin compiled against contract `1.0.0` loads and runs against a contract assembly at `1.1.0` carrying an added no-op virtual, built as a test asset.
- `dotnet test src/plugins/EdFi.Api.Plugins.Hosting.Tests.Unit` passes, and the project is added to all three solutions.

## Tasks

1. Add `PluginsOptions` and its binder with the trim-split-reject-duplicates rule.
2. Add `PluginLoadContext` exactly as design.md "### Load Isolation" shows it: simple-name host resolution, the explicit version comparison, and the `LoadUnmanagedDll` override.
3. Add `PluginLoader.Load(IConfiguration, IReadOnlyCollection<string> contractAssemblyNames)` returning `IReadOnlyList<LoadedPlugin>`, with the allowlist name-shape and containment checks, the metadata-read contract-skew check and the `.deps.json` dependency-skew preflight ahead of any type load, the `runtimepack` check, discovery, `Name` verification, the `FileLoadException` unwrapping, and `Console.Error` reporting.
4. Add `PluginLoadException` carrying plugin name and the structured reason.
5. Build the fixture plugin directories as test assets through a small MSBuild target or script that publishes each fixture project `--no-self-contained` into the test output, including the two version-skewed fixtures built against versions the host does not carry.
6. Write the fatal-row tests, the name-shape and containment tests, the isolation tests, the `IChangeToken` regression test with its enumerated-set control, the binder probe test, the unwrapping test, the native-asset test, and the older-plugin-on-newer-host test.
