# Story: Add the Plugin Loader, Discovery, and Load Isolation

## Description

With the contract in place, nothing yet reads `Plugins:Allowed`, finds a plugin directory, or loads an assembly out of it.
This story adds the loader in `EdFi.Api.Plugins.Hosting`: allowlist binding, allowlist-driven discovery, one non-collectible `AssemblyLoadContext` per plugin with host-first resolution, the contract-skew and refused-version fatals, and `Console.Error` diagnostics, per:

- `reference/design/plugins-DMS-1462/design.md` ("### The Unit of Delivery", "### Discovery", "### Load Isolation", "### Configuration Surface", "### Startup Failure Semantics" for the loader-side rows, "### Observability" for the pre-logger channel)

The loader is host-agnostic.
It takes an `IConfiguration`, returns the loaded plugin instances in allowlist order, writes its own outcomes to `Console.Error`, and throws a `PluginLoadException` on any fatal.
It knows nothing about `RunBootstrapPhase`, Serilog, or either host's `Program.cs`; draft 04 wires it in.

Host-first resolution is the only subtle code in the spine, and its two decisions, serve from the host whatever the host carries and treat a host copy older than the plugin declared as fatal rather than falling back, are pinned by probe tests rather than assumed.
The design records the measurement this rests on: `AssemblyLoadContext.Default.LoadFromAssemblyName` throws `FileNotFoundException` both when the host lacks an assembly and when it carries an older version, so the loader must ask by simple name and compare versions itself rather than distinguishing the two by exception type.
This story does not invoke `ContributeServices` through a recording wrapper; it returns the instances and draft 03 owns the invocation.

## Acceptance Criteria

- A `PluginsOptions` type binds the `Plugins` section with `Directory` (default `/app/plugins`, resolved against `AppContext.BaseDirectory` when relative) and `Allowed` as a `string` defaulting to the empty string. `Allowed` is split on commas once at bind time, each name trimmed, empty elements dropped, and the resulting order asserted to be the order written. A name repeated before or after trimming is fatal, naming the duplicate, and the duplicate check compares with `StringComparison.OrdinalIgnoreCase` so that two entries differing only in case are refused as ambiguous rather than resolving to one directory on a case-insensitive filesystem and two on the image's. Every other name comparison in this story is `StringComparison.Ordinal`. A test covers the case-only duplicate pair explicitly, and another asserts an ordinal comparison by loading a fixture whose directory differs from its `Name` only in case and asserting the mismatch is fatal. `Plugins__Allowed` set as an environment variable binds to the same ordered list as the JSON form.
- Each surviving name must be a single path segment matching `^[A-Za-z0-9][A-Za-z0-9._-]*$`; anything else is fatal, naming the entry and the rule, **before** the name is used to compose a path. Proven with `/etc/passwd`, `C:\\Windows`, `..`, `../sibling`, `sub/dir`, `sub\\dir`, and a leading-dot name, each asserted fatal and each asserted not to have opened any file. This is not stylistic: `Path.Combine(root, "/etc/passwd")` returns `/etc/passwd`, discarding the root entirely.
- Independently of the name rule, the composed plugin path is checked to sit under the root, and the check resolves symbolic links rather than normalizing lexically. The order of operations is the criterion, not an implementation note: the **root** is resolved once with `Directory.ResolveLinkTarget(root, returnFinalTarget: true)`, falling back to the root itself when that returns `null`; the plugin path is composed as `<resolvedRoot>/<Name>`; that path's final component is resolved the same way; and the result must start with the resolved root plus a directory separator. A path that does not is fatal, naming the entry and both resolved paths.
- Two fixtures prove it and **both** are required, because an implementation that passes either alone is a plausible wrong answer. A plugin directory that is a symbolic link to a directory outside the root is asserted fatal, which is the case the name rule cannot see. An ordinary, well-formed plugin directory under a plugin **root that is itself a symbolic link** is asserted to load. Composing against the configured root rather than the resolved one passes the first and fails the second: measured on `net10.0` with a root `app-plugins` linked to a sibling `realplugins`, it produced a resolved root of `.../realplugins` against a composed path of `.../app-plugins/Acme.Good` and reported the ordinary plugin as escaping. A third fixture, an escaping link **under** a linked root, is asserted fatal, which is the combination neither of the first two reaches.
- `Path.GetFullPath` alone does not satisfy this criterion and a test asserts as much: it normalizes lexically and never reads the filesystem, so on the escape fixture the composed path starts with the root and a `GetFullPath`-only implementation reports containment where the assembly loaded is the one outside.
- The containment check runs **after** the missing-directory check, and a test pins the ordering: `Directory.ResolveLinkTarget` throws `DirectoryNotFoundException` for a path that does not exist, measured on `net10.0`, so a misspelled allowlist entry must fail with the missing-path fatal rather than with a raw `DirectoryNotFoundException`.
- The check covers the plugin **directory** and nothing inside it. The entry assembly, the `.deps.json`, and every dependency under the directory may themselves be symbolic links pointing anywhere, and the loader does not resolve them. The story states this rather than leaving it implied, and points at design.md "### Trust Model and Verification": an `AssemblyLoadContext` isolates assembly identity and is not a security boundary, write access to the plugin root is equivalent to code execution as the host process, and this check is a completeness control that stops an unintended directory from loading rather than an integrity control against a party who can already write there.
- For each name in order, the loader resolves `<Directory>/<Name>/<Name>.dll` and `<Directory>/<Name>/<Name>.deps.json`. A missing root with a non-empty allowlist, a missing directory, a missing entry assembly, and a missing `.deps.json` are each fatal, naming the expected path. A missing root with an empty or absent allowlist returns an empty result and writes nothing.
- Before loading any type, the loader reads the entry assembly's references through `System.Reflection.Metadata` and, for every reference whose simple name matches a contract **assembly** the host declares, compares the referenced version to the version the host carries. A reference higher than the host's is fatal, naming the plugin, the contract, the version required, and the version the host carries, and a test asserts the failure came from the metadata read rather than from a type load by using a fixture whose type load would produce a different, recognizable error.
- The declared contract assemblies are a parameter supplied by the caller, not a constant in the loader, and they are **assembly names** rather than package ids. That distinction is load-bearing here and not stylistic: what an assembly reference carries is a simple assembly name, so the set the loader compares against is `EdFi.Api.Plugins` and `EdFi.DataManagementService.CustomValidation`, and never the package id `EdFi.Api.CustomValidation` that the latter ships under. A test passes a two-entry set and asserts a fixture skewed on the second entry is fatal and names it; another passes a set containing a package id where an assembly name belongs and asserts the skewed fixture is **not** caught, which is the failure mode this criterion exists to prevent from being written by accident. Draft 03 supplies the derivation that produces the set; the loader takes whatever it is given.
- A `.deps.json` carrying a `libraries` entry whose `type` is `runtimepack` is fatal, naming the plugin, because that is what a self-contained publish produces. The check does **not** key on a runtime identifier in `runtimeTarget`: a fixture published with `dotnet publish -r <rid> --no-self-contained` carries `".NETCoreApp,Version=v10.0/<rid>"` there and no `runtimepack` library, and a test asserts that fixture loads, since a RID-specific framework-dependent publish is how a plugin ships native assets.
- Each plugin loads into its own `AssemblyLoadContext` named for the plugin, non-collectible, backed by an `AssemblyDependencyResolver` over the plugin's `.deps.json`. `Load` calls `Default.LoadFromAssemblyName(new AssemblyName(assemblyName.Name))`, with the simple name only and no version: a `FileNotFoundException` from that call means the host carries nothing by that name and falls through to the resolver, and any other result is the host's copy. If the host's copy has a lower `AssemblyVersion` than `assemblyName.Version`, the loader throws, naming the plugin, the assembly, the version requested, and the version the host carries; otherwise the host's copy is returned. A test asserts the simple-name form is what is passed, by loading a fixture that declares a higher version of an assembly the host carries and asserting the host's copy was reached rather than a `FileNotFoundException` swallowed.
- The runtime wraps an exception thrown from inside `Load` in a `FileLoadException` whose `InnerException` is the thrown exception; the loader unwraps that chain before reporting, and a test asserts the reported message is "plugin '<name>' requires <assembly> >= <requested>, host carries <actual>" rather than the wrapper's own, which is measured on `net10.0` to be "Could not load file or assembly '<name>, Version=<the version the host carries>, Culture=neutral, PublicKeyToken=null'. General Exception (0x80131500)" and which names only the version the host has.
- Before constructing the plugin, the loader runs a preflight over the plugin's `.deps.json`: for every `runtime` entry carrying an `assemblyVersion`, it asks the host for that simple name and applies the same comparison, so a skewed dependency no hook happens to touch is still fatal at load rather than on a request. A test asserts a fixture whose skewed dependency is never referenced from any executed code path is still fatal, which is the case the `Load` override alone would miss. Reading `runtime` entries alone is sufficient for RID-specific managed assets and a test pins why: in a framework-dependent publish carrying `Microsoft.Data.SqlClient`, the library's `runtimeTargets` rows with `"assetType": "runtime"` repeat the simple name and the `assemblyVersion` of its top-level `runtime` entry, so a version skew in one is a version skew in the other. `"assetType": "native"` rows carry no `assemblyVersion` and are the known native gap; a RID-specific managed asset with no `runtime` counterpart, such as a resource assembly, is left to the `Load` override like anything else the manifest did not name.
- The preflight's largest blind spot is the **shared framework**, and the story states it rather than letting a reader infer that the preflight covers everything the manifest lists. A framework-dependent publish records no shared-framework assembly in its `.deps.json`: measured on `net10.0`, a class library carrying `<FrameworkReference Include="Microsoft.AspNetCore.App" />` and naming `IServiceCollection` and `IConfiguration` in its own public signatures published `--no-self-contained` to a `.deps.json` whose only library entry was the plugin itself. So a plugin that takes the two hook-signature abstractions from the shared framework rather than from packages gets no preflight coverage for them, and skew on one of them is caught by the `Load` override at first use. A fixture built that way is asserted to reach the `Load` backstop rather than the preflight, so the documentation and the guide can say "at first use" for that case honestly.
- `LoadUnmanagedDll` is overridden and returns a handle, not a path: it asks `_resolver.ResolveUnmanagedDllToPath(unmanagedDllName)`, passes a non-null answer to `LoadUnmanagedDllFromPath`, and returns `IntPtr.Zero` when the resolver has none, which is how the override defers to the default probing. A fixture plugin carrying a native asset under `runtimes/<rid>/native/` resolves it and calls into it. The story asserts no check that a declared native asset exists for the running RID: native resolution is lazy, so a missing one surfaces as `DllNotFoundException` at first use, and the design records that as a known gap.
- The loader reflects over the entry assembly's exported types for public non-abstract `EdFiApiPlugin` subclasses with a public parameterless constructor. Zero and more than one are each fatal, naming what was found. The one match is constructed and its `Name` compared to the directory name; a mismatch is fatal naming both.
- The entry assembly's own `AssemblyName` is compared to the directory name as well, and a mismatch is fatal naming both. This is the fourth of the four equalities design.md requires of directory, file name, `AssemblyName`, and `Name`, and it is the one the other three do not imply: a csproj can declare an `AssemblyName` and be published under a different file name, and such a plugin passes every other check. A fixture whose `AssemblyName` disagrees with its directory while its file name agrees proves it.
- The loader writes to `Console.Error` one line per allowlisted name in order, whether it succeeded or failed, and on failure the fatal reason. It also records, for every assembly it served host-first whose version differs from the version the plugin's `.deps.json` declared, the name and both versions, on a `LoadedPlugin` record the caller can log once a logger exists. `LoadedPlugin` also carries one row per file the plugin's `.deps.json` declares, with the file name, the declared `AssemblyVersion`, the SHA-256 computed over that file in the plugin directory, and a flag saying whether the assembly had been loaded into the plugin's context by the time loading finished. The declaration is the source, not the context's `Assemblies` enumeration: assemblies load lazily, so an enumeration taken at the end of startup omits every request-path assembly and every native library, and an inventory built from it would be silent exactly where an incident responder looks. A test asserts a plugin carrying a private third-party dependency lists both that dependency and the entry assembly; a second asserts that a declared assembly no executed code path touches still appears, with its digest and a loaded flag of `false`, which is the row the enumeration approach loses.
- Fixture plugin directories are built as test assets under `src/plugins/EdFi.Api.Plugins.Hosting.Tests.Unit/Fixtures/`: a well-formed plugin; one with no subclass; one with two; one whose `Name` disagrees with its directory; one whose entry assembly is corrupt; one published self-contained; one published `-r <rid> --no-self-contained`, which must load; one with no `.deps.json`; one carrying a private copy of `EdFi.Api.Plugins`, which asserts the host's copy is served; two plugins carrying different major versions of one third-party dependency the host does not carry, which asserts each gets its own; one built against a contract version higher than the host's; one declaring a higher version of an assembly the host carries; one whose skewed dependency is never referenced from executed code, for the preflight; and one carrying a native asset. Each fatal row is asserted to throw rather than log, and the well-formed cases are asserted to return one instance each in allowlist order.
- The `IChangeToken` regression test from design.md "### Load Isolation": a fixture plugin that binds options through `IOptions<T>` from a configuration section is loaded, `ContributeServices` is invoked against a real `ServiceCollection`, the provider is built, and the options resolve. A second copy of the loader with an enumerated shared set substituted for host-first is asserted to fail this case with `TypeLoadException`, so the test pins the decision rather than restating it.
- A probe test records what `Default.LoadFromAssemblyName` does when asked for a higher version of an assembly the host carries and when asked for an assembly the host does not carry, and asserts the two are indistinguishable by exception type. If a future runtime makes them distinguishable, this test fails and the loader's simple-name approach is revisited deliberately rather than silently.
- A test asserts a plugin compiled against contract `1.0.0` loads and runs against a contract assembly at `1.1.0` carrying an added no-op virtual, built as a test asset.
- `src/plugins/EdFi.Api.Plugins.Hosting.Tests.Unit` is a new project with a committed `packages.lock.json`, added to the same two solutions the production projects are in, `src/dms/EdFi.DataManagementService.sln` and `src/config/EdFi.DmsConfigurationService.sln`. `src/dms/EdFi.DataManagementService-Docker.sln` is deliberately left alone for the reason draft 01 records. `dotnet test src/plugins/EdFi.Api.Plugins.Hosting.Tests.Unit` passes.

## Tasks

1. Add `PluginsOptions` and its binder with the trim-split-reject-duplicates rule.
2. Add `PluginLoadContext` exactly as design.md "### Load Isolation" shows it: simple-name host resolution, the explicit version comparison, and the `LoadUnmanagedDll` override.
3. Add `PluginLoader.Load(IConfiguration, IReadOnlyCollection<string> contractAssemblyNames)` returning `IReadOnlyList<LoadedPlugin>`, with the allowlist name-shape check and the resolve-the-root-then-compose containment check, the metadata-read contract-skew check and the `.deps.json` dependency-skew preflight ahead of any type load, the `runtimepack` check, discovery, `AssemblyName` and `Name` verification, the `FileLoadException` unwrapping, and `Console.Error` reporting. The contract assembly names are a parameter rather than a constant here; draft 04 passes DMS's set, derived from the contract registry draft 03 adds.
4. Add `PluginLoadException` carrying plugin name and the structured reason.
5. Build the fixture plugin directories as test assets through a small MSBuild target or script that publishes each fixture project `--no-self-contained` into the test output, including the two version-skewed fixtures built against versions the host does not carry.
6. Build the three symbolic-link fixtures the containment tests need, since none can be a committed directory: the test creates, in its own temporary tree, an escaping link under a plain root, a well-formed plugin under a root that is itself a link, and an escaping link under a linked root.
7. Write the fatal-row tests, the name-shape and containment tests including the symlink escape, the symlinked-root positive case, the escape-under-a-linked-root case, the missing-directory ordering case, and the `GetFullPath`-is-not-enough assertion, the case-only duplicate and ordinal-comparison tests, the `AssemblyName` mismatch test, the isolation tests, the `IChangeToken` regression test with its enumerated-set control, the binder probe test, the unwrapping test, the native-asset test, the declared-but-unloaded inventory test, and the older-plugin-on-newer-host test.
