# Story: Document Plugins for Operators and Implementers and Publish the Host Assembly Manifest

## Description

Once the mechanism runs, nothing an operator or an implementer would find explains how to use it, and one fact they need does not exist yet anywhere: what assemblies the host carries.
This story writes the three documents the design owes and adds the per-release host assembly manifest, per:

- `reference/design/plugins-DMS-1462/design.md` ("### Acquisition" for the two recipes, "### Trust Model and Verification" for the operator requirements, "### Load Isolation" for the host manifest and the compatibility surface, "### The Plugin Contract" for the versioning and additive policy, "### Startup Failure Semantics" for the fatal catalogue)

The three documents are: the `Plugins` section of `docs/CONFIGURATION.md` completed, a new plugins chapter in `docs/OPERATIONS.md` carrying both acquisition recipes verbatim, and `PLUGINS.md`, the implementer guide packed into `EdFi.Api.Plugins` as its readme.
The recipes are load-bearing documentation, and the direction of that claim matters: the artifact is the pair of overlay files draft 04 committed, draft 04's end-to-end tiers run those files unedited and supply every deployment-specific value through the files' own `:?` environment variables, and this story asserts that the chapter it writes embeds them unchanged.
A change to either file has to run in draft 04's tiers and re-pass this story's equality assertion.

The host manifest exists because host-first resolution makes the host's whole assembly closure part of what a plugin is compatible with, and no contract package announces it.

DMS-1435, the custom validation implementer guide, is a separate document with a separate audience: it tells an implementer how to write a validator; this guide tells them how to package and deliver any plugin.
DMS-1435 links here for delivery and this guide links there for the validator contract.

## Acceptance Criteria

- `docs/CONFIGURATION.md`'s `Plugins` section states `Directory`, `Allowed` and that it ships empty, the trim-split rule, the single-path-segment name rule, that order is invocation order, that `Allowed` is the only switch and there is no per-feature toggle, and the configuration precedence order the design fixes: environment variables, then command-line arguments, then plugin sources in allowlist order, then `appsettings.json` and the other JSON sources. It states why the environment sits above the command line, which is DMS's own `AddEnvironmentVariables()` at `Infrastructure/WebApplicationBuilderExtensions.cs:46`, **with the qualifier design.md attaches to it**: that appended source outranks the command line only for keys read after `AddServices` has run. Two reads predate it and the chapter names them, because for those the command line wins: Serilog's configuration, read by `ConfigureLogging` (called at `:38`, reading `webAppBuilder.Configuration` at `:121`) before the `AddEnvironmentVariables()` call at `:46`; and `Plugins:Allowed` itself, read in the `LoadPlugins` bootstrap phase, which precedes the phase that calls `AddServices`. It also states why this is narrow in practice: `src/dms/run.sh:118` starts the application with no arguments, so the shipped container installs no command-line source at all and only a deployment that adds arguments is affected. `AppSettings:StartupStatusFilePath` is stated as the bootstrap exception it actually is, a key read before Phase A sources exist, and not as an exception to the environment-versus-command-line rule. The plugin-sources row is marked as landing with Phase A.
- `docs/OPERATIONS.md` gains a plugins chapter stating the plugin root must be writable by the deployment identity and never by the runtime identity, that the `:ro` mount is how a container deployment states that, and that DMS does not verify it. It carries Recipe 1 and Recipe 2 in Compose form as the two overlay files draft 04 committed, `eng/docker-compose/plugins-dms.yml` and `eng/docker-compose/plugins-fetch-dms.yml`, and Recipe 2 in Kubernetes `initContainers` form. It states the allowlist name rule as case-sensitive, since the image is Linux and every name comparison the loader makes is ordinal, and notes that a developer machine with a case-insensitive filesystem will resolve a mis-cased name that the image will not. It states that the two recipes are alternatives rather than additions, because both end at the single `/app/plugins` mount target; that the overlay is added with `-f` and the base compose files are unchanged; that clearing `<PluginRoot>/<Name>/` before extracting is part of the recipe; that the three deployment-supplied values are the `:?`-required environment variables `ACME_PLUGIN_PACKAGE_URL`, `PLUGIN_PACKAGE_SHA256`, and `PLUGIN_NAME`, which is what lets the committed file run without being edited; how to compute the digest to pin; and that the `fetch-plugins` image is pinned by digest, following the repository's own convention for third-party images (`eng/docker-compose/postgresql.yml:8`). The committed overlay carries a real, pullable `alpine` digest, so the chapter presents it as runnable as it stands and notes that an operator may re-pin it to an image they have approved rather than as a placeholder they must replace before the recipe works.
- **The Compose blocks in that chapter are asserted equal to the committed overlay files, and the assertion runs in this direction rather than the other.** A test reads each fenced Compose block out of `docs/OPERATIONS.md` and compares it byte for byte, after trimming trailing whitespace, with the corresponding file under `eng/docker-compose/`. The files are the artifact and draft 04's end-to-end tiers run them as committed; this story pins the prose to them, so a chapter edited without the file, or a file edited without the chapter, fails here. Nothing in any tier drives a recipe parsed out of Markdown, which would prove the document and not the artifact an operator actually composes with `-f`.
- The operations chapter groups every fatal row from design.md "### Startup Failure Semantics" by what the operator does about it (fix the allowlist, fix the deployment, contact the implementer, resolve a conflict between two plugins) rather than by mechanism, and states where the reason appears: the startup status file for why, the log for what loaded.
- `PLUGINS.md` in `src/plugins/EdFi.Api.Plugins/` replaces its placeholder with the implementer guide, containing a compiling sample of an `EdFiApiPlugin` subclass overriding `Name` and `ContributeServices`, the `dotnet publish --no-self-contained -o out/<Name>` command, the directory layout with the four-way equality rule design.md requires - the directory name, the entry assembly's file name, the loaded assembly's own `AssemblyName`, and `EdFiApiPlugin.Name` must all be the same string, compared ordinally, and each mismatch is fatal on its own - and the asset-only package shape under `contentFiles/any/any/<Name>/`.
- The guide states the compatibility surface as the contract packages **plus** the host assembly manifest for the DMS version targeted, and that a newer plugin on an older host is a named fatal.
- "By construction" is used for the **contract** and for nothing wider. An older plugin runs on a newer host by construction because the contract's shape and its additive-only policy make it so, which is design.md's claim under "### The Plugin Contract". The compatibility surface as a whole carries no such guarantee, and the guide does not imply one. design.md hedges the reverse direction under "### The Plugin Contract" - a plugin compiled against contract N+1 cannot run on a host carrying N, and that is a named fatal rather than a silent attempt - and hedges the manifest's reach under "### Load Isolation", where the `AssemblyVersion` comparison is stated as a major-skew check rather than a promise about every dependency. The guide repeats both hedges rather than the phrase.
- The guide states the dependency rule with the reach the loader actually has rather than as a blanket promise, in two respects. First, the manifest lists `AssemblyVersion`s, the loader compares `AssemblyVersion`s, and `Microsoft.Extensions.*` holds that version stable across a major, so the refusal fires on **major** skew and a plugin built against a newer minor of an assembly the host also carries loads without complaint. Second, **when** the refusal fires depends on where the assembly comes from: skew on anything the plugin's own `.deps.json` declares is caught at load by the preflight, while the manifest's shared-framework section is not in a framework-dependent `.deps.json` at all, so skew there is caught by the `Load` backstop at first use. The guide also says what "at first use" costs when that use is post-startup: on a request thread there is no loader frame to unwrap the friendly message, so the refusal surfaces as a `FileLoadException` inside the request and repeats on every request that reaches it, rather than stopping the process. An implementer who read "newer than the manifest is refused at load" and expected either a minor-level check or a startup-time one would be surprised in the wrong direction, which is why both limits are stated rather than left implied.
- The guide states the additive-only policy for `EdFiApiPlugin` and for every plugin-implemented interface, and that a breaking change is a new package id.
- The guide states that a plugin runs with full process trust, that the load context isolates assembly identity and is not a security boundary, and that the operator is told the same in `docs/OPERATIONS.md`.
- The guide states the naming rule the host-owned predicate makes necessary: a plugin must not name any assembly it ships with either Ed-Fi host prefix, `EdFi.DataManagementService.` or `EdFi.DmsConfigurationService.`, because that predicate keys on the assembly name and nothing else, so a type declared in an assembly a plugin published as `EdFi.DataManagementService.Acme` is treated as host-owned and refused. It states the consequence in one sentence - such a plugin fails the host-owned displacement check on its own types - so an implementer reads it as a naming rule rather than discovering it as an inexplicable fatal.
- The guide states what a plugin may and may not register: its own types and `Microsoft.Extensions.*` types freely; never a host-owned service type; never a removal of a host-owned descriptor. It states the registration form per cardinality as a rule rather than a suggestion, because the host's conflict detection depends on it: a **fan-in** contract is registered with `TryAddEnumerable`, and a **replace** contract is registered with a plain `Add`, never with a `TryAdd`. It gives the one-sentence reason - a replace contract has one claimant, so there is nothing to try - and states the consequence of ignoring it in the two shapes it actually has: a `TryAdd` that declines and was the plugin's one contribution leaves the plugin registering no declared contract, and startup fails naming it; a `TryAdd` that declines in a plugin that also registered something declared is **not** detected at all, and the replacement simply never happens. The guide states that second case plainly, because it is the one an implementer has to avoid by following the rule rather than by waiting for a startup failure to teach them. It states the two rules about removal that an implementer will otherwise learn from a startup failure: removing a pre-existing framework or third-party descriptor is permitted and appears in the inventory event, and removing one of the four logging-pipeline service types is **fatal**, so `logging.ClearProviders()` aborts startup while adding a provider does not. The guide gives the reason in one sentence - the host's logging is wired before a plugin's hook runs, so clearing providers silences DMS and the inventory event that would have recorded the plugin doing it - and says what to write instead.
- The sample is mirrored verbatim into `eng/verification/PluginsConsumer/` and compiles against the packed nupkg alone.
- A script under `eng/` emits `host-assembly-manifest.md` by inspecting the **released runtime image**, the one `src/dms/Nuget.Dockerfile` produces and `.github/workflows/on-prerelease.yml:542-552` builds and pushes under the name its `IMAGE_NAME` repository variable supplies (`.github/workflows/on-prerelease.yml:20`), which is `edfialliance/ed-fi-api` in the published registry. It emits three sections: the contract versions the release carries and the runtime base image reference and digest `src/dms/Nuget.Dockerfile:6` pins; one row per managed assembly at the **top level** of `/app`, with name and `AssemblyVersion`; and, for each of the two shared frameworks the application's `runtimeconfig.json` names, the version the image carries and one row per assembly in that framework's directory.
- Two scoping decisions in that script are stated in the story because both are easy to get wrong, and each has a test.
    - **The image is the released one, not the one `src/dms/Dockerfile` builds.** That Dockerfile produces `local/ed-fi-api` for development and for this repository's own test tiers, and the two are not interchangeable: `src/dms/Dockerfile:61` pins `aspnet:10.0.9-alpine3.23@sha256:f03685b2...` while `src/dms/Nuget.Dockerfile:6` pins `aspnet:10.0.3-alpine3.23@sha256:258b939d...`, so a manifest generated from the local image would state a shared-framework section no released image carries. The story notes that divergence as an observation and changes neither Dockerfile.
    - **The sweep is `/app/*.dll`, not everything under `/app`.** `/app/ApiSchemaDownloader/` is a second application that `src/dms/run.sh:53` invokes as its own process, packed as a sibling folder by `src/dms/frontend/.../EdFi.DataManagementService.Frontend.AspNetCore.nuspec:16`. Its assemblies are never in the DMS process, so a plugin can never be served one, and listing them would tell an implementer they were part of the compatibility surface. A test asserts the manifest contains no `ApiSchemaDownloader` assembly.
- Generating the manifest from the published `.deps.json` is explicitly rejected in the story and in the design: `src/dms/Dockerfile:56-57` publishes `--self-contained false`, so that file omits every shared-framework assembly, including `Microsoft.Extensions.Configuration.Abstractions` and `Microsoft.Extensions.DependencyInjection.Abstractions`, the two an implementer most needs; and `/app/Frontend` exists only in the build stage, while the released image and the `DataManagementService/` folder it unzips both use `/app`.
- A test asserts the generated manifest lists `Microsoft.Extensions.Configuration.Abstractions`, which is the assembly a `.deps.json`-based generator would silently omit, so a regression to that approach fails rather than shipping a manifest that looks complete.
- `on-prerelease.yml` runs the generator against the released image and attaches the result to the GitHub release beside the SBOM, and it does so in a **new job of its own** rather than as one more upload inside `attach-dms-artifacts-to-release` (`.github/workflows/on-prerelease.yml:381`). The reason is an ordering edge that job does not have: the image is built and pushed by the sibling `docker-publish-dms` (`:495`), whose only `needs:` is `publish-package-dms`, while `attach-dms-artifacts-to-release` needs the two pack, two SBOM, and two provenance jobs and has no edge to it, so the two run concurrently and a generator step added there could inspect an image that has not been pushed. The new job declares `needs: docker-publish-dms`, pulls the tag that job pushed, runs the generator, and resolves the release by the `vX.Y.Z` tag exactly as `attach-dms-artifacts-to-release` does with its own "Prepare release version" step (`:394-403`, read at `:436`), so the asset lands on the release an operator downloads.
- **The two gates differ and the story states the divergence rather than matching them silently.** `docker-publish-dms` carries no `if:` at all, so it also runs for an alpha prerelease and pushes the `pre` tag, while the manifest job carries the same `startsWith(github.event.release.tag_name, 'dms-') && !contains(github.event.release.tag_name, 'alpha')` gate `attach-dms-artifacts-to-release` carries, because an alpha prerelease has no `vX.Y.Z` release to attach an asset to. An alpha therefore publishes an image and no manifest, which is already what happens to the SBOM and the provenance, and the story says so in the pull request so nobody later reads the missing asset as a bug.
- **`on-release.yml` needs no change for the manifest, and the story says so rather than leaving a step nobody wrote.** That workflow deletes superseded pre-releases (`:22-63`), promotes Azure Artifacts packages through `Invoke-Promote` (`:66-116`), and retags the published images (`:119-192`). It attaches no GitHub release assets at all, so a manifest attached at prerelease is already on the release and there is nothing for it to promote.
- A CI assertion confirms the manifest lists `EdFi.Api.Plugins` at the version `src/plugins/Directory.Build.props` declares. It asserts **nothing** about `EdFi.Api.CustomValidation`'s version, and that scope is deliberate rather than an omission: `src/dms/core/EdFi.DataManagementService.CustomValidation/EdFi.DataManagementService.CustomValidation.csproj` declares no `Version`, `AssemblyVersion`, or `FileVersion` until draft 06, which this story precedes, so there would be no project-declared value to compare the manifest against. Draft 06 extends this assertion to the second contract in the same pass that creates the declaration, mirroring the split already made for draft 04's Docker-lane assertion.
- `eng/verification/Assert-PluginsPackage.ps1` asserts the packed readme is `PLUGINS.md` and is non-placeholder.
