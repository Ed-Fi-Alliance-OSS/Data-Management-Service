# Story: Add the Plugin Contract Package and `src/plugins/`

## Description

Nothing a third party can compile against names a plugin today.
This story ships the one type every plugin implements, `EdFiApiPlugin`, from a new published package, `EdFi.Api.Plugins`, and creates the `src/plugins/` folder both plugin projects live in, per:

- `reference/design/plugins-DMS-1462/design.md` ("### The Plugin Contract", "## Where the Code Lives", and the contract-versioning paragraphs under "### The Plugin Contract")

The first published contract carries `Name` and `ContributeServices` only.
`ContributeConfiguration` is decided in design.md but withheld until the secrets spike's first foundation story, because a virtual the host never calls is a hook a plugin can override to no effect.

The package is versioned on its own, starting at `1.0.0`, and deliberately outside `SetDMSAssemblyInfo`'s reach.
The loader's newer-plugin-on-older-host check compares `AssemblyVersion`s, so the contract's version has to move with its surface and only with its surface; stamping the DMS release onto it would refuse a plugin built against an identical contract.

This story follows the DMS-1432 pack-and-assert lane exactly, and stops short of publishing; see draft 06.

## Acceptance Criteria

- `src/plugins/EdFi.Api.Plugins/` exists and exposes exactly one public type, `EdFiApiPlugin`, an abstract class with `public abstract string Name { get; }` and `public virtual void ContributeServices(IServiceCollection services, IConfiguration configuration) { }`, with XML documentation on both members stating that `Name` must equal the plugin directory name and that the base implementation of `ContributeServices` is a no-op. The packed nupkg exports exactly that type, asserted against the XML documentation file the package carries.
- The project's only package references are `Microsoft.Extensions.Configuration.Abstractions` and `Microsoft.Extensions.DependencyInjection.Abstractions`, and the produced nupkg declares exactly those two dependencies, asserted against the extracted nuspec. This is a deliberate divergence from the sibling contract's zero-dependency policy (`src/dms/core/EdFi.DataManagementService.CustomValidation/EdFi.DataManagementService.CustomValidation.csproj:21-35`), and the csproj carries a comment saying so: `EdFiApiPlugin`'s hook signatures name `IConfigurationBuilder`, `IConfiguration`, and `IServiceCollection`, so the two Abstractions assemblies are in the public surface rather than in the implementation, and a contract cannot decline a dependency its own signatures require. Nothing beyond those two is added for an implementer's convenience.
- `src/plugins/Directory.Build.props` exists and carries what `src/dms/Directory.Build.props` actually carries: `Product`, `Authors`, `Company`, `TreatWarningsAsErrors`, `ErrorLog`, `RestorePackagesWithLockFile`, and the `Microsoft.CodeAnalysis.CSharp.CodeStyle` and `SonarAnalyzer.CSharp` analyzer `PackageReference`s with `PrivateAssets` all. It declares `VersionPrefix` of `1.0.0` and no `VersionSuffix`, with `AssemblyVersion` and `FileVersion` set to the same value. It is not generated and carries no "generated by the build script" comment. `TargetFramework`, `Nullable`, `ImplicitUsings`, and `GenerateDocumentationFile` are **not** in this file, because they are per-csproj everywhere under `src/dms/`; the license-header and formatting conventions come from the repository `.editorconfig` and csharpier, which reach `src/plugins/` without a props file. `src/dms/Directory.Build.targets` is not copied: it exists to materialize the bundled ApiSchema manifest and has no counterpart here.
- `build-dms.ps1`'s `SetDMSAssemblyInfo` is asserted not to touch `src/plugins/Directory.Build.props`: a test or build-lane step runs the build with an explicit `-DMSVersion` and asserts the file is byte-identical afterwards.
- A `build-dms.ps1` package target produces a nupkg whose package id is `EdFi.Api.Plugins`, whose package version is `1.0.0`, and whose contained `EdFi.Api.Plugins.dll` has `AssemblyVersion` `1.0.0.0`, all three asserted against the extracted package. The `AssemblyVersion` assertion is the one the DMS-1432 lane did not need and this one cannot do without, since it is what keeps the loader's skew check from going blind.
- The csproj declares `PackageLicenseExpression` of `Apache-2.0`, a `PackageProjectUrl`, a `Title`, a `Description`, and a `PackageReadmeFile` pointing at a `PLUGINS.md` beside it, whose placeholder content is replaced by draft 05. `Product`, `Authors`, and `Company` are declared in the new `Directory.Build.props` because nothing else supplies them under `src/plugins/`.
- `src/plugins/EdFi.Api.Plugins.Hosting/` exists as an empty class library project, not packaged (`IsPackable` false), so the solution and lock-file shape is settled here and draft 02 adds only code. It references `EdFi.Api.Plugins` by project.
- Both new projects are added to `src/dms/EdFi.DataManagementService.sln` and `src/config/EdFi.DmsConfigurationService.sln`, and each has a committed `packages.lock.json`. A missing project entry is a known failure mode in this repository and `--locked-mode` does not catch it, so the pull request lists both solution files in its diff. `src/dms/EdFi.DataManagementService-Docker.sln` is deliberately left alone: it carries six projects against the main solution's forty-four, it already omits `EdFi.DataManagementService.CustomValidation` and `Core.External`, and nothing builds it (`build-dms.ps1:165` knows only `EdFi.DataManagementService.sln`, and no workflow names it), so an entry there could go stale with nothing to notice.
- A scratch class library under `eng/verification/PluginsConsumer/`, whose only references are the produced `EdFi.Api.Plugins` nupkg from a local folder feed and the two `Microsoft.Extensions.*.Abstractions` packages it declares itself, compiles a subclass of `EdFiApiPlugin` overriding both members. Package source mapping pins the contract to the local feed so a published artifact cannot be substituted. The per-PR lane runs it, following `eng/verification/CustomValidationConsumer/` and the `on-dms-pullrequest.yml` job that drives it.
- `dotnet build src/dms/EdFi.DataManagementService.sln` and `dotnet build src/config/EdFi.DmsConfigurationService.sln` both succeed with `TreatWarningsAsErrors`, which with `GenerateDocumentationFile` set on the contract csproj makes an undocumented public member an error. Both commands already run in the per-PR lane, so this criterion has an automated home.

## Tasks

1. Create `src/plugins/Directory.Build.props` by copying the hand-maintained parts of `src/dms/Directory.Build.props` and adding `VersionPrefix` `1.0.0`, `Product`, `Authors`, and `Company`.
2. Add `src/plugins/EdFi.Api.Plugins/` with `EdFiApiPlugin`, the two Abstractions package references, the package metadata, and a placeholder `PLUGINS.md`.
3. Add `src/plugins/EdFi.Api.Plugins.Hosting/` as an empty, non-packable class library referencing the contract project.
4. Add both projects to `src/dms/EdFi.DataManagementService.sln` and `src/config/EdFi.DmsConfigurationService.sln`, and restore with lock files.
5. Add a `Plugins` package target to `build-dms.ps1` following the `CustomValidation` target's shape, packing with the project's own version rather than `-p:PackageVersion=$DMSVersion`.
6. Extend `eng/verification/Assert-CustomValidationPackage.ps1`'s pattern to a sibling script asserting id, package version, `AssemblyVersion`, dependency set, exported types, and readme presence for `EdFi.Api.Plugins`.
7. Add `eng/verification/PluginsConsumer/` and wire it into the per-PR lane beside the custom validation consumer.
8. Add the `SetDMSAssemblyInfo` non-interference assertion to the lane.
