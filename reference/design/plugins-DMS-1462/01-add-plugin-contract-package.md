# Story: Add the Plugin Contract Package and `src/plugins/`

## Description

Nothing a third party can compile against names a plugin today.
This story ships the one type every plugin implements, `EdFiApiPlugin`, from a new published package, `EdFi.Api.Plugins`, and creates the `src/plugins/` folder both plugin projects live in, per:

- `reference/design/plugins-DMS-1462/design.md` ("### The Plugin Contract", "## Where the Code Lives", the contract-versioning paragraphs under "### The Plugin Contract", and "### What the Stock Image Must Ship" for the build-stage change)

It also teaches `src/dms/Dockerfile`'s build stage about the new tree, which is a change no other story can safely make first: draft 03 adds the frontend's project reference into `src/plugins/`, and from that moment the image build has to be able to reach it.

The first published contract carries `Name` and `ContributeServices` only.
`ContributeConfiguration` is decided in design.md but withheld until the secrets spike's first foundation story, because a virtual the host never calls is a hook a plugin can override to no effect.

The package is versioned on its own, starting at `1.0.0`, and deliberately outside `SetDMSAssemblyInfo`'s reach.
The loader's newer-plugin-on-older-host check compares `AssemblyVersion`s, so the contract's version has to move with its surface and only with its surface; stamping the DMS release onto it would refuse a plugin built against an identical contract.

This story follows the DMS-1432 pack-and-assert lane exactly, and stops short of publishing; see draft 06.

## Acceptance Criteria

- `src/plugins/EdFi.Api.Plugins/` exists and exposes exactly one public type, `EdFiApiPlugin`, an abstract class with `public abstract string Name { get; }` and `public virtual void ContributeServices(IServiceCollection services, IConfiguration configuration) { }`, with XML documentation on both members stating that `Name` must equal the plugin directory name and that the base implementation of `ContributeServices` is a no-op. The packed nupkg exports exactly that type, asserted against the XML documentation file the package carries.
- The project's only package references are `Microsoft.Extensions.Configuration.Abstractions` and `Microsoft.Extensions.DependencyInjection.Abstractions`, and the produced nupkg declares exactly those two dependencies, asserted against the extracted nuspec. This is a deliberate divergence from the sibling contract's zero-dependency policy (`src/dms/core/EdFi.DataManagementService.CustomValidation/EdFi.DataManagementService.CustomValidation.csproj:21-35`), and the csproj carries a comment saying so: `EdFiApiPlugin`'s shipped hook signature names `IConfiguration` and `IServiceCollection`, so both Abstractions assemblies are in the public surface rather than in the implementation, and a contract cannot decline a dependency its own signatures require. `IConfigurationBuilder` joins them from the same `Microsoft.Extensions.Configuration.Abstractions` assembly when the secrets foundation story adds `ContributeConfiguration`, so that addition needs no new package reference. Nothing beyond those two is added for an implementer's convenience.
- `src/plugins/Directory.Build.props` exists and carries what `src/dms/Directory.Build.props` actually carries: `Product`, `Authors`, `Company`, `TreatWarningsAsErrors`, `ErrorLog`, `RestorePackagesWithLockFile`, and the `Microsoft.CodeAnalysis.CSharp.CodeStyle` and `SonarAnalyzer.CSharp` analyzer `PackageReference`s with `PrivateAssets` all. It declares `VersionPrefix` of `1.0.0` and no `VersionSuffix`, with `AssemblyVersion` and `FileVersion` set to the same value. It is not generated and carries no "generated by the build script" comment. `TargetFramework`, `Nullable`, `ImplicitUsings`, and `GenerateDocumentationFile` are **not** in this file, because they are per-csproj everywhere under `src/dms/`; the license-header and formatting conventions come from the repository `.editorconfig` and csharpier, which reach `src/plugins/` without a props file. `src/dms/Directory.Build.targets` is not copied: it exists to materialize the bundled ApiSchema manifest and has no counterpart here.
- `build-dms.ps1`'s `SetDMSAssemblyInfo` is asserted not to touch `src/plugins/Directory.Build.props`: a test or build-lane step runs the build with an explicit `-DMSVersion` and asserts the file is byte-identical afterwards.
- A `build-dms.ps1` package target produces a nupkg whose package id is `EdFi.Api.Plugins`, whose package version is `1.0.0`, and whose contained `EdFi.Api.Plugins.dll` has `AssemblyVersion` `1.0.0.0`, all three asserted against the extracted package. The `AssemblyVersion` assertion is the one the DMS-1432 lane did not need and this one cannot do without, since it is what keeps the loader's skew check from going blind.
- The csproj declares `PackageLicenseExpression` of `Apache-2.0`, a `PackageProjectUrl`, a `Title`, a `Description`, and a `PackageReadmeFile` pointing at a `PLUGINS.md` beside it, whose placeholder content is replaced by draft 05. `PackageReadmeFile` on its own does not pack the file: a markdown file beside a csproj is not a packed item under default SDK behaviour, so the csproj also carries `<None Include="PLUGINS.md" Pack="true" PackagePath="\" />`, exactly as the sibling contract does (`src/dms/core/EdFi.DataManagementService.CustomValidation/EdFi.DataManagementService.CustomValidation.csproj:37`). The readme's presence in the extracted nupkg is asserted, not assumed. `Product`, `Authors`, and `Company` are declared in the new `Directory.Build.props` because nothing else supplies them under `src/plugins/`.
- `src/plugins/EdFi.Api.Plugins.Hosting/` exists as an empty class library project, not packaged (`IsPackable` false), so this story settles the solution and lock-file shape for the two production projects. It references `EdFi.Api.Plugins` by project. Draft 02 still adds one project of its own, `EdFi.Api.Plugins.Hosting.Tests.Unit`, with its own solution entries and its own committed lock file; this story does not create it, because a test project with no code to test would be an empty shell nothing builds against.
- Both new projects are added to `src/dms/EdFi.DataManagementService.sln` and `src/config/EdFi.DmsConfigurationService.sln`, and each has a committed `packages.lock.json`. A missing project entry is a known failure mode in this repository and `--locked-mode` does not catch it, so the pull request lists both solution files in its diff. `src/dms/EdFi.DataManagementService-Docker.sln` is deliberately left alone: it carries five projects against the main solution's thirty-eight, it already omits `EdFi.DataManagementService.CustomValidation` and `Core.External`, and nothing builds it (`build-dms.ps1:165` knows only `EdFi.DataManagementService.sln`, and no workflow names it), so an entry there could go stale with nothing to notice.
- A scratch class library under `eng/verification/PluginsConsumer/`, whose only references are the produced `EdFi.Api.Plugins` nupkg from a local folder feed and the two `Microsoft.Extensions.*.Abstractions` packages it declares itself, compiles a subclass of `EdFiApiPlugin` overriding both members. Package source mapping pins the contract to the local feed so a published artifact cannot be substituted. The per-PR lane runs it, following `eng/verification/CustomValidationConsumer/` and the `on-dms-pullrequest.yml` job that drives it.
- CI notices a pull request that touches only `src/plugins`. Today it does not: `.github/workflows/on-dms-pullrequest.yml:136` and `.github/workflows/on-config-pullrequest.yml:116` set their relevance flag from a case list naming `src/dms/*` and `src/config/*`, and `.github/workflows/on-dms-merge-or-tag.yml:13-14` triggers on `paths: src/dms/**`. This story adds `src/plugins/*` to both relevance lists and `src/plugins/**` to the merge trigger, and the pull request records that its own checks ran, which is the observation the change exists to make possible.
- `src/dms/Dockerfile`'s build stage can see `src/plugins/`, and this story makes that change even though nothing in the image references the tree yet. The build stage copies an explicit per-project list inside the `src/dms/` build context, with `src/` available as the named context `parentdir` (`eng/docker-compose/local-dms.yml:11-13`), and `WORKDIR` is `/source`, so `src/plugins/` currently sits outside the tree it assembles. The change places the plugins tree beside the DMS tree exactly as `src/plugins` sits beside `src/dms`, with the repository's `Directory.Packages.props`, `nuget.config`, and `.editorconfig` at those trees' common parent rather than only inside `/source`; each new project's `.csproj` and `packages.lock.json` joins the restore pass at `src/dms/Dockerfile:15-29`, and its sources join the second pass at `:31-42`. Both new projects must carry committed lock files or `--locked-mode` fails the image build. `build-dms.ps1 DockerBuild` is run in this story and asserted to succeed, and the runtime stage (`:61-92`), `src/dms/run.sh`, `src/dms/Nuget.Dockerfile`, and the nuspec are asserted unchanged in the pull request diff.
- **This story owns that change because it creates the tree, and the ordering is what the criterion is for.** The frontend does not reference `EdFi.Api.Plugins.Hosting` today; draft 03 adds that `ProjectReference`, because its plugin guard is a frontend-owned startup task. From the moment that reference lands, a build stage that cannot reach `src/plugins/` fails `dotnet restore --locked-mode`, and `.github/workflows/on-dms-pullrequest.yml` builds `src/dms/Dockerfile` in nine places on a relevant pull request: the shared "Build and push DMS CI Docker image" step at `:696`, taken when prebuilt images are in use, and the eight "Build DMS Docker image" steps at `:1510`, `:1678`, `:1852`, `:2026`, `:2236`, `:2473`, `:2654`, and `:2864`, taken when they are not. Every one of them passes `file: ./src/dms/Dockerfile`, so both paths fail. Landing the build-stage change here rather than in draft 03 or 04 means no merge order can produce that failure. The other build-stage change, removing `/p:AssemblyVersion` from the publish command line, stays in draft 04, which also changes `build-dms.ps1`'s `DockerBuild`.
- `dotnet build src/dms/EdFi.DataManagementService.sln` and `dotnet build src/config/EdFi.DmsConfigurationService.sln` both succeed with `TreatWarningsAsErrors`, which with `GenerateDocumentationFile` set on the contract csproj makes an undocumented public member an error. Both commands already run in the per-PR lane, and with the relevance filters extended above they run for a pull request that touches only `src/plugins` as well, which is what gives this criterion an automated home rather than one that depends on the story's own diff happening to touch `src/dms`.

## Tasks

1. Create `src/plugins/Directory.Build.props` by copying the hand-maintained parts of `src/dms/Directory.Build.props` and adding `VersionPrefix` `1.0.0`, `Product`, `Authors`, and `Company`.
2. Add `src/plugins/EdFi.Api.Plugins/` with `EdFiApiPlugin`, the two Abstractions package references, the package metadata, and a placeholder `PLUGINS.md` packed through a `<None Include="PLUGINS.md" Pack="true" PackagePath="\" />` item.
3. Add `src/plugins/EdFi.Api.Plugins.Hosting/` as an empty, non-packable class library referencing the contract project.
4. Add both projects to `src/dms/EdFi.DataManagementService.sln` and `src/config/EdFi.DmsConfigurationService.sln`, and restore with lock files.
5. Add a `Plugins` package target to `build-dms.ps1` following the `CustomValidation` target's shape, packing with the project's own version rather than `-p:PackageVersion=$DMSVersion`.
6. Extend `eng/verification/Assert-CustomValidationPackage.ps1`'s pattern to a sibling script asserting id, package version, `AssemblyVersion`, dependency set, exported types, and readme presence for `EdFi.Api.Plugins`.
7. Add `eng/verification/PluginsConsumer/` and wire it into the per-PR lane beside the custom validation consumer.
8. Add the `SetDMSAssemblyInfo` non-interference assertion to the lane.
9. Add `src/plugins/*` to the relevance case lists in `.github/workflows/on-dms-pullrequest.yml:136` and `.github/workflows/on-config-pullrequest.yml:116`, and `src/plugins/**` to the `paths:` trigger in `.github/workflows/on-dms-merge-or-tag.yml:13-14`.
10. Change `src/dms/Dockerfile`'s build stage so the plugins tree sits beside the DMS tree with the shared props, `nuget.config`, and `.editorconfig` at their common parent, add both new projects to the restore and source passes, and run `build-dms.ps1 DockerBuild` to prove the image still builds.
