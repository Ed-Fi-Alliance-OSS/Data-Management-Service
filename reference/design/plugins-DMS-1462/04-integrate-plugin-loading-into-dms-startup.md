# Story: Integrate Plugin Loading into DMS Startup

## Description

The loader, the wrapper, and the guard exist but nothing in DMS calls them.
This story adds the `LoadPlugins` bootstrap phase to `Program.cs`, threads the loaded plugins into `AddServices`, re-emits the load inventory through Serilog once it exists, and proves the whole path with a real fixture plugin loaded by a real host, per:

- `reference/design/plugins-DMS-1462/design.md` ("### The Two Composition Phases" for the Phase B call site and the diagnostics rule, "### Observability", "### What the Stock Image Must Ship", "## Testing Strategy" integration and local-image tiers)

Only Phase B is wired.
Phase A's invocation, source placement, and additive guard land with the secrets spike's first foundation story.

The image gains two assemblies in the application's own publish output.
`src/dms/Dockerfile`'s build stage already carries `src/plugins/` by the time this story runs: draft 01 made that change when it created the tree, so that draft 03's frontend `ProjectReference` could not land in a build stage unable to reach it.
What this story changes in that file is one removal, and nothing is put in its place: it stops passing `/p:AssemblyVersion` and `/p:FileVersion`, which are global properties that override a contract project's own declared version and reach every project reference, so the contract that ships at `1.0.0.0` in the released package would otherwise carry the release version inside a locally built image.
An earlier revision replaced that stamping by having `build-dms.ps1`'s `DockerBuild` run `SetDMSAssemblyInfo` first, and design.md now rejects it: `SetDMSAssemblyInfo` regenerates the **tracked** `src/dms/Directory.Build.props` on every run, `DockerBuild` is reached from the `E2ETest` and `StartEnvironment` commands unless `-SkipDockerBuild` is passed, and the value it would stamp drops the build height the removed argument carried.
So a locally built image's DMS assemblies carry whatever the committed props declares, which is `8.0.0`, and that is accepted: nothing reads a DMS assembly's version out of a development image, while a contract assembly's version is read by the skew preflight.
The runtime stage, `src/dms/run.sh`, the entry point, `src/dms/Nuget.Dockerfile`, and the base compose files are all untouched, and that is what keeps the stock-image claim checkable.

This story builds its own minimal fixture plugin, and that fixture implements `ICustomResourceValidator`, the one contract DMS's production registry declares.
It has to implement something the production registry declares, because this story runs the production registry and a plugin that registers no declared contract is fatal.
`ICustomResourceValidator` ships in `EdFi.Api.CustomValidation`, which DMS-1432 already merged and packed, so the fixture depends on a **merged** contract package rather than on any open custom validation story.
The fixture's validator is a trivially passing one and this story asserts on the load inventory and on resolving the registration, not on a 400; it therefore needs neither DMS-1433's fan-in pipeline step nor DMS-1435's guide.
The custom-validation 400 over HTTP is DMS-1436's proof, and DMS-1436 depends on this story; wiring it the other way would make the two stories mutually blocking.
This story does depend transitively on DMS-1434, through draft 03, which runs its plugin guard beside DMS-1434's; the graph is still acyclic because nothing in the custom validation epic depends on this story except DMS-1435 and DMS-1436, which sit downstream of it.

The end-to-end tier here runs against a **locally built** image and proves everything except the word "stock"; draft 07 proves that word against a pulled image once one carries the loader.

## Acceptance Criteria

- `DmsStartupPhases.LoadPlugins` exists and `Program.cs` runs `PluginLoader.Load(builder.Configuration, DmsPluginContracts.Registry.ContractAssemblyNames)` inside `RunBootstrapPhase` between `WebApplication.CreateBuilder(args)` and the `ConfigureServices` phase, so it precedes the first configuration read in `AddServices`. The second argument is not optional and not a loader constant. `DmsPluginContracts` is this story's: a frontend-owned static holding DMS's one instance of draft 03's `PluginContractRegistry`, whose entries name `ICustomResourceValidator` as fan-in. `ContractAssemblyNames` is that registry's derived property rather than a second list: the registry computes it from the assembly declaring `EdFiApiPlugin` plus `typeof(T).Assembly.GetName().Name` for each declared contract type. For DMS that yields `EdFi.Api.Plugins` and `EdFi.DataManagementService.CustomValidation`, which are assembly names; a test asserts the package id `EdFi.Api.CustomValidation` is not among them, since an assembly reference carries an assembly name and matching on a package id would silently check nothing. Deriving it is what makes the skew preflight cover every contract the host declares without a change in the loader. A loader fatal takes the existing bootstrap fatal path and the startup status file records a failed `LoadPlugins` phase with the exception type and message, asserted by test.
- `WebApplicationBuilderExtensions.AddServices` takes draft 02's `LoadedPlugins` aggregate and invokes `ContributeServices` through the draft 03 invoker with `DmsPluginContracts.Registry`, after `AddServices`' own registrations and before `builder.Build()`. Adding that parameter is this story's diff: draft 03 left the signature alone and composed against `LoadedPlugins.Empty` inside the method, so what changes here is the source of the aggregate and nothing about the seam below it. The `PluginAuditInput` the invoker returns is registered in the same call through draft 03's frontend extension, which registers it as a singleton **instance** and registers the plugin startup task beside it, so records produced during Phase B reach a task resolved after `builder.Build()`. A test asserts the task read the records for the fixture plugin this story loads, which is what proves the seam is wired rather than merely designed. "After `AddServices`" is not "after every host registration": `Program.cs:46-110` registers JSON serializer options, response compression, `FormOptions` and `KestrelServerOptions`, forwarded headers, and CORS after `AddServices` returns, all of them inside the same `ConfigureServices` phase. A test asserts a plugin's hook sees the descriptors `AddServices` left behind, which is what the wrapper's pre-existing scope depends on, and the story states plainly that those later registrations are not visible to it, so nobody writes a plugin that expects them.
- Once the logger exists, one structured `Information` event per loaded plugin is emitted with named properties: `PluginName`, `AssemblyVersion`, `DeclaredFiles` (one entry per file the plugin's `.deps.json` declares, each carrying the file name, the declared `AssemblyVersion`, which is null for a native asset because none is declared and null for the entry assembly's own row, where the version reported instead is read from the loaded assembly and labelled as coming from there, neither case defaulting to a version nobody declared, its SHA-256 as read from the plugin directory, and whether it had loaded **at the moment this event is emitted**), `RegisteredServiceTypes`, `RemovedDescriptors`, and `HostFirstSubstitutions`. A test captures the log output and asserts the properties are present, that `DeclaredFiles` includes a declared assembly no executed code path touched, and that no configuration key or value appears.
- The loaded flags are read where the event is emitted rather than carried forward from loading, and that is a criterion because the two moments differ: an assembly first touched inside a `ContributeServices` hook loads after Phase B has returned, so a flag frozen at the end of `PluginLoader.Load` would report `false` for an assembly the process already holds. Draft 02 exposes the flags as a late-bound read against each plugin's context; this story materializes them at the emit point, immediately after `builder.Build()`. A test boots a fixture plugin whose hook forces a type load out of a declared dependency and asserts that dependency's flag is `true` in the emitted event, which a flag captured before Phase B would report `false`. The entry assembly's own row reports its version from the loaded assembly rather than from the declaration, since a framework-dependent publish's root `project` entry carries no `assemblyVersion`.
- The inventory event is emitted **before any startup task runs**, and that ordering is a criterion rather than an incidental placement. It goes immediately after `builder.Build()`, beside the existing `app.Logger` call at `Program.cs:131` that logs the startup status file path, and the startup-task executor is not entered until the `RunFatalAsync` invocations at `Program.cs:156`, `:163`, `:170`, and `:177`. Those invocations are the ordering evidence and the `RunByOrderRangeAsync` calls at `:315`, `:329`, and `:341` are not, because those sit in local-function bodies declared below `await app.RunAsync()` at `:256`, so their line numbers say nothing about execution order. The reason is attribution: draft 03 orders the plugin guard above DMS-1434's validator audit, so a plugin validator registered with the wrong lifetime is reported by that audit, which names the offending implementation type and knows nothing about plugins. A test boots a fixture plugin whose validator registration DMS-1434's guard rejects and asserts that the plugin inventory event, carrying that service type against the plugin name, appears in the captured log **before** the audit's failure. Without the ordering the operator is left with a type name and no way back to the plugin that supplied it.
- A `WebApplicationFactory<Program>` integration test boots with `Plugins:Directory` pointed at a fixture plugin directory and `Plugins:Allowed` naming it, and resolves a service only that plugin's `ContributeServices` could have registered.
- Fatal cases at the integration tier assert on the exception escaping host creation, not on `IStartupProcessExit`. Plugin loading runs pre-`Build()` inside `RunBootstrapPhase`, which writes the failed phase and rethrows (`Program.cs:443-462`), while `IStartupProcessExit` is DI-registered (`Infrastructure/WebApplicationBuilderExtensions.cs:79`) and first reached after `builder.Build()`, where `Program.cs:130` resolves `StartupPhaseExecutor`, which receives it through its primary constructor (`Infrastructure/StartupPhaseExecutor.cs:33-37`), so substituting it would prove nothing about this phase and a test that passed by substituting it would be passing for the wrong reason. Each of a misspelled allowlist entry, a plugin allowlisted on a missing root, and a plugin whose hook throws is asserted to throw out of `WebApplicationFactory`'s host creation, with no request ever served. The phase recorded in the startup status file differs between them and the assertions say which: the first two fail during loading and leave a failed `LoadPlugins` record, while a throwing `ContributeServices` hook fails during `ConfigureServices`, because `AddServices` invokes Phase B and `Program.cs:37-45` already runs `AddServices` inside that phase, and `RunBootstrapPhase` writes the phase it was given (`Program.cs:443-462`). The hook is not moved into `LoadPlugins` to make the record uniform: that would invoke Phase B before `AddServices` has populated the collection, which is the opposite of what the wrapper's pre-existing-descriptor scope needs.
- With `Plugins:Allowed` empty and no plugin root present, the host boots exactly as it does on main, asserted by the existing integration suite passing unchanged.
- A directory present under the plugin root but absent from `Plugins:Allowed` produces one warning naming it and is never opened, asserted by placing a directory whose entry assembly is deliberately corrupt and observing a clean boot.
- `docs/CONFIGURATION.md` gains the `Plugins` section with `Directory` and `Allowed`, stating that `Allowed` ships empty, that it is the only switch, and that its order is invocation order. It also states the one bootstrap exception: `AppSettings:StartupStatusFilePath` is read at `Program.cs:30-33`, before plugins load, so no plugin source can ever supply it. The full operator and implementer documentation is draft 05; this story adds only what its own configuration surface needs.
- Two new overlay compose files carry the mount, and they are the artifact: this story creates them, its end-to-end runs drive them as committed, and draft 05 later asserts that `docs/OPERATIONS.md` embeds them unchanged. `eng/docker-compose/published-dms.yml` and `eng/docker-compose/local-dms.yml` are unchanged. `eng/docker-compose/plugins-dms.yml` declares `- ${DMS_PLUGINS_MOUNT_SOURCE:?...}:/app/plugins:ro` on the DMS service for Recipe 1; `eng/docker-compose/plugins-fetch-dms.yml` declares the `fetch-plugins` one-shot service, the named volume, the `depends_on: condition: service_completed_successfully`, and the same mount for Recipe 2. They are alternatives, not additions: `/app/plugins` is one mount target. Each is added with `-f`, following `eng/docker-compose/bootstrap-dms.yml` and `local-dms-diagnostics.yml`. **All four variables the two overlays declare get the same documentation homes**, `DMS_PLUGINS_MOUNT_SOURCE` for Recipe 1 and `PLUGIN_PACKAGE_URL`, `PLUGIN_PACKAGE_SHA256`, and `PLUGIN_NAME` for Recipe 2: `eng/docker-compose/README.md`, `eng/docker-compose/.env.example`, which is tracked and is where an operator looks first, and the `.env.*` files the plugin end-to-end test uses. Recipe 2's three are not a lesser case than the mount: an operator who composes `plugins-fetch-dms.yml` in and finds three `:?` failures with nothing documented is in exactly the position the mount variable's entry exists to prevent. Because every one of the four is declared with `:?` rather than a default, each `.env.example` entry is commented out with the same note, that setting it is what a deployment does when it composes the overlay in, so an uncommented empty value cannot make a deployment that never asked for plugins fail. An unconditional mount in the base files is rejected because Docker would then create an empty root-owned `./plugins` beside every deployment that never asked for a plugin.
- The `src/dms/Dockerfile` build-stage change that lets the image see `src/plugins/` is **not** this story's; draft 01 made it, and draft 03 exercised it by adding the frontend's `ProjectReference`. This story asserts only that it still holds, by running `build-dms.ps1 DockerBuild` in its own end-to-end test and by listing in the pull request that its diff of that file touches the publish command line and nothing else.
- `src/dms/Dockerfile`'s publish step no longer passes `/p:AssemblyVersion` or `/p:FileVersion`, and the `ASSEMBLY_VERSION` build argument that fed them (`:45`, `:53-54`) is removed along with the `ASSEMBLY_VERSION` build-arg pair in `build-dms.ps1`'s `DockerBuild` (`:1962-1970`). **Nothing replaces the stamping**: the build stage takes whatever `src/dms/Directory.Build.props` declares in its committed shape, which the Dockerfile already copies at `:13` and which is `8.0.0` (`:3-4`). `/p:Version` and `/p:InformationalVersion` stay, because a global `Version` is measured not to override an explicitly declared `AssemblyVersion`. The proof is a test that builds the image with an explicit `-DMSVersion`, reads `EdFi.Api.Plugins.dll` out of it, and asserts it carries `1.0.0.0`, the version `src/plugins/Directory.Build.props` declares, while `EdFi.DataManagementService.Frontend.AspNetCore.dll` carries the committed `src/dms/Directory.Build.props` value and **not** the `-DMSVersion` the build was given. Without this the contract assembly ships two different `AssemblyVersion`s across the two image lanes, and the loader's skew preflight compares exactly that value.
- **`DockerBuild` is deliberately not taught to run `SetDMSAssemblyInfo`, and this story carries the assertion that proves it.** That helper regenerates the tracked `src/dms/Directory.Build.props` into a different shape (`build-dms.ps1:210-241`) and rewrites it on every run: the write goes through `Invoke-RegenerateFile`, whose change guard compares an undefined `$new_content` against the file instead of the `$NewContent` parameter (`eng/build-helpers.psm1:17`), and the regenerated shape differs from the committed one in any case, so this criterion holds whether or not that guard is ever repaired. Its only caller today is `BuildAndPublish`, through `Invoke-SetAssemblyInfo` (call at `:1871`, declaration at `:1868`, command at `:2006`); `DockerBuild` itself regenerates nothing (`:1960-1976`) and is reached from the `E2ETest` command (`:2011`, `E2ETests` at `:1127`, `Start-DockerEnvironment` at `:870-871`) and from `StartEnvironment` (`:2033`, `Start-BootstrapDockerEnvironment` at `:976-977`) unless `-SkipDockerBuild` is passed, so calling the helper there would rewrite a tracked file on every local run of either. `InstanceE2ETest` never reaches `DockerBuild`: it delegates to `src/dms/tests/EdFi.InstanceManagement.Tests.E2E/setup-local-dms.ps1` (`:1697`), which rebuilds the image on its own path. It would also execute only on developer machines, since every CI end-to-end leg passes `-SkipDockerBuild` and CI's own image is built by `docker/build-push-action` with no build arguments at all (`.github/workflows/on-dms-pullrequest.yml:696-707`, `:1510-1522`). And it stamps a different value from the argument it would replace: `Convert-ToAssemblyVersion` maps `8.4.0-pre.0.4` to `8.4.0.4` (`package-helpers.psm1:165-190`) while `VersionPrefix` stamping yields `8.4.0.0`, so the build height would be dropped. The criterion is that `src/dms/Directory.Build.props` is byte-identical and `git status` is clean after `build-dms.ps1 DockerBuild` is run with an explicit `-DMSVersion`.
- The consequence is accepted and stated in the pull request rather than left to be noticed later: a locally built `local/ed-fi-api` image's DMS assemblies carry `AssemblyVersion` and `FileVersion` `8.0.0` regardless of `-DMSVersion`, where today they carry a version derived from it. Nothing in this design or elsewhere reads a DMS assembly's version out of that image, `Version` and `InformationalVersion` still record what it was built for, and the release lane is untouched: `BuildAndPublish` still calls `Invoke-SetAssemblyInfo` (`build-dms.ps1:2006`), so the `EdFi.Api` package and the image an operator pulls are stamped exactly as they are today.
- The assertion covers `EdFi.Api.Plugins.dll` **only**, and that scope is deliberate rather than an oversight. `src/dms/core/EdFi.DataManagementService.CustomValidation/EdFi.DataManagementService.CustomValidation.csproj` declares no `Version`, `AssemblyVersion`, or `FileVersion` today; it inherits them from `src/dms/Directory.Build.props`, and draft 06 is the story that gives it its own. Asserting here that `EdFi.DataManagementService.CustomValidation.dll` "carries the version its own project declares" would be asserting against a value no project declares. Draft 06 extends this same assertion to that assembly in the same pass that adds the declaration, and its own scope note says so.
- `src/dms/run.sh`, `src/dms/Nuget.Dockerfile`, the Dockerfile's runtime stage (`:61-92`), and `src/dms/frontend/.../EdFi.DataManagementService.Frontend.AspNetCore.nuspec` are unchanged, asserted by the pull request diff. The nuspec needs nothing because it packs `**` from the publish directory, so the two new assemblies ride along.
- A local end-to-end test builds the DMS image with `build-dms.ps1`, publishes **this story's own** minimal fixture plugin `--no-self-contained` into a plugin directory, mounts it read-only through `plugins-dms.yml`, allowlists it, and asserts on the container's log output that the per-plugin inventory event named the fixture with its version and digests, and that removing the name from `Plugins:Allowed` produces no such event and an otherwise identical boot. The fixture registers a trivially passing `ICustomResourceValidator` through `TryAddEnumerable`, which is the one contract DMS's production registry declares and therefore the only kind of registration that satisfies the no-contract-registered check under the real registry. It consumes `EdFi.Api.CustomValidation` as a packed nupkg from the local folder feed, exactly as an external implementer would, and that package is merged work rather than an open story. This story asserts that the registration resolves and that the inventory names it; it does not exercise the fan-in pipeline step and does not depend on DMS-1433. Proving a custom-validation 400 over HTTP against a stock image is DMS-1436's criterion, and DMS-1436 depends on this story.
- A second local end-to-end run exercises Recipe 2 in its own Compose deployment, driving the committed `plugins-fetch-dms.yml` unedited rather than alongside Recipe 1, since both end at `/app/plugins`: the same fixture plugin packed asset-only into a `.nupkg`, fetched by the one-shot `fetch-plugins` service, digest-verified, extracted, and loaded. **"Unedited" means env-driven: the file is untouched and the harness supplies its three `:?`-required values**, `PLUGIN_PACKAGE_URL`, `PLUGIN_PACKAGE_SHA256`, and `PLUGIN_NAME`. The happy path computes the SHA-256 of the fixture nupkg it just packed and exports it, which is what makes the run repeatable even though a nupkg is not byte-reproducible across packs. A third run exports a `PLUGIN_PACKAGE_SHA256` that is deliberately wrong, with the same file and the same package, and asserts the service exits non-zero and DMS never starts.
- **The feed for that run is served over HTTP by the harness, and the published overlay is not modified to accommodate it.** Every other packaged path in this spike consumes a nupkg from a local **folder** feed and Recipe 2 cannot: `fetch-plugins` mounts only `plugins:/out`, its BusyBox `wget` speaks http, https, and ftp, and `PLUGIN_PACKAGE_URL` is a `PackageBaseAddress` address rather than a path. The harness therefore lays the packed nupkg out as `<id>/<version>/<id>.<version>.nupkg` in lower case, serves that directory over HTTP from a static-file container pinned by digest in a **test-owned** Compose overlay added with its own `-f`, and sets `PLUGIN_PACKAGE_URL` to that address. `eng/docker-compose/plugins-fetch-dms.yml` is run exactly as **committed**, unedited by the harness, which is the property this tier exists to prove; supplying a feed address, a digest, and a plugin name through the file's own `:?` variables is the deployment's side of the recipe in a real deployment too. The equality between that file and what `docs/OPERATIONS.md` prints is asserted by draft 05, which writes the chapter, as a document-versus-file check; this story runs the file and never reads the Markdown, since draft 05 comes after it and a test that pasted a recipe out of a chapter that does not exist yet could not run at all.
- The two sentences in `src/dms/core/EdFi.DataManagementService.CustomValidation/ICustomResourceValidator.cs:16-17` that tell an implementer the interface "is compiled into the host deployment and registered into DMS's composition; it is not loaded from a dropped-in assembly at runtime" are corrected to describe plugin delivery. That text ships inside the nupkg and shows in an implementer's IDE, and this story is the one that makes it false. The change is to the XML documentation only; no type, member, or signature moves, so `eng/verification/Assert-CustomValidationPackage.ps1`'s exported-type assertions are unaffected.
- `dotnet test src/dms/tests/EdFi.DataManagementService.Tests.Integration` passes.
