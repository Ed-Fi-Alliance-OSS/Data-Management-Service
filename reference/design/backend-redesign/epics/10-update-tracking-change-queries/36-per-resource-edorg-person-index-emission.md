# Story: Emit Per-Resource EdOrg and Person Tracked-Change Indexes

## Description

Story 34 establishes the provider-appropriate `ReadChanges` relationship query shape and freezes its cross-provider performance baseline.
This story then evaluates and emits only the per-resource EdOrg and person tracked-change indexes, keeping index effects isolated from the runtime rewrite and from Namespace prefix work.
It depends on Stories 33 and 34.

## Acceptance Criteria

- Extend the tracked-change portion of `DeriveIndexInventoryPass` with one single-key `DbIndexKind.Authorization` candidate for each root-scoped non-namespace EdOrg securable scalar column and each `TrackedChangeColumnRole.PersonDocumentId` column, excluding `SharedDescriptor`.
- Support both joined-person columns and zero-hop self-person columns (`PersonJoinName = null`, `CanonicalStorageColumn = DocumentId`, exact self identity path).
- Equality coverage may deduplicate a candidate when a provider-compatible existing PK/UK or index has the same leading column.
- Array-nested EdOrg securables remain outside tracked storage. Only-array-nested and mixed root/array configurations retain the security-configuration behavior specified by Story 34; index derivation does not reinterpret them as dynamic empty sets.
- Enumerate every candidate index in the harness artifact (at current DS 5.2 scale roughly 90 EdOrg scalar and 60 person columns across the per-resource tracked tables) and group the candidates under schema-derivable emission predicates keyed by index class (EdOrg scalar, joined-person, self-person) and key-column scalar type. Emission is decided per predicate because `DeriveIndexInventoryPass` sees only the derived model and never deployment cardinality: every tracked table matching an adopted predicate receives its index deterministically, including extension-project resources and tables absent from the benchmark schema.
- Within each predicate, stratify the benchmarked candidates by tracked-table cardinality tier and name at least one measured representative table per stratum, including each stratum's largest-cardinality table. Predicate membership, strata, and representatives are recorded in the artifact before measurement; strata exist to prove a predicate safe across the cardinality range and never participate in the emission rule.
- All read and write comparisons in every phase follow `22-spike-findings.md` § "Tracked-index evidence protocol": environment pinning, both supported SQL Server compatibility levels, workload floors, measurement and noise controls, the seek-use requirement, and the write and per-table baseline storage ceilings.
- After Story 34's selected query shapes are fixed, run an isolated predicate-only overlay for each emission predicate on both providers, over every representative table's applicable shapes: each predicate crosses its applicable strategy shapes with `/deletes` and `/keyChanges`, the five window shapes of the Tier-1 emission story's matrix (no bounds, min-only, max-only, both-bounds full, both-bounds narrow) with every cell also recording the separate `totalCount` count statement, and single-subject and district-scale subject cardinalities. Predicates in the EdOrg scalar class cross `RelationshipsWithEdOrgsOnly`, `RelationshipsWithEdOrgsOnlyInverted`, and `RelationshipsWithEdOrgsAndPeopleIncludingDeletes`, whose envelope ANDs the EdOrg predicate with the person predicates; predicates in the joined-person and self-person classes cross `RelationshipsWithEdOrgsAndPeopleIncludingDeletes`, `RelationshipsWithStudentsOnlyIncludingDeletes`, and `RelationshipsWithStudentsOnlyThroughResponsibilityIncludingDeletes`. Overlays compare against the protocol's cumulative baseline: the current generated DDL including Story 33's adopted categories, measured under Story 34's shipped query shapes. A predicate is eligible only when at least one representative shape in its largest-cardinality stratum provides the protocol's required benefit, every measured shape in every stratum stays within the protocol's regression ceiling, and no measured shape acquires a new unstable per-row nested-loop plan. Isolation comes from the predicate-only overlay, not post-hoc attribution; predicates may not borrow benefit or low cost from one another.
- Rerun the read matrix with the combined overlay of all eligible predicates, and rerun the bulk tombstone/key-change write matrix on every representative table that carries indexes from more than one predicate in that overlay. Every measured read shape must stay within the protocol's regression ceiling with no prohibited plan shape, and every measured combined per-table write ratio must stay within the protocol's write ceilings, before implementation begins. A combined failure preserves the isolated results, blocks simultaneous emission, and returns the selection for review, which may adopt a subset of the eligible predicates. An adopted subset containing more than one predicate must rerun a combined overlay restricted to that subset and pass the same read and write ceilings before implementation; a single-predicate subset is covered by its isolated result. Members of a non-adopted or unmeasured predicate are not emitted.
- Measure bulk tombstone/key-change writes on each representative table in the isolated overlays against the protocol's per-table write ceilings.
- Verify storage exhaustively rather than by representative: after building the full adopted index set at implementation scale, every affected tracked table must satisfy the protocol's per-table baseline storage ceilings. A provider failure blocks the affected predicates on both providers pending redesign.
- Unit and integration coverage matches the adopted predicates and the exclusions above on both providers; the concrete test and fixture inventory is owned by this ticket's tasking.
- Regenerate the affected DDL/manifests/goldens and pass PostgreSQL and SQL Server generated-DDL integration smoke tests; the `RelationalMappingVersion` bump this physical change requires is deferred to a dedicated mapping-version ticket rather than owned here; the first such ticket is filed with the follow-on tickets after spike approval and must land no later than the first story that ships a physical index change, and each later independently released batch of physical index changes requires its own bump ticket for that release.
- After emission, verify that the exact generated DDL for every adopted predicate is semantically identical to its pinned overlay over the benchmark deployment's tables (per-table key columns, operator classes, deduplication outcomes, and shortened identifiers); tables absent from the benchmark schema are covered by the deterministic emission predicate and the protocol's predicate-level seek verification rather than the overlay comparison or per-index seek measurement. Then rerun the applicable representative read and write matrix against that generated DDL. A mismatch or failed post-implementation gate blocks acceptance rather than being described as run-to-run noise.
- When predicates are adopted, this ticket merges the adopted design into the normative `change-queries.md`: the emission predicates, index shapes, and coverage and deduplication rules, superseding the deferral recorded in `22-spike-findings.md` § "Per-resource securable-element indexes are deferred".
- Namespace predicate changes and tracked namespace indexes are out of scope and owned by Story 37.
