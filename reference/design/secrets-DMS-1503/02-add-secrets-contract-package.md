# Story: Add the `EdFi.Api.Secrets` Contract Package and Relocate `IClientSecretHasher`

## Description

A plugin cannot claim a contract that does not exist, and it cannot compile against one that ships from an assembly named for an identity provider half the deployments do not use.
This story creates the Configuration Service's secrets contract package, defines the secret resolver in it, moves `IClientSecretHasher` into it, and repairs the configuration key the host's own hasher needs, per:

- `reference/design/secrets-DMS-1503/design.md` ("### The Contract Package", "### The `IClientSecretHasher` Relocation", "### Contract Cardinality")
- `reference/design/plugins-DMS-1462/design.md` ("### The Plugin Contract" for the additive-only policy and the package-versus-assembly-name rule, "### Applicability to the Configuration Service" for the relocation's provenance)

No plugin loads yet.
This story ships a contract and a corrected host default, and nothing calls a resolver until CMS host integration lands.
That split is deliberate: the package is what an implementer builds against, it has to be right before anything depends on it, and its public surface becomes a compatibility commitment the moment it is published.

The hashing-iterations repair travels with the relocation rather than being filed separately.
The spine found and recorded the defect and changed no code, handing the question here explicitly: the contract has to name a key that actually binds rather than inheriting either of the two dead ones.
Repairing it is what makes replacing the hasher an operator's option rather than their only route to a setting that was supposed to be configuration.

## Acceptance Criteria

- A new project `src/config/contracts/EdFi.DmsConfigurationService.Secrets/` packs as `EdFi.Api.Secrets` with assembly and root namespace `EdFi.DmsConfigurationService.Secrets`. The package id carries the platform prefix every contract package uses and the assembly is named for the tree it lives in, following `EdFi.Api.Identity` from `EdFi.DataManagementService.Identity`. The two names are never used interchangeably: a test asserts that the assembly name the package contains is `EdFi.DmsConfigurationService.Secrets`, because an assembly reference carries an assembly name and a skew preflight matching on a package id would silently check nothing.
- The project declares its own `AssemblyVersion`, `1.0.0`, in its own csproj. The loader's skew preflight compares exactly that value, so it must move when this contract's surface moves and must not move when it does not; tying it to the CMS release version would refuse a plugin built against the 8.4 contract on an 8.3 host whose surface is identical, naming two versions an implementer cannot act on.
- **Three lanes would otherwise stamp over it, and the csproj declaration closes only one of them.** The declaration beats an imported props file, so `SetDMSAssemblyInfo`, which regenerates `src/config/Directory.Build.props` with `VersionPrefix` set to the release version (`build-config.ps1:143-160`, reached from `BuildAndPublish` through `Invoke-SetAssemblyInfo` at `:377-381`, `:502`), is closed by the declaration alone. It does **not** beat a command-line global property, and there are two of those: `Compile` passes `/p:AssemblyVersion=$DmsCSAssemblyVersion` to `dotnet build` (`build-config.ps1:185-189`) and `PublishApi` passes it to `dotnet publish` (`:206-210`), both whenever `-DmsCSAssemblyVersion` is supplied, which `.github/workflows/on-prerelease.yml:591` does on the lane that packs the released package. A global property propagates to every project reference, so the contract would carry the release version in the very lane that produces the published package.
- **This story therefore excludes the contract project from both, and the exclusion is the criterion rather than the declaration.** The implementation is the project's choice, `GlobalPropertiesToRemove` metadata on the `ProjectReference` items that reach it or an equivalent, and the pull request names which. The proof reads **both** lanes' outputs, because they are separate builds and a fix to one does not prove the other: a test runs `build-config.ps1 BuildAndPublish` with an explicit `-DmsCSVersion` **and** an explicit `-DmsCSAssemblyVersion`, then asserts `1.0.0.0` on `EdFi.DmsConfigurationService.Secrets.dll` in the `Compile` step's own build output **and** in the `PublishApi` output. Asserting only the published copy can pass while `Compile` is still stamping, because `PublishApi` rebuilds. Whichever mechanism the implementation uses, `GlobalPropertiesToRemove` on the referencing `ProjectReference` items or another, it has to hold for a solution build that reaches the project directly and not only for a reference walk, and the pull request names what it used and which of the two assertions proved it. A test that supplies only `-DmsCSVersion` passes without exercising the lane that actually breaks this, which is why the assembly-version argument is named in the criterion.
- A test asserts the `AssemblyVersion` of the assembly inside the packed nupkg equals the package version.
- **The Docker lane is the third, and `src/config/Dockerfile` stops stamping `AssemblyVersion` on the publish command line, with nothing replacing it.** It accepts an `ASSEMBLY_VERSION` build argument (`:33`) and expands it into `/p:AssemblyVersion` and `/p:FileVersion` (`:39-40`), which is a global property: it overrides a csproj-declared value and propagates to every project reference, so this contract would publish as `1.0.0.0` in its package and as the release version inside a locally built image. The argument and the two properties come out, and the matching `ASSEMBLY_VERSION` build-arg pair comes out of `build-config.ps1`'s `DockerBuild` (`:463-467`). This mirrors the removal `src/dms/Dockerfile` **is taking** in the still-open DMS-1499, rather than one it has already taken: that file still declares `ARG ASSEMBLY_VERSION` (`:112`) and still expands `/p:AssemblyVersion` and `/p:FileVersion` (`:120-121`), so an implementer who opens it expecting a worked precedent will find the pre-change state. The reasoning is the same and the blast radius is the same, which the story states rather than assumes: `src/config/Dockerfile` builds the local development image, while the image an operator pulls is built from `src/config/Nuget.Dockerfile`, which compiles nothing and only downloads and unzips the `EdFi.Api.ConfigurationService` package (`:23-25`), echoing the argument it is passed (`:21`). So the released image is untouched and only a locally built image's CMS assemblies change, carrying whatever `src/config/Directory.Build.props` declares.
- The proof is a test that builds the local image with an explicit `-DmsCSAssemblyVersion` and asserts `EdFi.DmsConfigurationService.Secrets.dll` inside it carries `1.0.0.0`, the version its own csproj declares, while a CMS assembly carries the committed props value and **not** the version the build was given. Without it the contract ships two different `AssemblyVersion`s across two lanes and the loader's skew preflight compares exactly that value.
- `ISecretResolver` is defined with one member, `ValueTask<string> ResolveAsync(SecretReference reference, CancellationToken cancellationToken)`, and `SecretReference` is a `sealed record (string Name, string? Tenant)`. The record exists so the contract can gain an input later: the additive-only policy forbids changing a member's signature, so a two-parameter method could never take a third value, while a record can gain a property with a default. `Tenant` is null in a single-tenant deployment and carries the tenant name in a multi-tenant one.
- `IClientSecretHasher` moves from `Backend.OpenIddict/Services/IClientSecretHasher.cs` into this package with its three members and their signatures unchanged. `ClientSecretHasher` does **not** move: it is the host default rather than part of the contract, and it reads `IdentityOptions`, which is an OpenIddict type.
- All four registration sites and both consumers compile against the new namespace: `Config.Frontend/Infrastructure/WebApplicationBuilderExtensions.cs:206`, `Backend.Postgresql/OpenIddict/PostgresOpenIddictServiceExtensions.cs:37` and `:93`, `Backend.Mssql/OpenIddict/MssqlOpenIddictServiceExtensions.cs:35`, `Backend.OpenIddict/Repositories/OpenIddictClientRepository.cs:21`, and `Backend.OpenIddict/Services/OpenIddictTokenManager.cs:28`. The `:93` site sits inside the four-argument `AddPostgresOpenIddictStores` overload, which has no caller in the repository; it still changes because it still compiles, and the pull request says so rather than leaving a reviewer to report it as a phantom. Deleting that overload is out of scope for this story.
- **`src/config/Dockerfile`'s build stage gains the new project, and it gains it in this story rather than the next one.** That stage builds from an explicit per-project `COPY` list: each project's `.csproj` and `packages.lock.json` ahead of `dotnet restore --locked-mode` (`:14-20`, `:22`), then each project's sources (`:24-30`). `src/config/contracts/EdFi.DmsConfigurationService.Secrets` is a new project outside that list, and the frontend and four backends reference it from this story onward, so the image cannot restore without it. Assigning it here rather than to the CMS host-integration story follows the rule the plugin spine set for the same situation: the build-stage change belongs to the story that creates the tree, so that no merge order leaves a project reference pointing at something the image build cannot reach. The plugin tree's own copies are the host-integration story's, because that is the story that creates that reference.
- `Backend`, `Backend.OpenIddict`, `Backend.Postgresql`, `Backend.Mssql`, and `Config.Frontend` take a `ProjectReference` on the new project, and every one of their `packages.lock.json` files is regenerated. `--locked-mode` does not catch a missing project entry, so a test asserts the new project is present in `src/config/EdFi.DmsConfigurationService.sln`; a project present in one solution and missing from another is a known failure mode in this repository.
- The XML documentation on both contracts states the implementer obligations the host cannot enforce: that each is a replace-cardinality contract registered with a plain `Add` and never a `TryAdd`, because a contract with one claimant has nothing to try and the recording wrapper cannot see a candidate a `TryAdd` declined; that both must be registered as singletons; and that a resolver takes its tenant as an argument because a plugin instance outlives every tenant. The documentation ships inside the nupkg and is what an implementer reads in their IDE, so it is the criterion rather than a note.
- **`IdentitySettings:ClientSecretHashingIterations` becomes the live key.** `Backend.OpenIddict/Extensions/OpenIddictServiceCollectionExtensions.cs:26` is the repository's only `services.Configure<IdentityOptions>`; it assigns thirteen properties and the iteration count is not among them, so `ClientSecretHasher` always reads the model default of `210000` (`Backend.OpenIddict/Models/IdentityOptions.cs:73`, read at `Backend.OpenIddict/Services/ClientSecretHasher.cs:38` and `:97`). The binder gains the assignment, reading `IdentitySettings:ClientSecretHashingIterations` with a default of `210000`, and the model property is renamed from `HashingIterations` to `ClientSecretHashingIterations` so that the key, the property, and the setting an operator reads carry one name.
- `eng/docker-compose/published-config.yml:54` and `eng/docker-compose/local-config.yml:58` change from `IdentitySettings__HashingIterations` to `IdentitySettings__ClientSecretHashingIterations`, keeping the `DMS_CONFIG_IDENTITY_HASHING_ITERATIONS` variable and its default. Those two lines are the only places in the repository that set the dead key.
- `IdentitySettings:HashingIterations` remains unbound, and a test asserts it: setting it alone leaves the hasher at the default. That assertion exists so that nobody later makes both keys live, which would put an operator who set both in the position of having to know which wins.
- Three tests pin the repair. Setting `IdentitySettings:ClientSecretHashingIterations` to a non-default value reaches `ClientSecretHasher`, which is the assertion that fails on main today. The value `Config.Frontend/appsettings.json:45` ships equals the model default, which is what makes this change behavior-neutral for every deployment that does not override it, and it is asserted rather than left as prose. A secret hashed at one iteration count and verified at another fails verification, which pins the pre-existing stored-format property: the format is a version byte, a salt length, the salt, and the subkey (`ClientSecretHasher.cs:52-55`), and verification derives with the configured count rather than with one read back from the stored value (`:97`).
- `docs/CONFIGURATION.md` gains `IdentitySettings:ClientSecretHashingIterations` with its default and with the consequence stated plainly: raising it invalidates every client secret already hashed at the old count, and the remedy is to re-issue them.
- A per-pull-request lane packs `EdFi.Api.Secrets` into a local folder feed and compiles a scratch consumer against the produced nupkg, following `eng/verification/CustomValidationConsumer/`. The consumer implements both contracts, which proves the package carries everything an implementer needs and nothing it should not, and the lane asserts the packed assembly's `AssemblyVersion` equals the package version.
- `.github/workflows/on-config-pullrequest.yml` runs that lane, and `src/config/contracts/*` reaches its relevance filter through the existing `src/config/*` case at `:124`.
- No behavior changes for a deployment that sets neither iteration key, asserted by the existing CMS unit and end-to-end suites passing unchanged.
- `dotnet build --no-restore src/config/EdFi.DmsConfigurationService.sln` and `dotnet test src/config/EdFi.DmsConfigurationService.sln` pass.
