# Story: Add Phase A Configuration Contribution to the Plugin Contract

## Description

The plugin spine designed two composition phases and built one.
`EdFiApiPlugin` ships with `Name` and `ContributeServices` and no Phase A member (`src/plugins/EdFi.Api.Plugins/EdFiApiPlugin.cs`), because the spine withheld a hook the host would not call: a virtual the host never invokes is a hook a plugin can override to no effect, which is the silent no-op that design refuses everywhere.

This story is the first consumer arriving.
It adds `ContributeConfiguration` to the contract, invokes it from the loader, places what a plugin contributed where the design says it must sit, guards the contribution as additive, and carries the Phase A rows of the spine's test plan, per:

- `reference/design/plugins-DMS-1462/design.md` ("### The Two Composition Phases" for the hook shape, the invocation point, the placement rule, and the additive `Sources` guard; "### Contract Cardinality" for the `Contribute` row; "### The Plugin Contract" for the additive-only policy and the version move; "## Testing Strategy" for the Phase A cases)
- `reference/design/secrets-DMS-1503/design.md` ("### Phase A: The Process-Global Secrets" for the values it serves and the keys it cannot)

Every decision here was taken by the spine and is implemented rather than revisited.
What this story adds that the spine did not write down is the list of values Phase A serves, which the secrets design enumerates as eight named keys plus an `OtlpLogging:Headers` section in each host, and it matters to one acceptance criterion: the integration proof supplies a real one of them rather than an invented key.

This is the first exercise of the contract's additive-only policy, which is the property the base-class shape was chosen for.
A plugin compiled against `EdFi.Api.Plugins` 1.0.0 must load and run on a host carrying 1.1.0 without being rebuilt, and that is asserted rather than assumed.

**Citation convention.** Unprefixed paths are relative to the repository root, and `Program.cs` and `Infrastructure/` are relative to `src/dms/frontend/EdFi.DataManagementService.Frontend.AspNetCore/`, following the plugin spine's drafts.

Nothing in CMS is touched.
The CMS half of Phase A arrives with CMS host integration, which depends on this story.

## Acceptance Criteria

- `EdFiApiPlugin` gains `public virtual void ContributeConfiguration(IConfigurationBuilder configurationBuilder, IConfiguration bootstrapConfiguration)` with an empty body and XML documentation stating what each parameter is: the builder the plugin adds sources to, and the operator configuration already layered at that moment, which the plugin reads to find its own vault address. The signature is exactly the spine's, with both parameters, and is not reduced to one. The documentation does **not** call the parameter read-only: `IConfiguration` exposes a settable indexer, so a write through it is possible, and the merged contract already says exactly that of the sibling parameter `ContributeServices` receives. It is documented the way the spine documents mutation of a pre-existing source object, as a trust assumption the additive `Sources` guard does not cover, and `PLUGINS.md` states both in one place.
- `src/plugins/Directory.Build.props` moves the contract's version from `1.0.0` to `1.1.0`. It is a minor bump because the change is a new virtual with a no-op body, which is the only evolution the additive-only policy allows, and the version must move because the loader's skew preflight compares exactly this value.
- `LoadedPlugins` gains `public void ContributeConfiguration(ConfigurationManager configuration)`, taking one argument where the contract's hook takes two, the way `LoadedPlugins.ContributeServices` already differs from the contract's own. `ConfigurationManager` implements both `IConfigurationBuilder` and `IConfiguration`, so the aggregate passes it as the `configurationBuilder` and as the `bootstrapConfiguration` of each plugin's hook. Hooks run in allowlist order, one at a time.
- The loader writes `invoking ContributeConfiguration on <plugin>` to its diagnostics channel **before** each hook runs, matching what `LoadedPlugins.ContributeServices` already does and for the same reason: a plugin blocking inside a hook hangs startup with no timeout, so the last line on the channel has to name the plugin that was entered. A test asserts the announcement is already on the channel when a fixture hook throws.
- **The additive `Sources` guard.** The loader snapshots `configurationBuilder.Sources` before each Phase A call and compares it after. Any pre-existing source removed or moved is fatal, naming the plugin. Adding is the only permitted operation. The guard detects removal and reordering of the source objects it snapshotted and nothing else: mutation of a pre-existing source object is undetectable at this seam, is a documented trust assumption rather than a control, and the XML documentation and `PLUGINS.md` say so rather than implying coverage the guard does not have.
- **Placement.** After each hook returns and the guard has passed, the loader moves the sources that plugin appended to sit immediately below the **last** `EnvironmentVariablesConfigurationSource` present when Phase A began, preserving their relative order. "Last environment variable source" is the rule rather than an index, because the count varies with the environment: measured on `net10.0`, `WebApplication.CreateBuilder(args)` installs ten sources when started with no arguments and twelve when started with some, and the unprefixed environment source is `[8]` in one and `[9]` in the other. Among plugin sources later wins; all of them sit above every JSON source; none sits above the operator's environment or command-line source, because those are never moved. The loader adds no source of its own.
- A unit test over a `ConfigurationManager` carrying the same source list the host installs, with the placement step applied, asserts all three precedence outcomes: a key set only by the plugin resolves to the plugin's value even when `appsettings.json` carries an empty string for it; a key also set in the environment resolves to the environment's; a key also passed on the command line resolves to the command line's. The command-line assertion is a unit test and not an integration one, because `WebApplicationFactory` starts the host through its own entry point and a test cannot add configuration keys to the arguments it passes, and because the stock container installs no command-line source at all (`src/dms/run.sh:118`).
- A Phase A plugin that removes a pre-existing configuration source is fatal and named; one that reorders a pre-existing source is fatal and named; one that only appends is unaffected. Each is its own case.
- One test asserts a Phase A plugin cannot influence `Plugins:Allowed`. The allowlist was consumed to decide what loads before Phase A ran, so no addition, removal, or reordering can reach it. This is the security property from the spine's trust model stated as a test rather than as a convention.
- **The `Contribute`-only exemption in the no-contract-registered check.** A plugin whose `ContributeServices` registers only its own types and whose `ContributeConfiguration` adds nothing stays fatal as contributing no plugin contract; the same plugin with one Phase A source added is not. Both cases are asserted. The check reads the Phase A record rather than inferring it, so a plugin that added a source and then had it removed by a later plugin is not affected: Phase A contribution is recorded historically, like the replace-cardinality claims and unlike the surviving-registration rule.
- `Program.cs` invokes `loadedPlugins.ContributeConfiguration(builder.Configuration)` inside the existing `DmsStartupPhases.LoadPlugins` bootstrap phase, immediately after `PluginLoader.Load` returns and before the `ConfigureServices` phase begins. That placement is load-bearing and is stated as a criterion rather than left to the diff: `AddServices` calls `ConfigureLogging()` on its first line (`Infrastructure/WebApplicationBuilderExtensions.cs:36`), which reads the `Serilog` section, and it is the first read of a plugin-resolvable configuration value. That citation is `:36` and not the `:38` the merged spine document carries: the file has moved since that document was written, and this story corrects the reference rather than repeating it.
- `AppSettings:StartupStatusFilePath` is documented as the one key Phase A cannot supply, in `docs/CONFIGURATION.md`. `Program.cs:30-33` reads it to construct the bootstrap status signal before plugins load at all, and it must, because that signal is how a loader fatal is reported.
- **Binary compatibility across the version move is proven by the assets that already prove it, and this story keeps them honest.** The merged suite runs a plugin compiled against the production contract in a child host whose contract assembly has been swapped for a synthetic newer one (`PluginContractCompatibilityTests.cs`, `Given_a_plugin_built_against_the_older_contract_on_a_newer_host`; the plugin is `Fixtures/Plugins/Acme.OldContract/`, the synthetic contract is `Fixtures/Contracts/Contract_1_1/EdFi.Api.Plugins.v1_1.csproj`, and the runner is `Fixtures/Hosts/PluginHostRunner/`). That fixture declares `AssemblyVersion` `1.1.0` and adds one no-op virtual, `DescribeCapabilities`, and two reflection tests assert that the production surface is a subset of the fixture's (`It_keeps_every_public_member_the_production_contract_declares`, `PluginContractCompatibilityTests.cs:326-338`) and that the fixture adds **exactly one** member (`It_adds_exactly_one_no_op_virtual`, `:340-358`). Moving production to 1.1.0 breaks the version distinction, because two assemblies would then carry `1.1.0`, and it breaks the **subset** assertion, because the fixture would not carry `ContributeConfiguration`. It does **not** break the exactly-one assertion, which computes `fixture.Except(production)` (`:345`) and therefore never sees a production-only member; saying otherwise would send an implementer to the wrong test. So this story moves the fixture to `1.2.0`, copies `ContributeConfiguration` into its surface so production stays a subset, and leaves `DescribeCapabilities` as the one added virtual. Both tests are then unchanged in intent and assert the same properties one version higher. The fixture's csproj comment already explains why it is a copied surface rather than a project reference, and that reasoning is unchanged.
- The `Acme.OldContract` plugin overrides only `ContributeServices` and is asserted to run on the newer host with `ContributeConfiguration` taking the base no-op body, which is the property the added member has to have. `Acme.NewerContract` is untouched: it is built against `Acme.Contract2`, a separate synthetic contract, so the production version move does not reach it.
- The reverse direction stays fatal and its message is unchanged: a plugin whose entry assembly references `EdFi.Api.Plugins` 1.1.0 on a host carrying 1.0.0 is refused by the skew preflight with both versions named, from reading the assembly's references rather than from loading a type.
- An integration test boots `WebApplicationFactory<Program>` with a fixture plugin whose `ContributeConfiguration` adds an in-memory source supplying `ConfigurationServiceSettings:EncryptionKey`, and asserts the value DMS resolves is the plugin's rather than the empty string `appsettings.json` ships at that key. A real key is used rather than an invented one because the empty-string default is exactly the shadowing case the placement rule exists to prevent, and an invented key would pass under a placement that the shipped configuration would defeat.
- A second integration case asserts a key supplied both by a Phase A source and by an environment variable resolves to the environment value.
- A third asserts the loader added no source of its own: the set of non-plugin sources in `Sources` after Phase A is the set that was there before it.
- `docs/CONFIGURATION.md` states the resulting precedence order - environment variables, then command-line arguments, then plugin sources in allowlist order, then `appsettings.json` and the other JSON sources - and states that DMS's own `AddEnvironmentVariables()` call at `Infrastructure/WebApplicationBuilderExtensions.cs:44` is why the environment sits above the command line rather than below it. As above, the spine's `:46` has drifted by two lines and this story cites the current one.
- `src/plugins/EdFi.Api.Plugins/PLUGINS.md` gains the Phase A implementer rules: what the two parameters are, that contribution must be additive, that the guard catches removal and reordering but not mutation of a source object the plugin did not add, and that allowlist order is contractual for Phase A because later plugin sources win.
- `dotnet test src/plugins/EdFi.Api.Plugins.Hosting.Tests.Unit/EdFi.Api.Plugins.Hosting.Tests.Unit.csproj` and `dotnet test src/dms/tests/EdFi.DataManagementService.Tests.Integration` pass.
