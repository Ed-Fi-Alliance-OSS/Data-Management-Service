# Story: Resolve Secret References in Stored Connection Strings

## Description

This is the capability.
Everything before it builds the seam a plugin arrives through; this story is where an operator's database password stops being stored in the Configuration Service, per:

- `reference/design/secrets-DMS-1503/design.md` ("### The Secret Reference: Runtime-Data Secrets", "### Where Resolution Happens", "### Freshness, Caching, and the Tenant Set", "### Failure Semantics")

A stored connection string may carry `${secret:<name>}` tokens.
CMS stores the text exactly as any other connection string, encrypted, through the unchanged write path and validator.
When CMS reads the row, it decrypts, substitutes each token with what the plugin-supplied `ISecretResolver` returns, re-encrypts, and returns Base64.
DMS receives the shape it receives today and is not touched by this story at all.

The design records the measured constraints this story implements: the token survives the engine validators as a value, substitution must go through the provider's builder (textual replacement silently corrupts a leading-space password), and the builder must come from the same object that validated the string.

## Acceptance Criteria

- **The token grammar.** `${secret:<name>}`, `<name>` one or more of `A-Z a-z 0-9 _ - . / : @ +`, matched ordinal and case-sensitive; a `${` not followed by a well-formed token is left verbatim; no escape sequence; multiple tokens per value resolve independently. Asserted by a table with one case per permitted and per excluded punctuation character, plus empty name, embedded space, embedded brace, and unterminated `${secret:`, each left verbatim and failing nothing.
- **One rule, twelve call sites, every one materialized.** A host-owned service in `Backend/Services/` is awaited at all twelve. The eight collection sites are lazy `Select` projections returned inside `Success(...)` today, running during serialization outside the repository's `try/catch`, and a synchronous lambda cannot await `ResolveAsync`; each becomes an eager per-row awaited projection so `Success(...)` carries a completed list, and the four single-row `Get` sites gain an `await` in place. The sites: `DataStoreRepository.QueryDataStore` (PG/MSSQL `:193`), `GetDataStore` (`:265` both), `DataStoreDerivativeRepository.QueryDataStoreDerivative` (`:154`/`:149`), `GetDataStoreDerivative` (`:197`/`:192`), `GetDataStoreDerivativesByDataStore` (`:365`/`:355`), `GetDataStoreDerivativesByDataStoreIds` (`:406`/`:396`).
- A test drives a failing resolver through each collection method and asserts the documented failure result rather than an exception escaping during response enumeration, which is the assertion a lazy projection fails.
- A source-scan test asserts no `Convert.ToBase64String` over a connection string column remains in `Backend.Postgresql` or `Backend.Mssql` repository files outside the seam, so a thirteenth site fails rather than silently skipping resolution.
- **Every non-null row is decrypted, token-free ones included**, because token-freeness is unknowable in cipher text. A null column returns null with no decrypt; a token-free row returns the Base64 of its input bytes unchanged, byte-identical to main's response and with no resolver call, asserted against a value encrypted before the change.
- A decryption that throws fails the read with its own message, distinct from every resolution failure, on the parent path and both derivative paths, mentioning neither secrets nor resolvers. (Such a value reaches `Decrypt` for the first time under this design; the criterion is scoped to what unauthenticated AES-CBC can detect.)
- Resolution uses the existing `IConnectionStringEncryptionService` for both directions (`Backend/Services/IConnectionStringEncryptionService.cs:10-11`); `Decrypt` gains its first production caller and no new cryptography is written.
- **Substitution goes through the configured engine's `DbConnectionStringBuilder`, never textual replacement**, assigning each affected keyword through the builder's indexer and re-emitting `builder.ConnectionString`. The builder comes from the validator's own object: the abstract validator additionally implements a new one-member `IDataStoreConnectionStringBuilderSource` in `Backend/Services/` exposing its protected `CreateBuilder` parse (`Backend/Services/DataStoreConnectionStringValidator.cs:83`), and `AddDataStoreConnectionStringValidator` (`Config.Frontend/Infrastructure/WebApplicationBuilderExtensions.cs:215-231`) registers the one engine validator under both interfaces, second forwarded to first. A test resolves both interfaces and asserts the same instance. The row's `Provider` column is not read: derivative rows carry no provider at all (`DataModel/Model/DataStoreDerivative/DataStoreDerivativeResponse.cs:11-31`).
- The design's measured substitution table is a test, one case per value per engine (`simple`, `has"quote`, `has=equals`, `has'apos`, `has;semi`, `a;b=c`, and a leading-space value), with a companion probe test recording what textual substitution does with the same values, so a rewrite that reintroduces textual replacement fails here.
- Re-emission normalizes keyword naming, casing, ordering, and quoting (both engines canonicalize keyword names; see design.md, "The Secret Reference"); a test records the returned text is the builder's rendering. The re-encryption assertion round-trips through CMS's own `IConnectionStringEncryptionService.Decrypt`, never DMS's `ConnectionStringDecryptionService`, because no `src/config/` project references any `EdFi.DataManagementService.*` assembly and this story must not create the first.
- The resolver receives the token name and the tenant: `SecretReference.Tenant` is null under `TenantContext.NotMultitenant` and `TenantContext.Multitenant.TenantName` otherwise, asserted in both modes.
- Derivative connection strings resolve exactly once: a data store read with a tokenized derivative resolves that token once, not twice (the parent nests items the derivative repository already projected, `Backend.Postgresql/Repositories/DataStoreRepository.cs:164-182`).
- **Lifetimes.** The seam is transient like the repositories that call it, never a singleton, because it reads the scoped `ITenantContextProvider` (`Config.Frontend/Infrastructure/WebApplicationBuilderExtensions.cs:126`; the scope-validation warning sits in the comment at `:116-119`). The cache behind it is a singleton taking the tenant as an argument; `ISecretResolver` is a singleton. A test boots the host in the Development environment so a lifetime regression fails scope validation in a test.
- **Single-flight cache.** Concurrent misses on one key collapse to one resolver call whose result every waiter takes; a second key is not serialized behind the first; a failing call fails every waiter and caches nothing.
- **Host-owned cache** keyed `(tenant, name)` with absolute expiration `SecretsSettings:CacheExpirationSeconds`, default `300`; `0` disables caching. Tests: two reads inside the window call once, a read after calls again, two tenants are two entries, `0` calls every read; time via an injected `TimeProvider` taken as an optional constructor parameter defaulting to `TimeProvider.System` (the `TokenCleanupService` pattern, `Backend.OpenIddict/Services/TokenCleanupService.cs:22`), since CMS registers one only in the self-contained branch (`:384`).
- No invalidation from tenant administration: a new tenant's first read populates, and a removed tenant's entries are unreachable and expire; the second case is driven directly against the cache, since tenant administration exposes no removal today (`Config.Frontend/Modules/TenantModule.cs:21-23`).
- **Failure semantics, one test each**: a token with no resolver registered fails the read naming the data store and token and the missing contract; a resolver that throws, cancels, returns null, or returns empty fails the read with the exception type (never its message) in the log; the two messages are distinct; no response ever carries a decrypted value still containing `${secret:`.
- **The naming happens in the log line, not the response.** A resolution failure surfaces as the existing generic failure shape (`FailureResults.Unknown`, `Config.Frontend/Modules/DataStoreModule.cs:66-71`); a test correlates the log line by trace identifier and asserts it carries the data store id, tenant, and token name and never the resolved value.
- **A derivative token that cannot be resolved while read as part of a data store yields a null connection string for that derivative and a successful parent read**, matching DMS's own handling of an undecryptable derivative (`src/dms/core/EdFi.DataManagementService.Core/Configuration/ConfigurationServiceDataStoreProvider.cs:576`, `:588-612`), with a log naming parent, tenant, derivative type, and token. Covered on the collection and single-row paths, which reach derivatives through different arms. A parent token still fails the read, and one test asserts the asymmetry directly.
- **The standalone derivative endpoints fail instead** (`GET /v3/dataStoreDerivatives/` and `/{id}`, `Config.Frontend/Modules/DataStoreDerivativeModule.cs:21-22`), because there the derivative is the requested resource. The seam takes an argument saying whether the row is read as a resource or as part of one; two tests assert the same unresolvable token that returns null through a data store fails through each standalone endpoint.
- Pre-existing derivative-lookup-failure behavior is untouched: the arms mapping a failed lookup to an empty collection still behave as today, asserted.
- **The resolve timeout is a race the host owns**: `SecretsSettings:ResolveTimeoutSeconds`, default `10`; the seam invokes the resolver on a task it owns, races that (not the returned `ValueTask`), and passes a cancellation token. Load-bearing tests: a resolver returning an incomplete `ValueTask` ignoring the token fails within the window; one blocking before returning its `ValueTask` fails the same way; a cooperative resolver's token is cancelled; one returning just inside the window succeeds.
- A vault outage is a read failure and never a startup failure: CMS starts with an unreachable store, and a read of a token-free collection succeeds.
- **Blast radius asserted**: two data stores in one tenant, one with a failing parent token, and the collection read fails (DMS calls `EnsureSuccessStatusCode()` on that fetch, `ConfigurationServiceDataStoreProvider.cs:465`, `:487`); the companion case with a failing derivative token succeeds, which is the containment the derivative rule buys.
- `SecretsSettings` is added to `Config.Frontend/appsettings.json` with both keys, bound and validated like its neighbors, documented in `docs/CONFIGURATION.md`, with `DMS_CONFIG_*` overrides in both compose files.
- Integration through the real endpoint: a data store inserted through `/v3/dataStores/` with a token in its `Password` passes the real validator and reads back to the resolved connection string; the same row with a failing resolver produces the documented failure.
- **The end-to-end proof**: a fixture secrets plugin published `--no-self-contained`, delivered by the Recipe 1 mount through `plugins-config.yml`, resolver backed by a harness-written file; CMS and DMS up together, a data store created with a token password, and DMS serves a resource out of it. A second run rotates the file and asserts the new value takes effect after the configured expiration and not before, measured against CMS's own endpoint so DMS's cache does not fold into the number.
- `dotnet test src/config/EdFi.DmsConfigurationService.sln` and `build-config.ps1 E2ETest` pass.
