# Story: Resolve Secret References in Stored Connection Strings

## Description

This is the capability.
Everything before it builds the seam a plugin arrives through; this story is where an operator's database password stops being stored in the Configuration Service, per:

- `reference/design/secrets-DMS-1503/design.md` ("### The Secret Reference: Runtime-Data Secrets", "### Where Resolution Happens", "### Freshness, Caching, and the Tenant Set", "### Failure Semantics")

A stored connection string may carry `${secret:<name>}` tokens.
CMS stores the text exactly as it stores any other connection string, encrypted under `DatabaseSettings:EncryptionKey`, in the same column, through the same write path with no change to validation.
When CMS reads the row, it decrypts, substitutes each token with what the plugin-supplied `ISecretResolver` returns, re-encrypts, and returns Base64.
DMS receives the shape it receives today and is not touched by this story at all.

The token sits inside a connection string value rather than replacing the whole value, and that is a measured constraint rather than a style choice.
Every submitted connection string is parsed by the configured engine's own `DbConnectionStringBuilder` and rejected if the provider cannot read it (`Backend/Services/DataStoreConnectionStringValidator.cs:56-75`).
Measured on `net10.0` against `Npgsql` 8.0.4 and `Microsoft.Data.SqlClient` 6.1.4: `vault://prod/dms/ds-2026` throws `ArgumentException: Format of the initialization string does not conform to specification starting at index 0.` on both, while `Password=${secret:prod/dms/ds-2026}` parses on both and the builder hands the token back through the `Password` key unchanged.
So the design needs no change to the validator, and the story carries a test that fails if a future change to it makes a token unsubmittable.

Twelve call sites project a stored connection string into a response, six methods present once per engine.
One host-owned rule serves all twelve, in `Backend/Services/` beside `ConnectionStringWrite` and `ConnectionStringCipherText`, which exist there for exactly the same reason and say so in their own summaries.

## Acceptance Criteria

- **The token grammar.** `${secret:<name>}`, where `<name>` is one or more characters from `A-Z`, `a-z`, `0-9`, `_`, `-`, `.`, `/`, `:`, `@`, and `+`. Matching is ordinal and case-sensitive. A `${` not followed by `secret:` and a well-formed name closed by `}` is not a token and the text is left verbatim, which is what keeps a password containing `${` from being reinterpreted by an upgrade. There is no escape sequence. A value may carry more than one token and each resolves independently. The grammar is asserted by a table with one case per permitted punctuation character and one per excluded one, plus cases for an empty name, a name containing a space, a name containing a brace, and an unterminated `${secret:`, each asserted to be left verbatim and to fail nothing.
- **One rule, twelve call sites, in two shapes.** A host-owned service in `Backend/Services/` replaces the projection expression at all twelve. Eight read `row.ConnectionString` and four, the single-row `Get` methods on both resources and both engines, read `result.Value.ConnectionString`; the seam takes the bytes either way, so the two shapes are a call-site difference and not a rule difference. In `Backend.Postgresql/Repositories/DataStoreRepository.cs` and `Backend.Mssql/Repositories/DataStoreRepository.cs`: `QueryDataStore` (`:193` in both) and `GetDataStore` (`:265` in both). In `Backend.Postgresql/Repositories/DataStoreDerivativeRepository.cs` and `Backend.Mssql/Repositories/DataStoreDerivativeRepository.cs`: `QueryDataStoreDerivative` (`:154`, `:149`), `GetDataStoreDerivative` (`:197`, `:192`), `GetDataStoreDerivativesByDataStore` (`:365`, `:355`), and `GetDataStoreDerivativesByDataStoreIds` (`:406`, `:396`). The engine-specific repositories carry no policy of their own, following `Backend/Services/ConnectionStringWrite.cs`, which exists so that "the four update paths cannot drift apart".
- A test asserts the count rather than a reviewer doing it: no `Convert.ToBase64String` over a connection string column remains in `Backend.Postgresql` or `Backend.Mssql` outside the seam. It is a **source scan** over those two projects' repository files, because `System.Reflection` exposes metadata and not call sites, and asserting an absent call through metadata would mean reading IL bodies and walking compiler-generated async state machines to do what a text search does. Twelve identical lines are exactly the shape a thirteenth gets added to unnoticed, and a test over the assemblies is what makes a thirteenth fail rather than silently skip resolution.
- **A decryption that throws fails the read with its own message**, distinct from every resolution failure, on the parent path and on both derivative paths. Such a value reaches `Decrypt` for the first time under this design, because a read today Base64-encodes the bytes without looking at them. The criterion is scoped to what the format can actually detect: AES-CBC here is unauthenticated, so a value that is too short or fails to decrypt is caught and altered cipher text that still decrypts is not. The message mentions neither secrets nor resolvers.
- **Every non-null row is decrypted, including token-free ones**, because a stored value is cipher text and token-freeness is not knowable without decrypting. A null column is returned as null with no decrypt. A non-null token-free row is decrypted, found to carry no token, and returned as the Base64 of the bytes it was given, unchanged and with no resolver call: the response is byte-identical to main's, asserted against a value encrypted before the change. The "no decrypt for token-free rows" shortcut is explicitly **not** taken, and the criterion says why, because it cannot coexist with the no-resolver failure below: a row never decrypted is a row whose token is never seen, and `${secret:...}` would reach DMS as a password.
- **Resolution.** For a row that carries at least one token, the seam decrypts, substitutes, re-encrypts, and returns Base64. Both directions come from the existing `IConnectionStringEncryptionService`, which already declares `Encrypt` and `Decrypt` (`Backend/Services/IConnectionStringEncryptionService.cs:10-11`); no new cryptography is written, and `Decrypt` gains its first production caller, having been exercised only by tests until now.
- **Substitution goes through the provider's `DbConnectionStringBuilder`, never through textual replacement, and this is the criterion the story most needs to get right.** The seam parses the decrypted text with the builder for the **configured** datastore engine, the same choice `AddDataStoreConnectionStringValidator` makes when it decides which engine validates a submitted connection string (`Config.Frontend/Infrastructure/WebApplicationBuilderExtensions.cs:215-231`), assigns each affected keyword's resolved value through the builder's indexer, and re-emits `builder.ConnectionString`. It does **not** read the row's `Provider` column, and the criterion says why rather than leaving it to look like an oversight: `DataStoreDerivativeResponse` carries no provider at all (`DataModel/Model/DataStoreDerivative/DataStoreDerivativeResponse.cs:11-31`) and the derivative queries select none, so eight of the twelve sites have no row-level provider to read, and threading the parent's through would be a change to four queries and a DTO on behalf of a per-data-store engine this deployment model does not have. Measured on `net10.0` against `Npgsql` 8.0.4 and `Microsoft.Data.SqlClient` 6.1.4, textual substitution of a value with a **leading space** silently yields the value without it on both engines, with no error at any layer, which is a wrong password handed to a driver; `has;semi` throws on both; and `a;b=c` throws `Keyword not supported: 'b'` on SQL Server, having parsed the tail as a keyword. All of them round-trip exactly through the builder.
- The measured table is a test, one case per value per engine: `simple`, `has"quote`, `has=equals`, `has'apos`, `has;semi`, `a;b=c`, and a value with a leading space. A companion probe test records what textual substitution does with the same values, so the decision is pinned by measurement and a future rewrite that reintroduces textual replacement fails here rather than in a deployment. A separate case asserts both parent and derivative sites use the configured engine's builder, and that no code path reads `DataStoreResponse.Provider` for this purpose.
- Re-emitting normalizes keyword casing, ordering, and quoting, and that is accepted and asserted rather than discovered: a test records that the returned text is the builder's rendering rather than the operator's, and the story notes in the pull request that DMS keys connection-pool ownership on this value verbatim (`src/dms/core/EdFi.DataManagementService.Core/Configuration/DataStoreOwnership.cs`), so the normalized form is what that key holds from this story onward. The re-encryption assertion is a round trip through CMS's own `IConnectionStringEncryptionService.Decrypt` rather than a comparison against a fixed string. It is deliberately not DMS's `ConnectionStringDecryptionService`: no project under `src/config/` references any `EdFi.DataManagementService.*` assembly, and this story must not create the first such reference, because `ConnectionStringEncryptionService.Encrypt` generates a fresh initialization vector per call (`Backend/Services/ConnectionStringEncryptionService.cs:19-38`) and a fixed expectation would pin a value that is deliberately not stable.
- The resolver receives the token name and the tenant. `SecretReference.Tenant` is null under `TenantContext.NotMultitenant` and carries `TenantContext.Multitenant.TenantName` otherwise (`Backend/Services/TenantContext.cs`), asserted in both modes. The tenant comes from the request's resolved context rather than from the row's `TenantId`, because the contract takes a name and the context is where the name is.
- **Derivative connection strings resolve on the same rule and exactly once.** `DataStoreRepository` nests derivative items the derivative repository already projected (`Backend.Postgresql/Repositories/DataStoreRepository.cs:164-182`), so a test asserts a data store read with a tokenized derivative resolves that token once and not twice.
- **Lifetimes are stated, because the obvious choice fails at startup.** The seam is **not a singleton**, because it reads the request's tenant from `ITenantContextProvider`, which is registered scoped (`Config.Frontend/Infrastructure/WebApplicationBuilderExtensions.cs:126`); a singleton depending on it "fails DI scope validation at startup in the Development environment", which that file already warns about four lines above the registration (`:116-119`). Beyond that it takes the lifetime of the repositories that call it, which is **transient** in both engines (`:177-181`, `Backend.Mssql/MssqlServiceExtensions.cs:29`, `:31`), and `DataStoreRepository` is already a transient taking that scoped provider by constructor (`Backend.Postgresql/Repositories/DataStoreRepository.cs:27`), so this needs no new pattern. The cache behind it is a **singleton** holding no scoped dependency and receiving the tenant as an argument. `ISecretResolver` is a **singleton**. A test boots the host in the Development environment, which is where scope validation runs, so a lifetime regression fails a test rather than a developer's first run.
- **Concurrent misses on one key collapse into one resolver call.** Waiters take that call's result; a second key is not serialized behind the first; and a failing call fails every waiter on that key and caches nothing. Without this the design's bound is on distinct keys per window rather than on calls, because a cold start or an expiry under load would call the resolver once per in-flight request. Tests drive it with a resolver that blocks until released.
- **The host owns the cache.** Keyed by the pair `(tenant, name)`, absolute expiration from `SecretsSettings:CacheExpirationSeconds`, default `300`. Absolute rather than sliding, because the question an operator asks about a rotated secret is how long until it takes effect and only an absolute window answers with a number. Tests: two reads inside the window call the resolver once; a read after it calls again; two tenants asking for the same name are two entries and two calls; `0` disables caching and calls on every read. Time is controlled through an injected `TimeProvider` so no test sleeps. CMS registers one only inside the self-contained identity branch (`Config.Frontend/Infrastructure/WebApplicationBuilderExtensions.cs:384`), so the cache takes it as an optional constructor parameter defaulting to `TimeProvider.System`, which is what `TokenCleanupService` already does (`Backend.OpenIddict/Services/TokenCleanupService.cs:22`).
- The cache is not invalidated from tenant administration, and a test states why by asserting the two cases: a tenant added has no entries, so its first read populates and nothing was stale; entries for a tenant no longer in use are unreachable by any other tenant's lookup and expire on their own. That second case is driven directly against the cache rather than through tenant administration, which exposes a create and two reads and no removal today (`Config.Frontend/Modules/TenantModule.cs:21-23`).
- **Failure semantics, one test each, and every row below is about a token that fails on a path where failing is the rule**: a parent's, or a derivative's read through `/v3/dataStoreDerivatives/`. A token present with no `ISecretResolver` registered fails the read, naming the data store and the token and saying that a secret reference needs a plugin registering that contract. A resolver that throws, one that cancels, one that returns null, and one that returns an empty string each fail the read, naming the data store and the token, The resolver's exception is **not** carried outward as an inner exception: the repositories log a caught exception with its message (`Backend.Postgresql/Repositories/DataStoreRepository.cs:202`, `:274`), so the seam logs the exception type itself and raises a failure carrying no plugin-authored text. A test asserts the captured log contains the exception type and not its message. The two messages are distinct, so an operator can tell "no plugin installed" from "the plugin failed". In no case is an unresolved token passed through: a test asserts the response never contains a connection string whose decrypted text still carries `${secret:`.
- **The message that names the data store and the token is the log line, not the response.** A resolution failure reaches `FailureResults.Unknown(httpContext.TraceIdentifier)` (`Config.Frontend/Modules/DataStoreModule.cs:66-71`), a generic 500 with no detail, and this story does not widen it. The single-row handlers match a `FailureNotFound` arm ahead of that one, so this is a claim about resolution failures rather than about every non-success result: that would change a shipped API contract. A test asserts the response is the existing generic shape and that the log line, correlated by the same trace identifier, contains the data store id, the tenant, and the token **name**, and asserted not to contain the resolved value. The resolver's own exception message is never surfaced to an API client, on the same reasoning that already keeps a submitted connection string out of the validator's failure message (`Backend/Services/DataStoreConnectionStringValidator.cs:60-71`).
- **A derivative whose token cannot be resolved is returned as not configured, and the parent read succeeds.** That is DMS's own existing decision for this exact data, taken deliberately and with a comment: an undecryptable derivative connection string is treated as absent and "the parent data store and its remaining derivatives are unaffected" (`src/dms/core/EdFi.DataManagementService.Core/Configuration/ConfigurationServiceDataStoreProvider.cs:576`, `:588-612`). So an unresolvable derivative token yields a null connection string for that derivative, a log line naming the parent, the tenant, the derivative type, and the token, and a successful read. Tests cover it on the collection path and on the single-row path, which reach derivatives through different arms (`Backend.Postgresql/Repositories/DataStoreRepository.cs:164-182` and `:244-255`, and their SQL Server counterparts), so the rule cannot hold on one and not the other. A **parent** token that cannot be resolved still fails the read, and one test asserts the asymmetry directly: a data store with a failing derivative and a resolvable parent returns, and the same data store with a failing parent does not.
- **The standalone derivative endpoints fail the read instead, and that is a second rule rather than an exception to the first.** Four of the twelve sites serve `GET /v3/dataStoreDerivatives/` and `GET /v3/dataStoreDerivatives/{id}` (`Config.Frontend/Modules/DataStoreDerivativeModule.cs:21-22`), where the derivative is the requested resource and a `200` with a null connection string cannot be told apart from one that was never configured. The seam takes an argument saying whether the row is being read as a resource or as part of one, and that argument is the only difference between the two behaviours. Two tests assert that the same unresolvable token which returns null through a data store fails through each of those two endpoints; a seam that ignored the argument would pass every nested test and fail exactly these.
- This story changes **no** pre-existing derivative-failure behaviour. The arms that map a failed derivative *lookup* to an empty collection are untouched, and a test asserts they still behave as they do today, because a lookup failure and a resolution failure are different things and only the second is this design's.
- **The resolve timeout is the host's, and it is a race rather than a request.** `SecretsSettings:ResolveTimeoutSeconds`, default `10`. The seam invokes the resolver on a task it owns and races **that** against the deadline, rather than racing the returned `ValueTask`, because `ResolveAsync` runs synchronously until it returns and a resolver that blocks before returning would escape the narrower race. It passes a cancellation token beside it, since a token is something a plugin may ignore while the host's promise is that the read terminates. Two tests are load-bearing and fail for different reasons: one resolver returns an incomplete `ValueTask` and ignores the token, and one blocks before returning its `ValueTask` at all, which is the case the narrower race hangs on. Both must fail the read within the window. A third asserts the token a cooperative resolver received was cancelled, a fourth that a resolver returning just inside the window succeeds. The residual is stated in the pull request: the read terminates, and a thread an uncooperative resolver is blocking is not reclaimed until it returns.
- A resolution failure surfaces through the repository's existing unknown-failure result shape, so the endpoint's contract is unchanged, and it is a **read** failure and never a CMS startup failure: a test asserts CMS starts with a resolver whose store is unreachable, and that a read of a collection containing no tokenized row succeeds.
- **The blast radius is asserted rather than left to be discovered.** DMS reads the collection endpoint and calls `EnsureSuccessStatusCode()` (`src/dms/core/EdFi.DataManagementService.Core/Configuration/ConfigurationServiceDataStoreProvider.cs:465`, `:487`), so a failure on one row fails the whole fetch for that tenant. A test places two data stores in one tenant, one whose **parent** token fails and one plain, and asserts the collection read fails rather than returning the healthy row. A companion test places a data store whose **derivative** token fails beside a plain one and asserts the collection read succeeds, which is the containment the derivative rule buys. The story states in the pull request that this is accepted: returning the affected row with a null connection string, or omitting it, are both the silent degradation this design refuses, and a per-row error field is a change to a shipped API contract.
- `SecretsSettings` is added to `Config.Frontend/appsettings.json` with **both** keys, `CacheExpirationSeconds: 300` and `ResolveTimeoutSeconds: 10`, bound and validated like the sections beside it, and documented in `docs/CONFIGURATION.md` with what `0` does for the cache and what the timeout bounds. Both also get `DMS_CONFIG_*` overrides in `eng/docker-compose/published-config.yml` and `local-config.yml`, following every other tunable CMS setting in those files, because the cache expiration is the value the design tells an operator to change while diagnosing a rotation and a setting reachable only by editing `appsettings.json` inside an image is not reachable.
- **An integration test through the real endpoint.** A data store is inserted through `/v3/dataStores/` with a token in its `Password` and read back, asserting the response decrypts to the resolved connection string. The insert is asserted to pass the real validator, which turns the probe above into a regression test: if a future validator change makes a token unsubmittable, this fails rather than the capability silently becoming unreachable. The same row is then read with the resolver failing, asserting the documented failure rather than a pass-through.
- **The end-to-end proof.** A fixture secrets plugin published `--no-self-contained`, delivered by the Recipe 1 mount through `plugins-config.yml`, supplying an `ISecretResolver` backed by a file the harness writes rather than by a real vault. The deployment brings up CMS and DMS together, creates a data store whose password is a token, and asserts DMS serves a resource out of that data store. That is the claim of this design stated as one assertion: the operator's secret reached the database driver without having been written to CMS, to a configuration file, or to an environment variable. It runs against locally built images, for the same reason the spine's equivalent tier does.
- A second end-to-end run rotates the file the fixture resolver reads and asserts the new value takes effect after the configured expiration and not before. The assertion is made against a read of CMS's own `/v3/dataStores/` rather than against a DMS request, because DMS caches data stores for `CacheSettings:DataStoreCacheExpirationSeconds` on top of this cache and a DMS-side assertion would be measuring the sum of the two. The sum is what an operator experiences and it belongs in the documentation; what this test pins is this cache's own window.
- `dotnet test src/config/EdFi.DmsConfigurationService.sln` and `build-config.ps1 E2ETest` pass.
