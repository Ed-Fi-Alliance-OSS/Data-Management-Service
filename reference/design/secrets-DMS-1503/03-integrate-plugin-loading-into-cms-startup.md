# Story: Integrate Plugin Loading into Configuration Service Startup

## Description

The loader is host-agnostic and CMS does not call it.
The spine showed that CMS can have the whole mechanism for very little and deferred it on one ground only: no consuming epic drove it.
This spike is that epic, and this story is where CMS gains both composition phases, per:

- `reference/design/secrets-DMS-1503/design.md` ("### CMS Host Integration", "### Configuration Surface", "### Contract Cardinality" for the two entries the registry declares)
- `reference/design/plugins-DMS-1462/design.md` ("### Applicability to the Configuration Service", "### The Two Composition Phases", "### Startup Failure Semantics", "### Observability")

The integration is the minimal one the spine described and no bootstrap scaffolding is ported.
`Config.Frontend/Program.cs` is a plain minimal-API startup - `CreateBuilder` at `:14`, `AddServices()` at `:16`, `Build()` at `:53`, `RunAsync()` at `:113` - with no `FileStartupStatusSignal`, no `RunBootstrapPhase`, and no `StartupPhaseExecutor`.
None is added.
The loader reports its own outcomes to `Console.Error` and throws, which is fail-loud behavior with nothing to build first, and the plugin audit is a direct call rather than a startup task because CMS has no startup-task machinery and inventing an interface, an executor, and an ordering convention to serve one call site is exactly the scaffolding the spine said not to port.

Both contracts the registry declares exist and neither is called yet.
A resolver registered here resolves nothing until the read seam lands, which is the next story.
That ordering is deliberate: this story proves the mechanism loads, composes, and refuses what it should refuse, against a fixture that exercises both phases, and the story after it proves the capability.

The image gains one assembly in its own publish output and the build stage gains a tree it could not previously reach.
That change is not optional and it is not small in risk: `.github/workflows/on-config-pullrequest.yml` builds `src/config/Dockerfile` in three places, and the frontend's project reference into `src/plugins/` cannot land in a build stage that cannot restore it.
`src/dms/Dockerfile` already solved exactly this and its solution transfers line for line, with the measurements that produced each line recorded in that file's own comments.

## Acceptance Criteria

- `Config.Frontend` takes a `ProjectReference` on `src/plugins/EdFi.Api.Plugins.Hosting/EdFi.Api.Plugins.Hosting.csproj` and its `packages.lock.json` is regenerated. Both plugin projects are already in `src/config/EdFi.DmsConfigurationService.sln` (`:42`, `:44`, `:46`), which DMS-1496 did so that this story would not have to.
- **`src/config/Dockerfile` gains the plugin tree**, mirroring `src/dms/Dockerfile`: a `pluginsource` stage that copies `plugins/` from the `parentdir` named context and removes `bin/`, `obj/`, and `results.sarif` before the build stage sees it (`src/dms/Dockerfile:22-30`); the plugin `Directory.Build.props`, project files, and lock files copied ahead of the restore (`:53-57`); `WORKDIR` moved down one level so the CMS and plugin trees sit beside each other under a common parent holding the shared `.editorconfig`, `Directory.Packages.props`, and `nuget.config` (`:33-43`, `:59`); the restore extended to `EdFi.Api.Plugins.Hosting`, which walks its `ProjectReference` closure and therefore validates the contract's lock file too (`:87`); and the plugin sources copied from the staged tree after the restore (`:109`). The named context already exists on every lane that builds this file: `build-contexts: parentdir=./src` at `.github/workflows/on-config-pullrequest.yml:395`, `:489`, and `:583`, and `--build-context parentdir=../` in `build-config.ps1`'s `DockerBuild` (`:470`).
- The staging stage is not replaced by a `src/.dockerignore` and not by `COPY --exclude`, and the pull request says why rather than leaving the next reader to re-derive it: `src/dms/.dockerignore` filters the DMS build context and a named context is filtered by a `.dockerignore` of its own, which `src/` does not have, so a direct copy of the tree carries a local build's `bin/`, `obj/`, and `results.sarif` into the image, and an `obj/` arriving after the restore lands on top of the Linux-generated `project.assets.json`. A `src/.dockerignore` would change both images' contexts at once, which is why it was rejected for the DMS image and is rejected again here.
- `.github/workflows/on-config-pullrequest.yml:119` gains `src/plugins/*` in the case that sets `fresh_build_required`, beside `src/config/Dockerfile`, on the same ground: once the CMS image's build context includes that tree, a change there changes the image. `:124` already names `src/plugins/*` for `config_relevant` and needs nothing.
- `CmsPluginContracts` is a frontend-owned static holding CMS's one instance of `PluginContractRegistry`, declaring two entries: `ISecretResolver` as `Replace` and `IClientSecretHasher` as `Replace`. `ContractAssemblyNames` is that registry's derived property rather than a second list, and for CMS it yields `EdFi.Api.Plugins` and `EdFi.DmsConfigurationService.Secrets`. A test asserts the package id `EdFi.Api.Secrets` is not among them, because an assembly reference carries an assembly name.
- `Config.Frontend/Program.cs` calls `PluginLoader.Load(builder.Configuration, CmsPluginContracts.Registry.ContractAssemblyNames)` between `CreateBuilder(args)` at `:14` and `builder.AddServices()` at `:16`, then invokes `loadedPlugins.ContributeConfiguration(builder.Configuration)` immediately after. That placement is a criterion rather than a detail: `AddServices` reads configuration from its first statements, so Phase A has to have finished before it is entered.
- `AddServices` takes the `LoadedPlugins` aggregate and invokes `ContributeServices` through it with `CmsPluginContracts.Registry`, after its own registrations and before `Build()`, registering the returned `PluginAuditInput` as a singleton **instance** in the same call. Registering an instance activates nothing, and registering it after every hook has run is what stops a plugin that registered its own from displacing it, because a single-service resolve takes the last registration. A test asserts a plugin registering `PluginAuditInput` does not displace the host's.
- **The plugin audit is a direct call.** Between `Build()` at `:53` and `RunAsync()` at `:113`, CMS resolves the registered `PluginAuditInput`, calls `PluginRegistrationAudit.AuditAsync(input, app.Services)` (`src/plugins/EdFi.Api.Plugins.Hosting/PluginRegistrationAudit.cs:47`), writes every finding, and throws if there is one. The function returns findings rather than throwing precisely so a caller can report all of them, and the CMS call site does.
- **The lifetime-and-keyedness check is a CMS-side check beside the audit, over the same input.** Both declared contracts must be registered as singletons and unkeyed; a plugin registering either as scoped or transient, or under a service key, is refused with the plugin and the lifetime or key named. It is CMS-side rather than inside the shared audit because both rules are per-contract metadata the host holds and the registry does not carry, which is the same reason DMS-1434's transient-only rule for `ICustomResourceValidator` lives on the DMS side. The keyed refusal closes a hole the shared audit deliberately leaves open: a declared contract under a concrete key is supported there and counts as an ordinary claim (`src/plugins/EdFi.Api.Plugins.Hosting/PluginRegistrationAudit.cs:231`, `:88`), while CMS's consumers resolve unkeyed (`Backend.OpenIddict/Repositories/OpenIddictClientRepository.cs:21`), so a keyed registration would boot green, emit an inventory event saying the contract was registered, and displace nothing. A test asserts each refusal, and the keyed case specifically: a plugin registering `IClientSecretHasher` under a key fails startup rather than loading inert.
- **The inventory event is emitted before the audit runs.** One structured `Information` event per loaded plugin, with `PluginName`, `AssemblyVersion`, `DeclaredFiles`, `RegisteredServiceTypes`, `RemovedDescriptors`, and `HostFirstSubstitutions`, matching the shape DMS emits. The ordering is a criterion for the attribution reason the spine gives: an audit failure names a service type and only the inventory maps that type back to the plugin that registered it. A test asserts the event for a fixture plugin appears in the captured log before the audit's failure for the same boot.
- No configuration key or value contributed by a Phase A source appears anywhere in the log, asserted by a fixture whose source carries a value that looks like a secret: the captured output contains the source **type** and neither the key nor the value.
- `Config.Frontend/appsettings.json` gains `"Plugins": { "Directory": "/app/plugins", "Allowed": "" }`. `Allowed` ships empty, so a CMS deployment that adopts nothing boots exactly as it does today, asserted by the existing CMS unit and end-to-end suites passing unchanged with no plugin root present.
- A fixture plugin exercising **both** phases proves the integration: its `ContributeConfiguration` adds a source supplying a value CMS reads, and its `ContributeServices` registers an `ISecretResolver`. An integration test boots CMS with `Plugins:Directory` pointed at it and `Plugins:Allowed` naming it, and asserts the configuration value resolved to the plugin's and that the resolver is resolvable from the container. No fixture in the spine exercises both phases, so this one is new rather than reused.
- Fatal cases assert on the exception escaping host creation, because plugin loading happens before the container exists and because CMS has no startup status file to record a failed phase in. A misspelled allowlist entry, a plugin allowlisted on a missing root, a plugin whose `ContributeConfiguration` throws, and a plugin whose `ContributeServices` throws are each asserted to fail the boot with no request served, and each failure is asserted to have been written to `Console.Error`, which is the only channel the loader has before the logger exists.
- Two plugins each registering `ISecretResolver` is fatal and names both; one plugin registering it twice is fatal and names the plugin and its registration count and addresses its author; one plugin registering `IClientSecretHasher` once loads successfully with the host's own registrations of `ClientSecretHasher` still present. That last case is the one that must pass and the one a naive descriptor count would refuse, and it is asserted on both reachable shapes rather than against a source-site count: a self-contained PostgreSQL deployment registers the host default **twice**, once in `ConfigureDatastore` (`Config.Frontend/Infrastructure/WebApplicationBuilderExtensions.cs:206`) and once inside the OpenIddict extension `ConfigureIdentityProvider` calls immediately after it (`:90-91`, `:376`), while a Keycloak deployment registers it **once**. There are four registration sites in source and never four descriptors in one process, since the engine-specific sites are mutually exclusive and the fourth sits in an overload nothing calls. The replace-conflict count is indifferent to the number, because it reads only descriptors the per-hook diffs attribute to plugins.
- A plugin that registers a CMS-owned service type that is no declared plugin contract is fatal at the **startup guard's displacement check**, which is the audit and not the wrapper, and names both the plugin and the type. A plugin that removes or overwrites a pre-existing CMS-owned descriptor is fatal at the **wrapper**, before the call reaches the real collection. A plugin that registers its own types, `Microsoft.Extensions.*` options, and an `IHostedService` alongside a declared contract loads unaffected and its inventory event lists the hosted service.
- **`HostOwnedServiceTypes` needs no change for CMS, and this story proves that rather than assuming it.** Its prefix list already carries `EdFi.DmsConfigurationService.` beside `EdFi.DataManagementService.` (`src/plugins/EdFi.Api.Plugins.Hosting/HostOwnedServiceTypes.cs:38-42`), so every CMS service type is already the host's. The criterion is a test rather than a code change, because the assertion is that a rule written for one host already holds for the other and the way that stops holding is silently.
- `eng/docker-compose/published-config.yml` and `local-config.yml` are unchanged, and a `plugins-config.yml` overlay carries the `:ro` mount at `/app/plugins` for the CMS service, added with its own `-f`. It follows the shape of `eng/docker-compose/plugins-dms.yml`, which does **not** exist on main: that file is DMS-1499's output, as are the mount variable's entries in `eng/docker-compose/README.md` and `.env.example`. So this story either lands after DMS-1499 and mirrors a file it can read, or it writes the CMS overlay first and DMS-1499 mirrors this one; the pull request says which, rather than citing a precedent that was not there. An unconditional mount in the base files is rejected for the reason the spine gives: Compose cannot make a bind mount conditional inside one file, so Docker would materialize an empty root-owned directory beside every deployment that never asked for a plugin. The mount variable gets the same documentation homes the DMS one has: `eng/docker-compose/README.md` and the tracked `eng/docker-compose/.env.example`, commented out and carrying the same note about why it is declared with `:?`.
- `docs/CONFIGURATION.md` gains the CMS `Plugins` section, stating that `Allowed` ships empty, that it is the only switch, and that its order is invocation order and is contractual for Phase A. It also states which keys Phase A cannot supply in CMS. CMS has no equivalent of DMS's `AppSettings:StartupStatusFilePath`, because it has no bootstrap status signal. It does have the other one: `PluginLoader.Load` binds `Plugins:Directory` and `Plugins:Allowed` to decide what loads before any Phase A hook runs, so no plugin source can supply either, which is the same security property the DMS chapter states.
- `dotnet build --no-restore src/config/EdFi.DmsConfigurationService.sln`, `dotnet test src/config/EdFi.DmsConfigurationService.sln`, and `build-config.ps1 E2ETest` pass.
