# Changelog: 8.1.0

Brief descriptions of breaking changes and new features in this release, aimed at
integrators upgrading from the previous version. Each entry says what changed and what,
if anything, a client must do differently; the linked design documents carry the full
detail and rationale.

## Breaking changes

- **The retired XML utility's `ParseXml` and `Transform` commands, legacy options,
  and hierarchy-array output are removed.** Migrate conversion scripts to
  `security-metadata-tools convert-ods-xml --input export.xml --output Claims.json`.
  Conversion writes a complete `claimSets`/`claimsHierarchy` document and does not
  replace claims fragment merging. See the [Claims Loading Deployment Guide](../CLAIMS-LOADING-GUIDE.md).

- **PUT uses the URL ID and no longer requires a body `id`.** Omitted and null IDs
  are accepted; an otherwise-valid PUT with a different valid GUID body ID can now
  return `204` instead of a mismatch `400`. An empty object still fails for required
  resource fields, but no longer reports `id is required`. A supplied non-null `id`
  must be a GUID string accepted by `Guid.TryParse`; malformed IDs still return `400`,
  but `type` changes from `urn:ed-fi:api:bad-request` to
  `urn:ed-fi:api:bad-request:data-validation-failed`, and the diagnostic moves from
  `errors[]` to `validationErrors["$.id"]`. Update clients that match these error fields.
  Generated OpenAPI descriptions saying the body ID “will be ignored” are awaiting a
  MetaEd wording correction: the value does not select the target, but must still pass
  validation. See [DMS-1623](https://edfi.atlassian.net/browse/DMS-1623),
  [Data strictness](../DATA-STRICTNESS.md#unexpected-properties-are-dropped), and
  [METAED-1682](https://edfi.atlassian.net/browse/METAED-1682).

- **The self-contained identity provider defaults to 15 active tokens per Ed-Fi API client.**
  A positive `IdentitySettings:BearerTokenPerClientLimit` applies to Ed-Fi API clients.
  Exemption requires no live `dmscs.ApiClient` row and nonempty registered scopes consisting
  only of recognized Configuration Service admin scopes, as used by DMS's Configuration Service credential
  and Configuration Service admin/bootstrap clients. Clients with empty scopes or any unrecognized scope
  remain limited. Explicit values below 1 still disable enforcement globally. Limited
  clients must reuse their tokens:
  the 16th concurrent grant at the default limit receives the canonical HTTP 429 `Too Many Tokens`
  response, with message
  `Too many access tokens have been requested (limit is 15). Access tokens should be reused until they expire.`
  The Configuration Service's `/connect/token` answers with type
  `urn:ed-fi:management-api:security:authentication:too-many-tokens` (see the Configuration
  Service problem-type entry below). DMS `/oauth/token` parses that response, or the
  `urn:ed-fi:api:security:authentication:too-many-tokens` one an earlier Configuration Service
  returns, and rebuilds it with DMS's own, unchanged type
  `urn:ed-fi:api:security:authentication:too-many-tokens`.
  See [DMS-1459](https://edfi.atlassian.net/browse/DMS-1459) and
  [CONFIGURATION.md](../CONFIGURATION.md#identity-provider-configuration).

- **Self-contained OIDC discovery now advertises endpoint URLs from configuration.**
  The Configuration Service builds every advertised endpoint URL from
  `IdentitySettings:Authority` plus `AppSettings:PathBase`, regardless of the request Host.
  Set Authority to the issuer URL without the PathBase segment; otherwise endpoints can
  contain that segment twice. Set DMS `JwtAuthentication:Authority` to the exact issuer and
  `JwtAuthentication:MetadataAddress` to a reachable URL on the Authority's origin so DMS
  can fetch the advertised JWKS URL from that same origin. Update deployments that used a
  different internal name for metadata retrieval before upgrading.

- **`POST /connect/revoke` now requires client authentication, only revokes tokens
  belonging to the authenticated client, and revokes under both identity providers.**
  The endpoint previously accepted anonymous requests, and under
  `AppSettings:IdentityProvider = keycloak` it revoked nothing.

  *Client authentication and ownership (DMS-1478, self-contained identity provider).*
  Callers must authenticate with their own `client_id` and `client_secret` (HTTP Basic or
  form fields, as at `POST /connect/token`); the error a failed attempt receives is listed
  below. Put the token to revoke in the `token` form field. A bearer token in the
  `Authorization` header does **not** count as authentication. A caller may only revoke a
  token whose `client_id` matches its own; a mismatch is a silent no-op that still returns
  `200 OK`, per RFC 7009. Because every authenticated outcome returns the same `200 OK`,
  confirm a revocation with `POST /connect/introspect`, authenticated as the token's owner,
  rather than relying on the status code.

  *Added by DMS-1327:*
  - **Keycloak support.** Under `keycloak`, the Configuration Service checks that the caller is a confidential
    client and forwards the revocation to Keycloak with the caller's own credentials, so
    Keycloak's ownership check applies; another client's token is answered `200 OK` and left
    active. Public (secretless) and bearer-only clients are refused with `invalid_client`.
    The Configuration Service reads the caller's client definition with its own Keycloak service credentials,
    which need the `realm-management` `view-clients` role (part of the `realm-admin` role
    the setup scripts assign). Configuration Service `/connect/introspect` cannot observe Keycloak tokens;
    confirm a revocation through Keycloak's own introspection endpoint.
  - **OAuth error format for every error.** Every non-2xx response is an RFC 6749 JSON
    object (`{"error": "...", "error_description": "..."}`), including the missing-token
    `400`, which DMS-1218 had changed to the Ed-Fi problem-details format. A request without
    credentials, or with incomplete form credentials, is answered `400 invalid_client`;
    `401 invalid_client` with a `WWW-Authenticate: Basic` challenge is reserved for a failed
    HTTP Basic attempt. Duplicated parameters, a duplicated `Authorization` header, or HTTP
    Basic combined with form credentials are `400 invalid_request`. A token type the
    provider does not support is `400 unsupported_token_type`, and an unexpected fault is
    `500 server_error`.
  - **`503` for an outage, refused startup for a missing implementation.** A database or
    identity provider failure during revocation is answered
    `503 temporarily_unavailable`: the outcome could not be confirmed (the token may or may
    not have been revoked), retrying is safe, and the Configuration Service keeps serving. The Configuration Service does not check
    provider availability at startup, but it refuses to start when no token revocation
    implementation can be constructed for the configured `AppSettings:IdentityProvider`
    (for example a custom registration that removes or breaks the shipped one); the
    startup error names only the exception types.
  - **`+` decoding in HTTP Basic credentials on `/connect/revoke`.** Credentials are
    decoded per RFC 6749 §2.3.1: the client form-encodes `client_id` and `client_secret`
    before joining and base64-encoding them, so a `+` is decoded as a space and a literal
    `+` must be sent as `%2B`. A malformed Basic value is refused rather than repaired.
    `POST /connect/token` keeps its existing decoding.

  See [CS-AUTH.md](../../reference/design/configuration-service/CS-AUTH.md),
  [OWASP-AUTH-COVERAGE.md](../OWASP-AUTH-COVERAGE.md) and the
  [DMS-1327 design](../../reference/design/configuration-service/DMS-1327-cms-token-revocation.md).

- **`POST /connect/introspect` now requires client authentication and only describes tokens belonging to the authenticated client.**
  The endpoint previously accepted anonymous requests and described any valid token.
  - **Client authentication.**
    Callers must authenticate with their own `client_id` and `client_secret`, as HTTP Basic or form fields (exactly one of them), as at `POST /connect/revoke`.
    A bearer token in the `Authorization` header does **not** count as authentication.
    A request without credentials is answered `400 invalid_client`, and failed credentials are answered `invalid_client` (`401` with a `WWW-Authenticate: Basic` challenge for a failed HTTP Basic attempt).
    A client-store failure while authenticating is answered `503 temporarily_unavailable`.
    A `self-contained` host refuses to start when no introspection implementation can be constructed (for example a custom registration that removes the shipped one); the startup error names only the exception types.
  - **Owner-only disclosure.**
    A valid token is described only to the client it was issued to.
    Every other token (another client's, unknown, malformed, expired or revoked) is answered `200` with `{"active": false}`.
    So is a token the service could not decide because a signing-key or token-status store failed; that case logs the Error `Token validation could not reach a decision`.
  - **OAuth error format for every error.**
    Every error from this endpoint, in both identity provider modes, is an RFC 6749 JSON object, including a malformed or unreadable form body.
    A request without a `token` is answered `400 invalid_request`, not the Ed-Fi problem-details body DMS-1218 introduced.
    An unexpected fault is answered `500 server_error` with "The introspection request could not be processed."
  - **URL-encoded bodies only, here and at `POST /connect/revoke`.**
    Both endpoints answer any body other than `application/x-www-form-urlencoded`, `multipart/form-data` included, with `400 invalid_request`.
    A `multipart/form-data` body was previously accepted.
    The exception is introspection in `keycloak` mode, which makes no request checks (see below).
  - **`exp` and `iat` are JSON integers.**
    Update clients that read them as strings.
  - **Discovery and OpenAPI.**
    `introspection_endpoint_auth_methods_supported` and `revocation_endpoint_auth_methods_supported` now both list `client_secret_basic` and `client_secret_post`.
    `/openapi/v1.json` and `/metadata/specifications` describe `POST /connect/revoke`, and `POST /connect/introspect` in `self-contained` mode, with a `client_secret_basic` HTTP Basic security scheme instead of an empty security requirement.
  - **Keycloak mode is unchanged.**
    The endpoint makes no credential checks and answers `{"active": false}` for any request that carries a token.
    The only visible change is the OAuth error format described above.
    Configuration Service introspection still cannot observe Keycloak tokens.

  See [DMS-1479](https://edfi.atlassian.net/browse/DMS-1479),
  [CS-AUTH.md](../../reference/design/configuration-service/CS-AUTH.md#token-introspection) and
  [OWASP-AUTH-COVERAGE.md](../OWASP-AUTH-COVERAGE.md).

- **DMS now requires `JwtAuthentication:Authority` to equal the identity provider's issuer
  exactly.** Previously DMS read this setting (`DMS_JWT_AUTHORITY` in Docker) but never used
  it, and trusted whatever `issuer` its OIDC metadata document asserted. Now the `issuer`
  served at `JwtAuthentication:MetadataAddress` must match `Authority` character for
  character, with no trailing-slash or case normalization.
  - **At startup:** a mismatch stops DMS from starting.
  - **After startup:** a mismatch that appears on a later metadata refresh makes DMS reject
    every token with `401 Unauthorized` until DMS re-fetches metadata that matches. DMS
    retries at most once per `RefreshIntervalMinutes` (default 60), so recovery can lag the
    fix by up to that long; restarting DMS recovers immediately.
  - **Logging:** both cases are logged with the configured and discovered values. After
    startup, only the first rejected request is logged as an error; repeats log at debug
    level until DMS adopts metadata that matches.
  - **Signing keys:** DMS also refuses a metadata document whose `jwks_uri` is not on the
    origin (scheme, host and port) of `JwtAuthentication:MetadataAddress`, so a tampered
    document cannot point DMS at keys served elsewhere even when its `issuer` is correct. At
    startup this stops DMS from starting; on a later refresh DMS keeps the last good metadata
    and retries until a fetch succeeds (once the automatic refresh is due, on every request).
    The first refusal is logged as an error, and repeats at debug level until DMS fetches
    signing keys successfully again. DMS does not follow redirects when fetching these documents, so `MetadataAddress` and
    `jwks_uri` must be the final URLs.

  Before upgrading, set `Authority` to the `issuer` your metadata document serves, and make
  sure the document's `jwks_uri` is on the origin of `MetadataAddress`:
  - **Keycloak:** use the public realm URL built from `KC_HOSTNAME`, for example
    `http://localhost:8045/realms/edfi`. Use it even when DMS fetches metadata over an
    internal hostname. In that case, also run Keycloak with
    `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true`. Keycloak's default, `false`, makes `jwks_uri` name
    the public host, and DMS will not start. Otherwise, point `MetadataAddress` at the public
    URL.
  - **Configuration Service's self-contained provider:** use the value of its
    `IdentitySettings:Authority`.

  See [CONFIGURATION.md](../CONFIGURATION.md).

- **`RequireHttpsMetadata` ships as `true` in both services.** The shipped `appsettings.json`
  files set DMS `JwtAuthentication:RequireHttpsMetadata` and Configuration Service
  `IdentitySettings:RequireHttpsMetadata` to `true`, and both also default to `true` when the
  key is omitted. A host started from the shipped `appsettings.json` with an `http://`
  metadata address and no override now fails at startup (DMS) or at the first authenticated
  request (Configuration Service with Keycloak; self-contained mode fetches no metadata).
  - **Compose stacks:** the shipped Compose test/demonstration files and `.env.*` files still
    set it to `false` for their private-network identity providers, so they need no change.
  - **Direct development runs:** the `appsettings.Development.json.example` starter files set
    `"RequireHttpsMetadata": false`. Add the same line under `JwtAuthentication` (DMS) or
    `IdentitySettings` (Configuration Service) to an existing `appsettings.Development.json`.
  - **Startup warning:** a host whose hosting environment is not `Development` logs a
    startup warning while the value is `false`.

  Set `false` only when the identity provider is not reachable over an untrusted network. See
  [DMS-1483](https://edfi.atlassian.net/browse/DMS-1483),
  [Running locally](../RUNNING-LOCALLY.md), and
  [CONFIGURATION.md](../CONFIGURATION.md#identity-provider-configuration).

- **The six `E2E-*` claim sets are no longer built in.** `E2E-NameSpaceBasedClaimSet`,
  `E2E-NoFurtherAuthRequiredClaimSet`, `E2E-RelationshipsWithEdOrgsOnlyClaimSet`,
  `E2E-RelationshipsWithEdOrgsOnlyInvertedClaimSet`,
  `E2E-RelationshipsWithEdOrgsOnlyMixedStrategyClaimSet` and
  `E2E-RelationshipsWithEdOrgsOnlyOrInvertedClaimSet` were test-only claim sets that earlier
  releases installed in every deployment, both in the built-in claims and in the
  `Deploy/AdditionalClaimsets` directory the Docker Compose files mount. New databases no longer
  get them; existing databases keep them. This affects applications assigned to one of these
  claim sets: on a new database, every request from their clients fails with `500` (a
  security-configuration error). Assign those applications a built-in claim set, such as
  `EdFiSandbox`. To remove the claim sets from an existing database, see
  [Upgrading an Existing Deployment: E2E Claim Sets](../CLAIMS-LOADING-GUIDE.md#upgrading-an-existing-deployment-e2e-claim-sets).

- **Claims fragment files are named `*-claims.json`.** This affects deployments that load
  their own fragments in `Hybrid` or `Filesystem` mode, including files in the Azure VM stack's
  `compose/claims` directory and the bootstrap scripts' `-ClaimsDirectoryPath`. The Configuration
  Service, and bootstrap staging, read only files whose names end in `-claims.json`. A file still
  named `*-claimset.json` is not read, and the Configuration Service logs a warning that names it
  whenever it reads fragments: when it seeds an empty database at startup, on a claims reload,
  and on the first `GET /management/current-claims`. A database that already holds claims is not
  reseeded at startup, so an in-place upgrade logs no warning until one of the others happens.
  Bootstrap staging warns the same way. The fragment directory the Docker Compose files mount
  moved from `Deploy/AdditionalClaimsets` to `Deploy/AdditionalClaims`. Rename each
  `*-claimset.json` file to end in `-claims.json` before upgrading. A fragment with non-parent
  entries but no top-level `name` registers its claim set under the file name, so renaming the
  file also renames that claim set: applications assigned to the old name lose their access, and
  any claim set already registered under the old name stays in the database. Before renaming
  such a file, add a top-level `"name"` set to its old file name without `.json`, for example
  `"010-vendor-claimset"`. Bootstrap staging rejects such fragments, so this applies only to
  fragments the Configuration Service reads directly.

- **A POST that finds an existing record is authorized as `Update`, not `Create`.** A POST
  that creates a record still needs `Create` permission and runs `Create`'s authorization
  strategies. A POST whose identity matches a record that already exists, including an
  identical repost, now needs `Update` permission and runs `Update`'s strategies against the
  stored record, the same as a `PUT`. Previously every POST was checked as `Create`. This
  matches the ODS/API.

  The default claim sets are affected. For the `people` domain (Student, Staff, Contact and
  so on), `Create` uses `NoFurtherAuthorizationRequired` and `Update` uses
  `RelationshipsWithEdOrgsAndPeople`. For `primaryRelationships` (such as
  StudentSchoolAssociation), `Create` uses `RelationshipsWithEdOrgsOnly` and `Update` uses
  `RelationshipsWithEdOrgsAndPeople`. A client on `SISVendor`, `DistrictHostedSISVendor` or
  `EdFiSandbox` that re-POSTs an existing student not associated with its education
  organizations now receives `403 Forbidden` where it previously received `200 OK`.

  A client whose claim set grants `Create` but not `Update` can no longer change an existing
  record by POST; a client granted `Update` but not `Create` can now do so. A POST that neither
  action permits is still refused as a `Create` denial. Loaders that re-run against existing
  data need `Update` as well as `Create`: the built-in `SeedLoader` claim set now grants both,
  while `BootstrapDescriptorsandEdOrgs` still grants only `Create`, as in the ODS/API (see
  [SCHOOL-YEAR-LOADER.md](../SCHOOL-YEAR-LOADER.md)).

  **Upgrade step for an existing Configuration Service database.** The Configuration Service
  writes its shipped claims only into empty claims tables, so a database created by 8.0 keeps
  the Create-only `SeedLoader` grants it was first loaded with. Re-running seed delivery against
  it fails with `403` on the first record that already exists. Before that rerun, call
  `POST /management/reload-claims` to rebuild the claims from the shipped files. The endpoint
  needs `CONFIGURATION_SERVICE_DANGEROUSLY_ENABLE_UNRESTRICTED_CLAIMS_LOADING=true` and an admin-scope
  token. The reload replaces the non-reserved claim sets and the whole claims hierarchy, so export
  any claim set that exists only in the database (`GET /v3/claimSets/{id}/export`) first and
  re-import it afterwards (`POST /v3/claimSets/import`). `SeedLoader` is
  system-reserved, so `/v3/claimSets` cannot add the grant to it directly.

  On Data Standard 6.1, `SeedLoader` now also grants `Create` and `Update` on the
  `specialEducation` domain (`IDEAEvent`, `StudentIEP` and its goal, service delivery and
  service prescription), without which the Populated sample's `SpecialEducation.xml` is refused
  with `403`. A DS 6.1 database created before this change needs the same reload to get it.

- **DMS answers `503 Service Unavailable` when it cannot get profile data from the
  Configuration Service, and profile enforcement may switch on after this upgrade.** DMS
  previously treated any failure to fetch an application's profile assignments or a profile
  definition — a `5xx`, a timeout, a `403` — as "no profile", and cached that result for
  `ProfileCacheExpirationSeconds`. Requests then ran with no profile enforcement, and explicit
  profile headers were answered `406`/`415`. DMS now answers a retriable `503` with type
  `urn:ed-fi:api:service-unavailable` for resource requests, token info and the profile metadata
  endpoints, caches nothing, and fetches again on the next request. Clients should retry a `503`.
  A Configuration Service `404` for a single profile still means that profile is absent.

  The `edfi_admin_api/authMetadata_readonly_access` scope now also grants
  `GET /v3/applications/{id}`, `/v3/profiles` and `/v3/profiles/{id}`, the reads DMS needs to
  enforce profiles. A single-tenant deployment whose DMS used that scope, the example value in
  [CONFIGURATION.md](../CONFIGURATION.md), was refused those reads in 8.0: implicit profile
  enforcement was silently off. After this upgrade it is on, so clients of applications with
  assigned profiles see filtered responses, and writes silently drop the members a profile
  excludes: those members are not saved, and the write still succeeds. A `POST` whose profile
  excludes a required member is refused with `400 data-policy-enforced`, and a request with no
  profile header is refused with `403` when more than one assigned profile covers the resource.
  Upgrade the Configuration Service together with DMS: DMS on that scope against an 8.0
  Configuration Service answers `503` to every resource `GET`, `POST` and `PUT`, and to token
  info. See the error matrix in
  [DMS-Profiles-Design.md](../../reference/design/profiles-DMS-877/DMS-Profiles-Design.md#82-error-response-matrix)
  and [ROLES-SCOPES.md](../ROLES-SCOPES.md).

- **Vendor and profile names are unique per tenant, and profiles belong to a tenant.** This
  affects Configuration Service API clients, mostly in multi-tenant deployments. In 8.0 these
  names were unique across the whole deployment, and every tenant could see and assign every
  profile.
  - Different tenants can now use the same vendor or profile name.
  - Each tenant sees and manages only its own profiles. Assigning another tenant's profile to an
    application returns `409` ("Profile does not exist.").
  - Creating a profile with a name already used in the tenant still returns `400`. Renaming a
    vendor to a name already used in the tenant returns `400` instead of `500`. The next entry
    covers the duplicate response body and the change to `POST /v3/vendors`.
  - Claim set names remain unique across all tenants.

  **Before upgrading a multi-tenant deployment:** existing profiles are assigned to tenants by
  the applications that use them. A profile shared by several tenants is copied, and the copies
  get **new ids**. Inventory your profile definitions first, and upgrade all Configuration
  Service and DMS processes together. Single-tenant profiles are unchanged. See
  [Upgrading an Existing Multi-Tenant Deployment](../MULTI-TENANCY-GETTING-STARTED.md#upgrading-an-existing-multi-tenant-deployment).

- **The Configuration Service rejects duplicates with `400 Bad Request`, and
  `POST /v3/vendors` no longer updates an existing vendor.** These changes follow the
  Management API specification, which documents `400` for these operations:
  - `POST /v3/vendors` only creates. A company that already exists in the caller's tenant was
    previously updated and answered `200 OK`; it is now rejected with `400`, and the existing
    vendor is left unchanged. To change a vendor, call `PUT /v3/vendors/{id}`, finding the id
    with `GET /v3/vendors?company=<name>` if needed.
  - Data store names must be unique within a tenant, and API client names must be unique
    within an application. A duplicate is rejected with `400`, on `POST` and on a `PUT` that
    renames onto a name already in use. An API client may still share its name with a client
    of another application.
  - Claim set name duplicates on create, update and copy now receive `400` instead of
    `409 Conflict`. An import whose claim set name belongs to another tenant also receives
    `400` instead of `409 Conflict`. An import whose name already exists in the caller's
    tenant still replaces that claim set's grants and answers `201 Created`. A second data
    store derivative of the same type for one data store is rejected with `400`.
  - Every duplicate rejection has the same body: type `urn:ed-fi:management-api:bad-request:data`, with
    the message under the duplicated field in `validationErrors`, for example
    `"Company": ["A vendor with this company name already exists."]`.

  **Upgrade step.** The upgrade adds the new uniqueness rules to the Configuration Service
  database. If existing data store or API client rows already collide, the Configuration
  Service stops at startup and lists up to 20 ids of the colliding rows per table. Before
  upgrading, find such rows on the current version and rename them with
  `PUT /v3/dataStores/{id}` or `PUT /v3/apiClients/{id}`, or remove them with `DELETE`, then
  retry the upgrade. To find collisions before upgrading, list each tenant's data stores and
  each application's API clients and look for repeated names. On SQL Server, names that differ
  only in letter case or trailing spaces also collide. In a multi-tenant deployment, send the
  owning tenant's `Tenant` header with every request, including each `PUT` or `DELETE`.
  Repeated runs of setup scripts that create data stores, such as
  `-SchoolYearRange`, are the usual source of duplicate data store names. See
  [API-CLIENT-AND-INSTANCE-CONFIGURATION.md](../API-CLIENT-AND-INSTANCE-CONFIGURATION.md#related-tables).

- **The Docker Compose environment variables use the Configuration Service name.** This
  affects deployments built on the provided Compose files or the Azure VM stack. The
  Configuration Service's variables now start with `CONFIGURATION_SERVICE_` instead of
  `DMS_CONFIG_`, and the Ed-Fi API's settings for calling it start with
  `DMS_CONFIGURATION_SERVICE_` instead of `CONFIG_SERVICE_`. The earlier names are not read and
  have no aliases; the setup scripts only warn about them. Rename the variables in each
  environment file before upgrading and keep their values, in particular the database
  encryption key and the client secrets. On the Azure VM stack
  `DMS_CONFIG_ENABLE_CLAIMS_RELOAD` becomes
  `CONFIGURATION_SERVICE_DANGEROUSLY_ENABLE_UNRESTRICTED_CLAIMS_LOADING`. See
  [Migrating from the earlier variable names](../CONFIGURATION.md#migrating-from-the-earlier-variable-names).

- **The Configuration Service requires PostgreSQL 15 or later.** This affects every
  deployment whose Configuration Service runs on PostgreSQL 13 or 14, single-tenant or
  multi-tenant. Its 8.1 database upgrade uses a feature those versions lack
  (`NULLS NOT DISTINCT`). Upgrade PostgreSQL before upgrading the Configuration
  Service. SQL Server deployments are unaffected. See
  [Database versions](../OPERATIONS.md#database-versions).

- **DMS requires PostgreSQL 18 or later with a UTF-8 database encoding.** This affects
  every DMS deployment on a PostgreSQL server older than 18, and every DMS database
  that is not UTF-8, single-tenant or multi-tenant. Descriptor identity will rely on
  PostgreSQL's builtin `pg_c_utf8` collation, which needs a UTF-8 database. Before
  upgrading DMS, upgrade the server to PostgreSQL 18 or later, and re-create any
  database that is not UTF-8 as UTF-8 (PostgreSQL cannot change an existing
  database's encoding). A server shared by DMS and the Configuration Service must meet
  the DMS floor. SchemaTools checks the server version and the database encoding
  before it creates a database or runs any DDL, and stops with a message naming both
  requirements. Docker volumes created by PostgreSQL 16 images must be removed or
  upgraded with `pg_upgrade` before the first start on the PostgreSQL 18 image. SQL
  Server deployments are unaffected. See
  [Database versions](../OPERATIONS.md#database-versions) and
  [PostgreSQL major upgrades](../POSTGRESQL-MAJOR-UPGRADE.md).

- **DMS claimset management endpoints now require an admin token.** This affects deployments
  that set `AppSettings:EnableClaimsetReload=true`. In 8.0, those deployments let anyone call
  `POST /management/reload-claimsets` and `GET /management/view-claimsets`
  (`/management/{tenant}/...` when multi-tenant) without a token.

  In 8.1 one switch, `AppSettings:ManagementEndpoints:Enabled`, decides whether both endpoints
  are exposed, and `EnableClaimsetReload` is no longer read. A deployment that left
  `EnableClaimsetReload=false` but sets `DMS_ENABLE_MANAGEMENT_ENDPOINTS=true` (the
  `.env.template` value since 8.0) exposes reload and view to callers holding the required role once
  it also sets a valid `AppSettings:ManagementEndpoints:RequiredRole`. To keep them disabled,
  set `AppSettings:ManagementEndpoints:Enabled=false` (`DMS_ENABLE_MANAGEMENT_ENDPOINTS=false`
  under Docker Compose).

  To keep using these endpoints after upgrading:
  - Set `AppSettings:ManagementEndpoints:Enabled=true` (`DMS_ENABLE_MANAGEMENT_ENDPOINTS`);
    otherwise they return `404`. It replaces both 8.0 switches, which 8.1 no longer reads:
    `AppSettings:EnableManagementEndpoints`, which had no effect in 8.0, and
    `AppSettings:EnableClaimsetReload`. Deployments created from the 8.0 `.env.template` files
    already set `DMS_ENABLE_MANAGEMENT_ENDPOINTS=true`.
  - Call them with a token that has the `cms-client` role. The Configuration Service gives this
    role to every admin client it registers; Ed-Fi API client tokens don't have it. Requests
    without a valid token get `401`, and tokens without the role get `403`.
  - If you renamed `IdentitySettings:ConfigServiceRole` in the Configuration Service, set
    `AppSettings:ManagementEndpoints:RequiredRole` (`DMS_MANAGEMENT_REQUIRED_ROLE`) to the same
    name.

  See [CONFIGURATION.md](../CONFIGURATION.md).

- **Optional-feature and ApiSchema configuration keys moved into their own sections.** DMS and
  the Configuration Service no longer read the earlier keys, and there are no aliases. Rename
  them in `appsettings.json` overrides and in environment variables before upgrading:
  - `AppSettings:EnableManagementEndpoints` becomes `AppSettings:ManagementEndpoints:Enabled`,
    and `AppSettings:EnableClaimsetReload` is removed (see the claimset management entry above).
    Management endpoints stay off by default.
  - `AppSettings:UseApiSchemaPath` and `AppSettings:ApiSchemaPath` become
    `AppSettings:ApiSchema:UseCustomPath` and `AppSettings:ApiSchema:Path`. A deployment that sets
    only the earlier keys loads the bundled ApiSchema workspace instead of its custom one.
  - Keys added earlier in the 8.1 cycle also moved: `AppSettings:EnableIdentityManagement`
    becomes `DataManagement:IdentityManagement:Enabled` (still off by default), and the
    Configuration Service's `IdentitySettings:TokenCleanupEnabled` and
    `IdentitySettings:TokenCleanupIntervalMinutes` become
    `IdentitySettings:TokenCleanup:Enabled` and `IdentitySettings:TokenCleanup:IntervalMinutes`
    (cleanup stays on, every 30 minutes, by default).

  The Docker Compose variables keep their names, and the shipped Compose files map them to the
  new keys. `DataManagement:ResourceLinks:Enabled` (default `true`) is now listed in the shipped
  `appsettings.json`. See [Optional features](../CONFIGURATION.md#optional-features) for the
  switch convention, every optional feature's key and default, and the full migration table.

- **Correlation IDs in error responses now match the logs.** This affects deployments that set
  `AppSettings:CorrelationIdHeader` so clients can send their own correlation ID. With it empty
  (the default), clients see no change. In 8.0, error responses echoed the value as sent, while
  the logs recorded a cleaned-up version, so the two could differ. Now DMS cleans the value
  once, and both use the result: it removes control characters, invisible format characters
  (such as zero-width and bidirectional marks) and line and paragraph separators, and truncates
  the value to `AppSettings:CorrelationIdMaxLength` (default `255`).

  `CorrelationIdMaxLength` must be between `64` and `1024`. With any other value, DMS starts but
  answers every request, including `/health`, with `500` until the setting is fixed and DMS is
  restarted. See
  [Correlation ID normalization](../LOGGING.md#correlation-id-normalization).
- **DMS now ignores `If-None-Match` on POST, PUT, and DELETE, matching the ODS/API.** In
  8.0.0, a write carrying `If-None-Match: *` or a matching tag returned `412 Precondition
  Failed`. DMS now processes it as if the header were absent: a POST upserts and returns `200`
  or `201`, and a PUT or DELETE returns `204`. Conditional GET is unchanged: `If-None-Match` still
  returns `304 Not Modified` on a match. A client that used `If-None-Match: *` as a create-only
  guard no longer has that protection, and there is no replacement header; a POST for an
  existing record now overwrites it. To prevent lost updates, send `If-Match` with the `_etag`
  from the stored resource. `If-Match: *` is unchanged and follows RFC 9110, succeeding when
  the resource exists and returning `412` when it does not; the ODS/API differs, returning `412`
  for `If-Match: *` every time. See
  [the ETag ADR amendment](../../reference/adr-etag-from-content-version.md#amendment-2026-09-30-if-none-match-is-a-conditional-read-validator-only).
- **DMS now ignores unknown query parameters, matching the ODS/API.** In 8.0.0, an unknown
  query parameter returned `400`. Now DMS ignores it and lists its name in an `X-EdFi-Warning`
  response header. A mistyped filter is dropped and widens the result, so check for this
  header. Malformed values of known parameters still return `400`, and paging parameters are
  still rejected on endpoints that don't support them. `/deletes` and `/keyChanges` now ignore
  resource filters. See
  [the ADR](../../reference/adr-unknown-query-parameters-DMS-1589.md).
- **DMS `/oauth/token` now accepts client credentials in the request body, and rejects bad
  credentials the way the ODS/API does.** In 8.0.0, DMS accepted credentials only in an
  `Authorization: Basic` header. Now it also accepts `client_id` and `client_secret` in an
  `application/x-www-form-urlencoded` or `application/json` body. A Basic header still works on
  its own, including with a JSON body. A request that uses both a Basic header and body credentials
  returns `400`, as it does in the ODS/API. An empty body field counts as omitted, as RFC 6749
  §3.2 requires, and a JSON `null` field counts as absent, so neither is a second mechanism beside
  the header. A whitespace-only field isn't either, matching the ODS/API. In 8.0.0, DMS ignored
  the body fields of such a request, so a client that sends both must now drop one.
  A request with missing or partial credentials, which returned `400 Malformed Authorization
  header` in 8.0.0, now returns `401` with `title` `invalid_request`. A request with an
  `Authorization` scheme other than Basic now returns `401` with `title` `invalid_client`. Both
  match the ODS/API, except that the ODS/API answers `400` to a non-Basic header that isn't exactly
  two space-separated parts, such as a bare `Bearer`. A client that checked for the `400` must
  handle the `401` instead. An empty `Authorization` header still returns `400`, now with the
  detail `The Authorization header must not be empty` instead of `Malformed Authorization
  header`. A body
  `client_id` or `client_secret` longer than 2048 characters returns `400`, and a JSON
  `"grant_type": null` now returns `400 Unsupported grant type` instead of `500`.
  An `Authorization` header that contains `basic` but is not a valid header value, such as
  `Basicxyz:secret` or two `Authorization` headers sent together, now returns
  `400 Malformed Authorization header` instead of `500`, and the header is no longer logged.
  See [the ADR](../../reference/adr-oauth-token-client-credentials-DMS-1604.md).

- **Descriptor storage now uses an independent `int DescriptorId` primary key.**
  Stored resource descriptor foreign keys now reference `dms.Descriptor.DescriptorId`
  instead of `DocumentId`. The descriptor's owning `bigint DocumentId` remains a unique,
  non-null foreign key to `dms.Document`. `dms.Descriptor.Discriminator` is removed;
  descriptor type identity uses `ResourceKeyId`. The stored `dms.Descriptor.Uri` column is
  removed: PostgreSQL reconstructs the URI from `Namespace` and `CodeValue`, while SQL
  Server retains a non-persisted computed `Uri` column. The shared descriptor
  change-tracking table also replaces `Discriminator` with `ResourceKeyId`.

  Update direct SQL and custom authorization views to join resource descriptor references
  to `dms.Descriptor` on `DescriptorId`. Custom views must still output the owning
  `bigint DocumentId` for authorization membership checks.

  **Existing databases must be reprovisioned before running the new runtime.**
  `RelationalMappingVersion` remains `v3`, and `EffectiveSchemaHash` can still match an
  incompatible older physical schema because generated DDL is not included in the hash.
  Rerunning create-only provisioning does not upgrade that schema. See
  [Reprovisioning and legacy data carry-forward](../RELATIONAL-BACKEND.md#reprovisioning-and-legacy-data-carry-forward).

- **`dms.Document.CreatedAt` is removed.** The DMS API data path did not use this column;
  removing it does not change API fields, ETags, change queries, or authorization decisions.
  There is no replacement creation-time column. Direct SQL that names `dms.Document.CreatedAt`
  fails against newly provisioned databases.

  **Existing databases keep the column until they are deliberately reprovisioned.** The DMS API
  works either way, but the storage saving exists only in databases provisioned from the new
  DDL. `RelationalMappingVersion` remains `v3`, and `EffectiveSchemaHash` does not change,
  because generated DDL is not included in the hash. A matching hash therefore cannot show that
  the column is gone; check the catalog instead. Rerunning create-only provisioning does not
  remove the column. Database template packages built before this change still have the column
  and must be replaced with packages built from the new DDL.

  **Established CDC deployments have no supported upgrade or cutover path in this release.**
  CDC validation and the guarded start, restart, and resume pre-checks fail closed while an
  established binding's database still has the column, though the DMS API keeps serving. A fresh
  database provisioned from the new DDL supports initial CDC enablement as before. See
  [Reprovisioning and legacy data carry-forward](../RELATIONAL-BACKEND.md#reprovisioning-and-legacy-data-carry-forward).

- **The foreign keys from every resource root table and `dms.Descriptor` to `dms.Document`
  no longer cascade.** The relational model now emits them with the `Restrict` delete action:
  `ON DELETE RESTRICT` on PostgreSQL and `ON DELETE NO ACTION` on SQL Server. This affects only
  scripts that modify the database directly. A `DELETE FROM dms.Document` now fails while the
  resource root row (or the `dms.Descriptor` row) still exists. Delete the root or
  `dms.Descriptor` row first, then the `dms.Document` row, which is the order DMS itself uses.

  **Only a newly provisioned database gets the new keys.** To get the new keys,
  provision a fresh database and reload it. See
  [Provisioning a database for an effective schema](../RELATIONAL-BACKEND.md#2-provisioning-a-database-for-an-effective-schema).

- **Application-level writes no longer change data store assignments, and the
  application credential reset is always available but refuses multi-client applications.**
  This affects Configuration Service API clients that manage applications with more than one
  API client, or that reassigned data stores through the application endpoint.
  - `PUT /v3/applications/{id}` no longer changes any API client's data store assignments.
    It ignores a `dataStoreIds` member in the request body. Assign data stores per client with
    `PUT /v3/apiClients/{id}`.
  - `POST /v3/applications` is unchanged: it still assigns its `dataStoreIds` to the
    application's first API client. `GET /v3/applications/{id}` still reports the union of the
    data stores assigned to all of the application's API clients.
  - `PUT /v3/applications/{id}/reset-credential` is always available. For an application with
    more than one API client it returns `409 Conflict` and resets nothing; reset a specific
    client's credentials with `PUT /v3/apiClients/{id}/reset-credential`. Single-client
    applications are unchanged.
  - The `AppSettings:EnableApplicationResetEndpoint` setting
    (`DMS_CONFIG_ENABLE_APPLICATION_RESET_ENDPOINT` in the Docker Compose files of earlier releases) is removed. A leftover value is
    ignored.

  See [API Client to Data Store Association](../API-CLIENT-AND-INSTANCE-CONFIGURATION.md#api-client-to-data-store-association).

- **Identity API body-validation `400`s are now `application/problem+json`.** This affects
  clients of the Identity API in `v8.1.0-beta.0.1`. On the three `POST` routes under
  `/identity/v2/identities` (create, `/find` and `/search`), a malformed body, an empty body or
  a duplicate property name was answered with `Content-Type: application/json`, although the
  served Identity OpenAPI document declares only `application/problem+json` for that `400`.
  DMS now sends the declared media type. Response bodies and status codes are unchanged, and
  `/data` routes keep `application/json` for the same errors. See
  [DMS-1595](https://edfi.atlassian.net/browse/DMS-1595) and
  [What a client sees](../IDENTITY-MANAGEMENT.md#what-a-client-sees).

- **The Configuration Service problem types use the Management API prefix.** Every
  problem-details `type` the Configuration Service returns now starts with
  `urn:ed-fi:management-api:` instead of `urn:ed-fi:api:`, matching the ODS Admin API v3
  implementation of the Management API. For example, a validation failure now has type
  `urn:ed-fi:management-api:bad-request:data`, and a failed client authentication at
  `/connect/token` has type `urn:ed-fi:management-api:security:authentication`.
  - Only the prefix changes. Suffixes, HTTP statuses, titles, details and every other member of
    the body are unchanged. A response whose status has no Ed-Fi problem type still uses
    `about:blank`.
  - DMS's own problem types are unchanged and keep the `urn:ed-fi:api:` prefix. This includes
    the responses from DMS `/oauth/token`.
  - Clients and scripts that compare Configuration Service `type` values, including those
    calling `/connect/token`, must match the new prefix.

  **Upgrade DMS before, or together with, the Configuration Service.** DMS recognizes the
  Configuration Service's token-limit 429 under either prefix. An earlier DMS paired with an
  upgraded Configuration Service still answers `429` at `/oauth/token`, but with the generic
  `urn:ed-fi:api:too-many-requests` type and without the "limit is N" message, until DMS is
  upgraded. See [DMS-1586](https://edfi.atlassian.net/browse/DMS-1586).

- **`POST /connect/token` on the Configuration Service answers `400`, not `502`, when Keycloak rejects the requested scope.**
  Under Keycloak, an `invalid_scope` answer from Keycloak now returns `400` with `type` `urn:ed-fi:management-api:bad-request` and `errors` of `["invalid_scope. <description>"]`, for example `invalid_scope. Invalid scopes: edfi_admin_api/readonly_access`.
  In 8.0.0 it returned `502`.
  A client that branched on that `502` must handle the `400`.
  Other Keycloak failures keep their previous answers: a failed connection, a `5xx` or any other `400` error code returns `502`, and a name-resolution failure or a timeout returns `500`.
  The self-contained provider is unchanged: it issues the requested scopes the client holds, and the client's registered scopes when it holds none of them.

- **The Configuration Service OpenAPI documents declare a working client credentials scheme, and their tags are renamed.**
  Both `/openapi/v1.json` and `/metadata/specifications` now declare an `oauth2_client_credentials` scheme whose `tokenUrl` is `<base>/connect/token`, built from the request scheme, host and path base, with the scopes `edfi_admin_api/full_access`, `edfi_admin_api/readonly_access` and `edfi_admin_api/authMetadata_readonly_access`.
  In 8.0.0, `/openapi/v1.json` declared no scheme, and `/metadata/specifications` pointed at `IdentitySettings:Authority` followed by `/connect/token`: under Keycloak a realm URL with no token endpoint, and in self-contained mode the configured authority host without the path base.
  Operations that need no token declare an empty `security` array.
  The title of `/openapi/v1.json` is now `Ed-Fi API Configuration Service API`.
  Operation tags now use Management API style names, such as `Vendors`, `ApiClients` and `Connect`, instead of the module class names, so a client generated from the document and grouped by tag changes its group names on regeneration.

- **Under Keycloak, `POST /connect/token` on the Configuration Service uses the HTTP Basic credentials when a request carries both Basic and form credentials.**
  In 8.0.0 the Basic header was ignored under Keycloak and the form fields authenticated the request.
  A client that sends both must send the same credentials in both, or only one of them.

- **DMS and the Configuration Service now send `Strict-Transport-Security` when they see HTTPS outside the `Development` environment.**
  This affects deployments where TLS ends at a proxy that adds its own HSTS and forwards HTTPS to the applications through `AppSettings:ReverseProxy:UseForwardedHeaders`.
  The applications send `max-age=31536000`, and a proxy that appends headers, as nginx `add_header` does, places its own field after it.
  Browsers honor only the first `Strict-Transport-Security` field, so a proxy policy with `includeSubDomains` or `preload` silently stops taking effect.
  To keep the proxy's policy, have the proxy remove the application's header first (nginx: `proxy_hide_header Strict-Transport-Security`), as the review gateway now does.
  See [DMS-1484](https://edfi.atlassian.net/browse/DMS-1484) and [Security response headers](../CONFIGURATION.md#security-response-headers).

- **DMS data API responses now carry `Cache-Control: no-store`.**
  This covers every response from the resource and descriptor endpoints, their `deletes` and `keyChanges` routes, and Change Queries `availableChangeVersions`.
  A browser or other HTTP cache no longer stores them, so a client that relied on its HTTP cache to revalidate resources must keep the `ETag` itself and send `If-None-Match`.
  DMS still answers `304 Not Modified` on a match.
  See [DMS-1484](https://edfi.atlassian.net/browse/DMS-1484) and [Security response headers](../CONFIGURATION.md#security-response-headers).

## New features

- **`EdFi.Api.SecurityMetadataTools` converts ODS security metadata XML to a complete
  Configuration Service claims document.** Use `security-metadata-tools convert-ods-xml`;
  conversion validates before writing and preserves exported authorization strategies.
  See the [Claims Loading Deployment Guide](../CLAIMS-LOADING-GUIDE.md) for loading.

- **The Configuration Service rate limits `/connect/*`.**
  **Before upgrading, configure the Configuration Service to trust the Ed-Fi API's token proxy,
  or raise or disable `ConnectRateLimit` limits.** Without trusted forwarding, proxied callers and
  the Ed-Fi API's system-token refresh share one source budget and can block each other.
  Paired Compose stacks configure this trust automatically. `/connect/token`, `/connect/revoke`,
  `/connect/register` and `/connect/introspect` now answer `429 Too Many Requests` with
  `Retry-After` once a source address exceeds 120 requests, or a source address and `client_id` pair
  exceeds 30 token, revocation and authenticated introspection requests (self-contained mode), in a
  60-second window. The body is the Ed-Fi `urn:ed-fi:management-api:too-many-requests` problem details
  on all four routes. Other revocation and introspection errors retain their OAuth format.
  Clients should reuse tokens to reduce traffic.
  Operators can tune or disable the limits through `ConnectRateLimit`. See
  [ConnectRateLimit](../CONFIGURATION.md#connectratelimit) and
  [DMS-1482](https://edfi.atlassian.net/browse/DMS-1482).

- **Token, revocation and authenticated introspection credentials have a client ID length limit.**
  `client_id` values longer than 1024 UTF-16 code units, including padding, are rejected before authentication:
  token returns an Ed-Fi validation `400`; revocation and authenticated introspection return OAuth `invalid_client`
  (`401` with a Basic challenge for Basic authentication, `400` otherwise). This also applies
  when rate limiting is disabled. See [ConnectRateLimit](../CONFIGURATION.md#connectratelimit).

- **`POST /connect/token` on the Configuration Service accepts HTTP Basic client authentication under Keycloak, and an omitted `scope` gets the default scope.**
  In 8.0.0, only the self-contained provider read `Authorization: Basic`; under Keycloak the credentials had to be form fields.
  Both modes now accept either, with Basic taking precedence: form fields only fill a value Basic left empty, and a malformed Basic value falls back to the form fields.
  A stock Swagger UI can now authorize against the Configuration Service in both modes.
  An omitted or empty `scope` is no longer forwarded to Keycloak, which then issues the client's default scopes; under Keycloak it previously returned `502`.
  The self-contained provider keeps issuing the client's registered scopes.

- **Vendor namespace prefixes are optional.** The Configuration Service accepts empty or
  omitted `namespacePrefixes` on vendor creation and update; explicit `null` is normalized
  to an empty string. Omitting the field on PUT clears all existing vendor prefixes and
  updates the namespace claim of its existing clients. Changes apply to newly issued tokens;
  previously issued tokens retain their claims until expiry. Each supplied prefix may now
  be up to 255 characters, matching the ODS/API (8.0.0 allowed 128). A downgrade to 8.0.0
  keeps the wider column, but 8.0.0 rejects a vendor POST or PUT carrying a longer prefix.
  Newly provisioned clients of vendors without prefixes receive tokens containing
  `"namespacePrefixes": ""` with either identity provider.
  Keycloak admin clients registered after the upgrade also receive this empty claim;
  existing admin clients are not automatically updated. No-prefix clients may use claim
  sets containing NamespaceBased authorization, but requests carrying an empty namespace
  claim receive `403` for operations using that strategy; other strategies retain their
  existing behavior. Repeated vendor POSTs still return `400`; use PUT to
  change an existing vendor. See the [DMS-1532 outcome](../../reference/design/configuration-service/DMS-1532-optional-vendor-namespace-prefixes-outcome.md).

- **A claims fragment can define a claim set.** When a fragment has non-parent resource claims
  (those without `"isParent": true`) and the base claims do not already declare the fragment's
  `name`, the Configuration Service registers that name as a new system-reserved claim set. The
  Management API cannot change or delete it, and removing the fragment later does not remove it.
  A provisioning script that creates a claim set with the same name through
  `POST /v3/claimSets` now receives `400 Bad Request`. See
  [Fragment File Structure](../CLAIMS-LOADING-GUIDE.md#fragment-file-structure).

- **Clients can discover tenant names without credentials or a `Tenant` header.** The
  Configuration Service adds `GET /tenancy`, which returns `{ "tenants": [ ... ] }` with the
  name of every configured tenant and nothing else. It needs no authentication, requires no
  `Tenant` header and ignores one if supplied. With multi-tenancy disabled it returns `200 OK`
  with an empty array, and it also returns `200 OK` with an empty array when multi-tenancy is
  enabled but no tenant exists yet, so an empty list does not by itself mean multi-tenancy is
  off. Clients should reach the endpoint through `urls.tenancy` rather than a fixed path.
  `GET /` advertises the endpoint as the absolute URL `urls.tenancy`,
  built the same way as `urls.openApiMetadata`; the response is otherwise unchanged. With
  multi-tenancy enabled, `GET /`, `GET /metadata/specifications` and `GET /openapi/v1.json`
  no longer require a `Tenant` header, so a client that knows no tenant name can read `GET /`,
  follow `urls.tenancy`, and then choose a tenant. `GET /v3/tenants/` is unchanged and still
  requires authentication. See
  [Tenant Header](../MULTI-TENANCY-GETTING-STARTED.md#tenant-header).

- **Both services send security response headers.** Every response from the DMS API and the
  Configuration Service carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
  `X-Frame-Options: DENY` and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`.
  `Strict-Transport-Security: max-age=31536000` is sent only over HTTPS as the application sees it,
  and never for `localhost`, `127.0.0.1` or `[::1]` or in the `Development` hosting environment.
  Non-2xx responses other than 304 carry `Cache-Control: no-store`.
  The token endpoints (DMS `/oauth/token` and every Configuration Service
  `/connect/*` endpoint) send `Cache-Control: no-store` with `Pragma: no-cache`, and authenticated
  Configuration Service responses send `Cache-Control: no-store`, as do the DMS claimset management
  endpoints, the DMS DocumentCache status endpoint (`/health/document-cache`) and every DMS data API
  response. DMS `/oauth/token_info` changes from
  `Cache-Control: no-cache` to `no-store`.
  A proxy that sends its own HSTS, and a client that relied on an HTTP cache for DMS resources, may
  need a change (see Breaking changes). See
  [DMS-1484](https://edfi.atlassian.net/browse/DMS-1484) and
  [CONFIGURATION.md](../CONFIGURATION.md#security-response-headers).
