# Changelog: 8.1.0

Brief descriptions of breaking changes and new features in this release, aimed at
integrators upgrading from the previous version. Each entry says what changed and what,
if anything, a client must do differently; the linked design documents carry the full
detail and rationale.

## Breaking changes

- **`POST /connect/revoke` now requires client authentication, and only revokes tokens
  belonging to the authenticated client.** The endpoint previously accepted anonymous
  requests. Callers must now present the same `client_id`/`client_secret` they use at
  `POST /connect/token`, either as HTTP Basic credentials or as `client_id` and
  `client_secret` form fields; a request without them is answered `401 Unauthorized`
  with the OAuth `invalid_client` error code. Note that these credentials identify the
  *caller* and are separate from the `token` form field, which names the token being
  revoked — a bearer access token in the `Authorization` header does **not**
  authenticate this request.

  A caller may only revoke a token whose `client_id` matches its own; a mismatch is a
  silent no-op that still returns `200 OK`, per RFC 7009. Because every authenticated
  outcome returns the same `200 OK`, confirm a revocation with
  `POST /connect/introspect` rather than relying on the status code.

  This applies when CMS is running its self-contained identity provider. Under
  `AppSettings:IdentityProvider = keycloak` the endpoint revokes nothing and is
  unchanged; revocation there is the responsibility of Keycloak.
  See [CS-AUTH.md](../../reference/design/configuration-service/CS-AUTH.md)
  and [OWASP-AUTH-COVERAGE.md](../OWASP-AUTH-COVERAGE.md).

- **The six `E2E-*` claim sets are no longer built in.** `E2E-NameSpaceBasedClaimSet`,
  `E2E-NoFurtherAuthRequiredClaimSet`, `E2E-RelationshipsWithEdOrgsOnlyClaimSet`,
  `E2E-RelationshipsWithEdOrgsOnlyInvertedClaimSet`,
  `E2E-RelationshipsWithEdOrgsOnlyMixedStrategyClaimSet` and
  `E2E-RelationshipsWithEdOrgsOnlyOrInvertedClaimSet` were test-only claim sets that earlier
  releases put in every deployment. New databases no longer get them; databases provisioned by an
  earlier release keep them. Creating an application with one of these names still succeeds, but
  on a new database DMS then rejects every request from that application's clients with a
  security-configuration error. Assign applications to a built-in claim set, such as
  `EdFiSandbox`, instead. To remove the old rows from an existing database, see
  [Upgrading an Existing Deployment: E2E Claim Sets](../CLAIMS-LOADING-GUIDE.md#upgrading-an-existing-deployment-e2e-claim-sets).

- **A POST that finds an existing record is authorized as `Update`, not `Create`.** A POST
  that creates a record still needs `Create` permission and runs `Create`'s authorization
  strategies. A POST whose identity matches a record that already exists, including an
  identical repost, now needs `Update` permission and runs `Update`'s strategies against the
  stored record, the same as a `PUT`. Previously every POST was checked as `Create`. This
  matches the ODS/API.

  The default claim sets are affected. For the `people` domain (Student, Staff, Contact and
  so on), `Create` uses `NoFurtherAuthorizationRequired` and `Update` uses
  `RelationshipsWithEdOrgsAndPeople`. For `primaryRelationships` (such as
  StudentSchoolAssociation), `Create` uses `RelationshipsWithEdOrgsOnly` and `Update` uses
  `RelationshipsWithEdOrgsAndPeople`. A client on `SISVendor`, `DistrictHostedSISVendor` or
  `EdFiSandbox` that re-POSTs an existing student not associated with its education
  organizations now receives `403 Forbidden` where it previously received `200 OK`.

  A client whose claim set grants `Create` but not `Update` can no longer change an existing
  record by POST; a client granted `Update` but not `Create` can now do so. A POST that neither
  action permits is still refused as a `Create` denial. Loaders that re-run against existing
  data need `Update` as well as `Create`: the built-in `SeedLoader` claim set now grants both,
  while `BootstrapDescriptorsandEdOrgs` still grants only `Create`, as in the ODS/API (see
  [SCHOOL-YEAR-LOADER.md](../SCHOOL-YEAR-LOADER.md)).

  **Upgrade step for an existing Configuration Service database.** The Configuration Service
  writes its shipped claims only into empty claims tables, so a database created by 8.0 keeps
  the Create-only `SeedLoader` grants it was first loaded with. Re-running seed delivery against
  it fails with `403` on the first record that already exists. Before that rerun, call
  `POST /management/reload-claims` to rebuild the claims from the shipped files. The endpoint
  needs `DMS_CONFIG_DANGEROUSLY_ENABLE_UNRESTRICTED_CLAIMS_LOADING=true` and an admin-scope
  token. The reload replaces the non-reserved claim sets and the whole claims hierarchy, so export
  any claim set that exists only in the database (`GET /v3/claimSets/{id}/export`) first and
  re-import it afterwards (`POST /v3/claimSets/import`). `SeedLoader` is
  system-reserved, so `/v3/claimSets` cannot add the grant to it directly.

## New features

- **A claims fragment can define a claim set.** When a fragment has non-parent resource claims
  (those without `"isParent": true`) and the base claims do not already declare the fragment's
  `name`, the Configuration Service registers that name as a new system-reserved claim set. The
  Management API cannot change or delete it, and removing the fragment later does not remove it.
  A provisioning script that creates a claim set with the same name through
  `POST /v3/claimSets` now receives `409 Conflict`. See
  [Fragment File Structure](../CLAIMS-LOADING-GUIDE.md#fragment-file-structure).
