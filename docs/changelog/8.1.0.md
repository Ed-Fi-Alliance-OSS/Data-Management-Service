# Changelog: 8.1.0

Brief descriptions of breaking changes and new features in this release, aimed at
integrators upgrading from the previous version. Each entry says what changed and what,
if anything, a client must do differently; the linked design documents carry the full
detail and rationale.

## Breaking changes

- **`POST /connect/revoke` now requires client authentication, and only revokes tokens
  belonging to the authenticated client.** The endpoint previously accepted anonymous
  requests. Callers must now present the same `client_id`/`client_secret` they use at
  `POST /connect/token`, either as HTTP Basic credentials or as `client_id` and
  `client_secret` form fields; a request without them is answered `401 Unauthorized`
  with the OAuth `invalid_client` error code. Note that these credentials identify the
  *caller* and are separate from the `token` form field, which names the token being
  revoked — a bearer access token in the `Authorization` header does **not**
  authenticate this request.

  A caller may only revoke a token whose `client_id` matches its own; a mismatch is a
  silent no-op that still returns `200 OK`, per RFC 7009. Because every authenticated
  outcome returns the same `200 OK`, confirm a revocation with
  `POST /connect/introspect` rather than relying on the status code.

  This applies when CMS is running its self-contained identity provider. Under
  `AppSettings:IdentityProvider = keycloak` the endpoint revokes nothing and is
  unchanged; revocation there is the responsibility of Keycloak.
  See [CS-AUTH.md](../../reference/design/configuration-service/CS-AUTH.md)
  and [OWASP-AUTH-COVERAGE.md](../OWASP-AUTH-COVERAGE.md).
